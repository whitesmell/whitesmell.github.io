上周，腾讯将大语言模型与多模态模型团队合入基础模型部，由姚顺雨统一负责。比组织图更值得看的，是一位接近腾讯高层人士提到的细节：姚顺雨曾向总裁刘炽平请求，新模型发布后，至少一年不要看 Benchmark——大约给团队两代模型的时间，放下短期排名，先把训练基础设施、数据和评测重新做扎实。

克制

“一年不看榜单”，不是不要评测。

恰恰相反，它是要把评测重新当回事。

姚顺雨以顾问身份排查混元时，检查了模型训练的各个环节，也去元宝、微信等产品团队听反馈。据一位在场人士转述，他在会上指出，团队过度追逐榜单，打榜语料被放进训练集，污染了评测。模型在榜单上很好看，进了真实场景却不好用。

Benchmark 能成立，有两个前提：测试数据没有参加训练，测试任务又能代表模型未来要面对的问题。打榜语料一旦混进训练集，分数测到的就可能是记忆和针对性优化，而不是泛化。

更麻烦的是，当排名成为组织的交付目标，团队会自然地围着分数工作。数字不断上涨，用户体验却可能停在原地。

他希望团队戒掉的，正是这种急功近利：杜绝数据污染，也不再拿榜单掩盖产品问题。

到了 Agent 阶段，同一种错觉更容易出现。

pi、OpenClaw、Codex、Claude Code 已经能读文件、调工具、执行命令，再根据结果继续工作。它们都保留着一个简单骨架：观察，思考，行动，再观察。

模型因此可以写出很长的计划，调用十几个工具，跑上几十步。整个过程看起来很忙。

可调用工具只是动作，不是结果。

工单有没有关闭？代码有没有通过测试？退款有没有回到账户？生成的文件能不能直接交付？这些最终状态，才决定任务是否完成。

姚顺雨在访谈里给过 Agent 一个更严格的定义：它能够自主决策，与环境交互，并试图优化 Reward。

工具扩大的是动作空间。环境返回什么反馈，系统奖励什么结果，决定了 Agent 学会的是完成任务，还是迎合指标。

计划写得再漂亮，也不能替代交付；轨迹跑得再长，也不能替代验收。

一道问题，追了六年

姚顺雨对这个问题的追问，比今天这轮 Agent 热潮早得多。

2020 年，他和合作者发表 CALM，让 Agent 进入文字游戏。

文字游戏的难点不是按钮太少，而是动作几乎可以用任意语言表达。CALM 先让语言模型根据游戏历史生成一组更可能有效的动作，再由强化学习 Agent 重排选择。面对训练时没见过的游戏，它的平均得分比此前最好方法相对提高 69%。

Agent 先跨过的，是动作门槛：当选择近乎无限，怎样找到值得尝试的下一步。

两年后的 WebShop，把问题推向更真实的互联网环境。模拟网站里有 118 万件真实商品和 12087 条众包指令。Agent 要理解需求、搜索商品、翻页、选择规格，最后完成购买。

当时最好的模型，任务成功率只有 29%；人类专家是 59%。

模型已经会读、会搜、会点，却还是经常买错。

姚顺雨后来回忆，WebShop 最难的不是把购物网站模拟出来，而是设计 Reward。奖励必须落在最终结果上，基于规则、可计算、可解释。过程看起来合理，不代表结果正确；代码写得再漂亮，没有解决问题，也不该得到奖励。

到了这里，难题从生成动作转向判定结果：Agent 做完之后，世界怎样告诉它对还是错。

同一年的 ReAct，把 Reasoning 与 Acting 交错放进一条轨迹。模型不再一次写完计划，而是边行动、边获取新证据，再根据环境变化修正推理。

在 ALFWorld 和 WebShop 上，ReAct 只使用一两个上下文示例，相比当时的模仿学习与强化学习方法，绝对成功率分别提高了 34 个和 10 个百分点。

推理由此进入行动循环。

今天常见 Agent 的最小内核，依然能看见 ReAct 的影子。权限审批、重试和追踪让循环更适合生产环境，却没有改变最基本的事实：Agent 必须一边做，一边看世界发生了什么。

CALM 处理动作，WebShop 构造环境与结果奖励，ReAct 让推理和行动互相修正。六年里，问题不断向现实靠近：

模型怎样进入一个陌生世界，把一件事真正做成？

2025 年，姚顺雨在《The Second Half》里把这个问题推到了 AI 主线：

“The second half of AI will shift focus from solving problems to defining problems.”

AI 的下半场，将从解决问题转向定义问题。

当一种通用方法开始能够解决越来越多的考试、游戏和编程题，继续把题目做难，已经不够了。更重要的问题变成：AI 应该做什么，怎样衡量真实进步。

这就是他所说的 Utility Problem：模型在考试、数学、编程和游戏中迅速变强，现实价值却没有按同样速度增长。

ReAct 把循环转了起来。《The Second Half》追问的是：循环应该驶向哪里，什么结果值得被奖励。

代码为什么先跑出来

姚顺雨在访谈里说过一句很形象的话：

“Code 有点像人的手。”

手让人可以使用锤子、笔和筷子。Code 则让 Agent 能够读取文件、调用软件、操作系统，改变数字世界。

更关键的是，代码环境会判分。

仓库可以读取，命令可以执行，编译器和日志会报错，测试可以验收，Git 还能记录和回滚每一次修改。Agent 做完一步，环境很快就会告诉它哪里错了。

姚顺雨认为，Coding 之所以最早跑出来，是因为它对 Agent 相对简单：Reward 清楚，不需要先构造一个复杂环境，本身又需要推理。

这里的“简单”，不是说软件工程在人类世界里容易，而是它更容易被机器定义和验收。

2023 年发表 InterCode 时，姚顺雨和合作者追问过一个当时并不主流的问题：模型生成代码之后，为什么不把执行结果再反馈给它？

他们把一次性代码生成改成多轮 Agent 任务。模型不只提交答案，还要读取运行结果、发现错误、继续修改。今天 Coding Agent 里最常见的“写代码—跑测试—再修改”，已经能看到这条思路。

CodeBuddy正好工作在这种环境里。它提供插件、IDE 和 CLI 三种形态，进入编码、评审、测试与运维流程。腾讯披露，CodeBuddy 已覆盖公司超过 95% 的工程师，整体编码时间缩短 40%。

这些是腾讯的内部口径，不是独立测评。但抛开效率数字，CodeBuddy 仍然说明了 Coding Agent 为什么先成熟：状态可读，动作可执行，结果可复现，失败还能立刻进入下一轮修正。

客服和企业协作就没有这么干净。

一段回复看起来合理，不等于工单已经关闭；流程显示完成，不等于用户不需要返工。任务还散落在多人对话、业务系统、权限关系和没有写下来的规则里。

模型没有突然变笨。

它只是从一间能自动判卷的考场，走进了没有标准答案的工作现场。

真正难的是工作现场

真实工作不会像 Benchmark 那样，一次把完整问题交给 Agent，再安静等它返回答案。

人会补充需求、确认风险、纠正方向，有时还会中途改变目标。客服需要在多轮对话中遵守政策、调用系统、处理例外；办公任务则会跨越文档、会议、表格和不同的人。

不同任务对“成功”的要求也完全不同。

写作和创意允许多试几次，只要有一次足够好。客服看起来更简单，却可能要求一百次里九十九次都不能出错。把两类任务压成一个平均分，产品最在意的可靠性就消失了。

真实工作还是连续的。

昨天改过的代码、上周确认的权限、用户反复强调的偏好、某次事故留下的教训，都会改变今天的决定。这些不会自动出现在一个更长的 Prompt 里。

这就是 Context。

姚顺雨举过一个很日常的例子：普通员工进入公司七天，推理能力依然远不如前沿模型，却可能已经比模型更会做事。因为他开始熟悉老板的习惯，也积累了许多没有写进文档的信息。

缺少 Context，Agent 每次都像第一天上班。

WorkBuddy 是腾讯把 Agent 从代码环境推向办公环境的一次尝试。它可以读写本地文件、调用工具、拆解并执行任务，也能在项目空间沉淀流程与知识。

企业版又把腾讯文档和组织知识接进工作台：人和 Agent 可以在同一份文档里接力，腾讯会议沉淀的上下文也能被 Agent 调用。重点不是功能又多了几个，而是任务状态开始留在同一个工作环境里。

多模态把这个问题继续向外推。

姚顺雨判断，Code 与 GUI 最终不会二选一。Agent 可以调用为机器准备的 API，也可以读取截图、操作原本为人设计的界面。就像让车适应不同的路，比把所有道路都改造成 API 更现实。

屏幕上的按钮、视频里的动作、语音中的意图、游戏里的空间关系，都会成为任务状态。Agent 每进入一种新模态，不只是多了一种输入，也多了一组可能出错、需要验收的结果。

所以，多模态不是能力表上的加法。它扩大的是 Agent 能够进入的世界。

腾讯能不能把场景变成回路

姚顺雨在与汤道生的一次对谈中，把加入腾讯的原因归到场景和产品：模型可以在这里获得真实输入与 Context。

模型方法逐渐通用之后，好问题越来越多地藏在产品里：用户在哪里中断，为什么返工，哪种错误绝不能发生，什么结果才愿意付费。

腾讯并不缺这样的现场。微信、文档、会议、代码、云服务、内容和游戏里，装着大量真实任务。难的是，这些场景过去并不会自动流向模型。

一位混元人士称，混元的模型与产品之间曾长期存在割裂：模型有自己的技术目标，产品有自己的迭代节奏。模型追榜单，产品等能力，很多设想卡在两支团队中间。

姚顺雨推动的 Co-design，是让双方从定义任务时就绑在一起。混元向业务派驻后训练团队；新模型针对 WorkBuddy 的运行框架适配，WorkBuddy 的用户反馈再成为模型优化的方向。

这不是多开几次会。它要让模型和产品共享同一组任务、失败与验收标准。

磨合仍然存在。一位混元人士描述过两边最常见的时间差：产品催着要一个本周就能上线的迭代，模型团队想的却是下个版本怎样提升整体能力。

姚顺雨在访谈中用 iPhone、ChatGPT 和微信做过类比：通用产品形态要获得持续增长，仍然需要每个阶段的 Killer App。

放到腾讯，CodeBuddy 和 WorkBuddy 的价值就不只是多两款 AI 产品。前者把 Agent 放进反馈清楚的代码环境，后者试着进入 Context 更复杂的办公现场；腾讯文档和腾讯会议沉淀工作状态，ADP、ClawPro 与 Agent Runtime 支撑连接、运行和治理。

这套产品组合还远不能证明腾讯已经跑通 Agent 下半场，但几种必要角色已经出现：模型提供智能，产品提供任务与 Context，基础设施让 Agent 行动，产品反馈再帮助模型修正问题。

Hy3 的模型卡把产品反馈列为改进依据。Preview 版本先接入 CodeBuddy、WorkBuddy、元宝等产品；正式版披露的内部评测显示，幻觉率从 12.5% 降至 5.4%，多轮问题率从 17.4% 降至 7.9%。

腾讯还披露，WorkBuddy 接入 Hy3 Preview 后，首次响应速度提升 54%，平均任务完成时间缩短 47%。

这些数字仍来自腾讯自己的评测。它们不能代替真实任务中的长期结果，却至少把模型优化从榜单拉向了具体产品问题。

据一位混元人士转述，姚顺雨还给团队设想过一个更直接的目标：不必在所有能力上击败最前沿模型；如果能用对方 1% 的价格，在 90% 的日常问题上做到相当甚至更好，对多数用户就可能更有价值。

这比“冲到榜单第几名”难得多。它要求团队先知道用户真正做什么、愿意承担多少成本，再决定模型该往哪里长。

基础模型、产品落地、前沿研究——姚顺雨把长期 AGI 组织概括为这样一个平衡三角。真正的挑战不是把三个词写进组织图，而是让三者围绕同一个结果转起来。

组织可以在一天内合并，真实任务仍然横跨整家公司。模型团队要长期能力，产品团队要本周上线；技术路线可以统一，数据、权限、利益和节奏不会自动统一。

腾讯的产品越多，机会越大，这道组织题也越难。

这才是混元重组值得观察的地方。不是语言、图像、视频和 3D 最终会不会塞进同一个模型，而是它们能否围绕同一项任务协作；产品里的失败，能否变成下一轮评测、数据和训练。

过去几年，Agent 先解决了怎样让模型行动。

下半场要解决的是：哪些问题值得行动，世界怎样判定成败，系统能不能从失败中继续学习。

榜单只能证明模型通过了一场考试。真正的 Agent，要让现实世界持续出题、判分，再把每一次失败变成下一次进步。

子非AI，焉知AI之乐。
