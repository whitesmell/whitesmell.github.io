模型API卖的是智力，Agents API开始交付一段能够持续工作的过程。它替开发者接管了最麻烦的Agent工程，也开始保管Agent最难迁移的工作状态。

一个Agent最轻松的时刻，往往是它第一次运行成功的时候。

它读懂指令，调用工具，生成文件，Demo顺利结束。台上的人开始谈论“数字员工”，台下的工程师却知道，麻烦才刚刚开始。

任务运行了两个小时，连接断了怎么办？上下文快满了，哪些信息必须留下？工具调用失败，应该重试、回滚，还是换条路继续？用户中途修改要求，Agent能不能立即转向？当它开始读文件、执行命令、访问内网，密钥和权限又该交给谁？

十几行代码可以证明模型会使用工具，却证明不了它能在生产环境里把事情做完。

OpenAI最新发布的Agents API，就是来填这条鸿沟的。它没有带来新模型，也不是给Agents SDK换了一个名字，而是把Codex背后那套负责会话、编排、上下文压缩、工具执行和任务恢复的Harness，做成了一项托管服务。

过去，开发者调用OpenAI，得到的是一次模型响应。现在，OpenAI试图交付一段跨越多个轮次、可以观察、干预和继续推进的工作过程。

Agent的竞争，由此离开聊天框，进入运行时。

OpenAI开始出售Codex的“工作方式”

Harness不是模型，也很难简单翻译成“框架”。

它更像Agent的工作系统：模型只负责判断下一步，Harness负责保存任务状态、组织模型与工具协作、管理越来越长的上下文，并推动任务继续向前。

按照OpenAI Docs，Agents API围绕四个核心对象运行：

Agent定义模型、指令、工具和MCP服务；Environment提供文件、Skill、命令行和代码执行环境；Session保存一项持续工作的任务；Events与Items记录模型输出、工具调用和执行结果。

换成更直白的话：

Agent决定谁来干，Environment决定在哪里干，Session保存这份工作，Harness负责让工作继续。

此前，开发者主要购买模型的“大脑”，其余部分要自己搭建。现在，OpenAI开始把工作记忆、执行环境和任务调度一起提供。

这才是Agents API与普通模型接口的根本区别。

Agent走到了第三个阶段

回看Agent过去几年的演进，大致经历了三个阶段。

最早是Prompt。人们试图用一段指令定义Agent是谁、要做什么、应该怎样回答。

随后是Context。企业很快发现，模型再聪明，不理解内部文档、业务规则、历史决策和当前状态，也做不了真实工作。RAG、长期记忆、知识库和Context Engineering因此成为主角。

现在，重心开始转向Harness。

当Agent开始修改文件、运行代码、连接业务系统、协调多个子任务，它面对的已经不只是“知道什么”，而是“如何持续行动”。

Prompt定义行为，Context提供知识，Harness组织行动。

这三个阶段并非相互替代。一个生产级Agent必须同时具备三者：知道目标，理解业务，还能把任务稳定地推进到结果。

Agents API释放的信号是，模型能力依然重要，但Agent产品最难复制的部分，正在从模型本身转向模型之外的运行系统。

代码只有十几行，系统并没有消失

官方快速入门代码很短：

from openai import OpenAI

with OpenAI() as client:
    with client.beta.agents.sessions.create(
        agent={"model": "gpt-6-astra"},
        environment={"type": "openai_hosted"},
        input="创建并运行一个脚本，返回实际输出",
        stream=True,
    ) as events:
        for event in events:
            print(event.to_json())

这一次请求内联配置Agent，创建Session，启动OpenAI托管的Sandbox并提交任务，再通过事件流持续返回进度。官方快速入门目前仍使用Beta接口。

几行代码背后，Agent已经获得了一套完整运行时。

它可以在Sandbox中执行命令、编辑文件和生成Artifact；通过MCP和函数连接外部系统；在工作过程中接收追加指令；当上下文越来越长时压缩已有工作；遇到适合拆分的任务，还能派出拥有独立上下文的子Agent并行处理。

客户端不必始终保持连接。应用既可以通过事件流观察每一步，也可以依靠Webhook获知任务完成、失败或者正在等待输入。

从架构看，开发者自己的应用负责用户、业务权限、审批和产品体验；OpenAI托管Harness，负责模型循环、Session和上下文；Environment则负责代码、命令和文件的实际执行。官方架构说明

代码减少了，是因为复杂度从应用里搬进了OpenAI的平台，而不是因为复杂度已经消失。

开发者真正纠结的，不是功能够不够多

Agents API发布后，公开讨论很快越过了功能列表，集中到一个更现实的问题：

Harness究竟是可以外包的基础设施，还是Agent产品必须掌握的核心能力？

选择托管的理由很务实。

如果产品真正的竞争力在行业知识、专有数据和业务工具，自建Session服务、上下文压缩、任务队列、Sandbox控制面和多Agent调度器，很可能只是在重复修建管道。

让OpenAI维护这层基础设施，团队可以更快验证业务，而不是先把自己变成一家Agent Runtime公司。

谨慎者担心的，则不只是模型绑定。

过去更换模型，可能只需要调整接口和提示词；进入Harness时代后，真正难迁移的对象变成了Session状态、上下文压缩方式、工具调用历史、Artifact格式，以及任务失败后的恢复逻辑。

这时，锁定你的已经不是某个模型，而是Agent形成的整套工作方式。

Agents API最吸引人的地方和它最大的风险，恰好来自同一个设计：

OpenAI替你接管了最麻烦的Agent工程，也开始保管Agent最难迁移的工作状态。

“自托管”背后，有三条不能混淆的边界

托管服务让接入变得简单，却没有消灭软件工程的基本规律。

首先，自托管Sandbox不等于私有部署Agent。

在Self-hosted模式下，企业运行的是执行器和Sandbox，OpenAI仍然运行Harness。代码、文件、依赖、私网服务和计算资源可以留在企业环境中，执行器通过出站WebSocket接收Harness下发的命令，不必对公网开放入站端口。自托管Sandbox文档

这更像企业自带工作台，而不是整套Agent进入企业内网。

其次，Session持久不等于工作目录永久存在。

Session可以比Environment活得更久，但OpenAI托管Sandbox中的文件只在环境存续期间保留。写入/workspace/outputs的文件会在当前Turn完成时发布为不可变Artifact，Sandbox过期后仍可下载；关键数据仍然需要同步到企业自己的持久化系统。文件与Artifact说明

Session保存的是任务过程，不是一块永久硬盘。

最后，可以恢复不等于命令自动续跑。

客户端事件流断开，不会自动取消正在运行的任务；应用重新连接后，也可以读取Session中已经保存的消息、工具调用和Turn结果。但自托管执行器中途断线仍可能导致工具调用失败，已经终止的命令不会自动重启，进程崩溃后尚未完成的输入也不保证恢复。环境生命周期说明

如果Agent能够修改数据库、发送消息或者触发业务流程，应用仍需自己设计幂等、检查点、审批和补偿机制。

“可恢复的Agent”和“永不失败的数字员工”之间，隔着真实的软件工程。

谁应该现在使用Agents API

是否使用Agents API，不取决于团队是不是“拥抱Agent”，而取决于希望把运行时控制权放在哪里。

如果业务主要是直接调用模型，或者团队准备自行掌握Agent循环、历史状态和执行环境，Responses API更加合适。

如果需要自定义工具、Handoff和多Agent工作流，同时希望控制部署、存储与审批，可以使用运行在应用内部的Agents SDK。

如果任务需要长时间运行、跨轮次保留进度、操作文件、调用大量工具，还要允许用户中途干预，Agents API才真正体现价值。官方运行时对比

它尤其适合代码调查、数据分析、故障响应和文档审核等任务。这些场景目标相对明确，过程能够观察，结果可以验证，又确实需要文件、命令和持续工作的Session。

相反，一次性问答、简单信息抽取，或者只调用一两个工具的流程，没有必要为了“Agent”这个名字引入更重的运行时。

还有一条更重要的判断：

如果Harness只是产品的公共管道，托管通常更经济；如果多模型路由、Context策略、成本控制、私有化执行和失败恢复本身就是产品竞争力，那么Harness值得掌握在自己手中。

Agent平台的价值，将向两端移动

Agents API会给一类公司带来直接压力：那些只在模型API外面包了一层简单循环的“薄平台”。

当Session、上下文压缩、Sandbox、MCP和子Agent调度逐渐变成上游能力，单纯依靠流程编排将越来越难形成溢价。

Agent平台的价值会向两端移动。

向下，是多模型路由、端云协同、私有化Harness、权限、安全和审计；向上，是企业知识、行业工具、业务流程，以及一套能证明任务“确实做对了”的验收体系。

中间那层通用编排能力，则会越来越像云计算时代的数据库、消息队列和容器服务：依然重要，但未必需要每家公司从头建造。

这也是Agents API不会终结自建Harness的原因。它只是迫使每个团队重新回答一个问题：

你的护城河，究竟在哪一层？

如果答案只是“我们也能让模型调用工具”，这道护城河正在迅速变浅。

如果答案包括独有的知识Context、组织权限、业务闭环、成本结构和验收体系，那么上游运行时越成熟，反而越容易放大这些差异。

一场比模型更深的卡位

Agents API目前仍处于Public Beta。企业接入之前，还有几条现实限制需要考虑。

Agent生成的代码能够访问Environment中可见的文件、凭证和网络。官方建议隔离不同用户和工作负载，限制出站访问，把应用主密钥留在Sandbox之外，并通过受限凭证或代理访问第三方系统。Sandbox安全说明

费用也不只有模型Token，还包括工具调用和托管容器。任务越长、子Agent越多、失败重试越频繁，推理与计算成本越容易失控。官方定价说明

合规边界更加明确：Agents API目前只支持美国数据驻留，不具备Zero Data Retention资格；选择自托管Sandbox，也不会改变这一限制。官方数据控制说明

这些限制不会抹掉Agents API的价值，却决定了哪些场景可以立即使用，哪些场景仍需等待或者自建。

过去两年，行业不断追问哪家模型更聪明。Agents API把问题向前推了一步：

模型再聪明，如果缺少工作状态、执行环境和失败恢复，也只能完成一次精彩演示；Harness再稳定，如果缺少企业知识、业务权限和验收标准，也很难创造可靠的业务结果。

Agent的技术栈正在形成一条清晰的分工：

模型决定通用能力的下限，知识Context决定业务能力的上限，Harness决定这些能力能否持续转化为结果。

OpenAI正在把Harness做成公共基础设施。

它降低了Agent进入生产环境的门槛，也把竞争推向了一个更深的位置。企业接下来要回答的已经不只是“选择哪家模型”，而是：

谁保存Agent的工作状态，谁控制它的行动边界，失败之后又由谁承担后果？
