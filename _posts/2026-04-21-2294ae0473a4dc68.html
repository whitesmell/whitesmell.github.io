AI编程最大的问题，不是"写不出代码"。

是"想都不想就写"。

这是Karpathy在去年的观察，原话是这么说的：

"The models make wrong assumptions on your behalf and just run along with them without checking."

它们替你在不核对的情况下做出错误假设，然后一路狂奔。

说实话，我看到这句话的时候后背发凉。

因为我太清楚那种感觉了——让AI加个小功能，它吭哧吭哧给你整了五个文件，回头一跑，三四个bug全是它自己引入的。

你问它为什么改这些？

它说："我觉得这样更合理。"

这就是Karpathy说的"AI不思考的病"。

你的AI在犯这4个致命习惯

习惯一：替我做决定，还不问

AI拿到一个模糊的需求，不会先确认，而是直接猜。猜对了皆大欢喜，猜错了——你花半小时debug，发现问题出在AI自己编的那个"假设"上。

你有没有过这种经历：AI给你解释为什么这样实现，你说"我什么时候说过要这样？"。

习惯二：遇到问题不提问，直接跳过

它们不管理自己的困惑。遇到模棱两可的地方，它不问你，而是凭直觉选一个方向继续干。结果往往是那个你最不想要的方向。

习惯三：给你最复杂的那个方案

能用100行解决的问题，AI给你写1000行。不是因为它不会简化，是因为它不问你"要不要简化"。1000行看起来"更专业"，不是吗？

习惯四：改完就跑，不验证

AI很少主动说"我写完了，你验证一下"。它默认"跑通就是成功"。但很多问题只有在特定场景下才会暴露，AI不会主动制造那个场景。

这四个习惯，说白了都是同一个问题：

AI不习惯"停下来想"。

Karpathy开出的药方：先想后写

四个原则，说白了就是：

第一条：Think Before Coding

写代码之前，先把你脑子里的假设说出来。不确定的地方，要问。别silent failure——别在沉默中替用户做决定。

遇到多步任务？先列计划，每一步怎么验证，然后才开始。

第二条：Simplicity First

能用50行解决的事情，不要写200行。不要给还没到来的问题写"预防性代码"。你不需要为"万一产品要加这个功能"预留空间——除非产品真的说要加。

Karpathy的原话很狠：如果你写了1000行但100行就够了，重写。

第三条：Surgical Changes

只切该切的地方。改代码的时候，不要"顺便优化"旁边的代码，不要顺手把注释也改了，不要改格式。

测试标准：每一行被修改的代码，都能追溯到用户的原始需求。

第四条：Verify Before Done

定义清楚"完成"长什么样。最理想的是测试——"加了这个功能"就写这个功能的测试，"修了这个bug"就写能复现bug的测试。

没有测试的时候，至少跑一遍手动验证。

别让AI说"我干完了"就真的认为干完了。

# Claude Code
cp targets/claude/CLAUDE.md /你的项目/

# 或者用 Skill 格式
cp targets/claude/skills/karpathy-skills/SKILL.md ~/.claude/commands/

加完之后，Claude Code在写代码之前，会先说"我的假设是XXX"，遇到模糊的地方会先问你，遇到复杂方案会先说"要不要简化一下"。

不是AI变聪明了，是AI变谨慎了。

工作原理

项目的设计很巧妙：单一真相源——一个 core.md 文件定义了所有原则，scripts/build.sh 会把它转换成各工具对应的配置文件。

改一行规则，所有工具的配置同时更新。

附：Karpathy 四大原则详解

本节来自项目 whitesmell/karpathy-skills 的 core.md

原则一：Think Before Coding

不要假设。不要隐藏困惑。呈现权衡。计划先于构建。

遇到多步任务时，先列计划：

1. [步骤] → 验证：[如何确认]
2. [步骤] → 验证：[如何确认]
3. [步骤] → 验证：[如何确认]

先得到对计划的确认，再开始写代码。

原则二：Simplicity First

如果一位 senior engineer 说"这太复杂了"，那就简化。

  • • 不做超出需求的功能
  • • 不给单一使用的代码写抽象
  • • 不预留"以后可能用到"的配置
  • • 200行能解决就不要写1000行

最小代码解决明确的问题。不做假设性扩展。

原则三：Surgical Changes

只触碰必须改的地方。只清理你自己的烂摊子。

  • • 不要"顺便优化"相邻代码
  • • 不要改动没坏的地方
  • • 匹配现有风格，即使你会有不同做法
  • • 你改的每一行代码，都能追溯到用户的原始需求

原则四：Verify Before Done

定义"完成"长什么样。移动之前先确认。

测试是最强的验证形式——优先用测试：

  • • "加验证" → 先写无效输入的测试，再让测试通过
  • • "修bug" → 先写能复现bug的测试，再让测试通过
  • • "重构X" → 确保测试在重构前后都通过

没有测试时，用最可靠的替代方案验证，但永远不要跳过验证这一步。

写在最后

适合谁用？

如果你用AI编程工具写过生产级代码，你应该会感谢这套规则。它不会让AI更聪明，但会让AI更少自作主张。

不适合谁？

快速探索、试错的时候可以先不加。约束太多反而影响探索效率。
