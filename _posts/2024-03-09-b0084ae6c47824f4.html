本文讲述了作者在初创公司 Reka 从零开始训练超大语言模型 (LLM) 的经历。作者分享了他们在训练过程中遇到的各种挑战，包括硬件选择、代码库选择、以及训练策略等。作者也总结了一些经验教训，希望对其他想要训练 LLM 的人有所帮助。

以下是文章的一些亮点：

  • 作者分享了他们在选择硬件和代码库时遇到的挑战。

  • 作者介绍了他们使用 YOLO 策略训练 LLM 的经验。

  • 作者总结了一些经验教训，包括：

    • 构建世界一流的训练基础设施需要时间和精力。

    • 选择合适的硬件和代码库对成功训练 LLM 至关重要。

    • YOLO 策略可以帮助快速找到有效的训练方法。

这篇文章对以下人群有所帮助：

  • 想要了解如何训练 LLM 的人

  • 对 LLM 训练技术感兴趣的人

  • 正在考虑在初创公司训练 LLM 的人


这篇文章献给各位热爱折腾的 AI 技术爱好者们！最近，许多小伙伴对 Reka 公司白手起家训练超大语言模型（LLM）的经历感到好奇，尤其是我们如何从零构建基础设施并训练 LLMs 的过程。由于我经常在社交媒体上吐槽外部（谷歌之外）的基础设施和代码，大家更是对我在这个“荒野”中的各种心酸血泪史充满兴趣。那么，今天这篇文章就来满足大家的求知欲！

荒野炼丹的第一道坎：硬件彩票

训练模型，首先要解决算力问题。看起来容易吧？但现实却让人大吃一惊。各种算力提供商的稳定性差异惊人，集群、加速器以及它们之间的连接质量更是天差地壤。

大家可能认为，只要选对加速器（TPU 还是 GPU 等），所有的 GPU 集群都差不多。然而，对于我们来说，这种想法很快就被击碎了。在尝试过不同的服务商之后，我们发现即使是相同的硬件（比如 H100 GPU），集群的质量差异也巨大。这里需要注意的是，这里的“硬件”指的是整个集群的质量，而不仅仅是芯片或加速器本身。

简单来说，就像买彩票一样，你永远不知道会拿到什么样的硬件。

什么意思呢？

  • 并非所有硬件生而平等。不同供应商提供的集群质量差异巨大，就好比一场关于训练痛苦程度的抽奖。

  • 我们租用过几家供应商提供的集群，规模从几百到几千颗芯片不等。有些集群勉强可用，只是有一些小问题，通过工程师稍微折腾就能解决。但有些集群简直是灾难，每隔几小时就会因为各种各样的原因宕机。比如，某些集群的节点每隔 N 个小时就会出故障，问题范围从线路问题（这里的 N 可小到令人发指）到 GPU 硬件错误等五花八门。更让人吃惊的是，同一个供应商提供的不同集群，在稳定性方面也可能存在巨大差异。

  • 性能差异也让人头疼。有些集群的节点虽然更稳定，却因为 I/O 和文件系统性能低下，以至于保存检查点都可能超时，或者花费大量时间，极大地降低了集群的利用率。还有一些计算资源需要完全不同的软件层才能运行，并且对自带代码库的团队非常不友好，需要额外的迁移成本才能运行实验或大型任务。

  • 没有完美的方案，但有些供应商明显比其他供应商更糟糕。

最让人抓狂的是，几乎无法提前预知会拿到什么样的硬件，以及整个训练过程的稳定性和容错性如何。更糟糕的是，你也没法保证供应商是否会按时交付，或者延期几个月发货，让你在接下来几周甚至几个月内都无法从其他来源采购所需的算力。有些供应商甚至会误删你的检查点……

哦，对了，我还忘了提不同集群的模型计算峰值利用率（MFU）也会有所不同！如果不幸遇到一个节点线路问题严重的供应商，那么这部分流失的算力将是非常可观的。对于文件系统性能非常差的系统来说，只要团队成员之间开始在大规模集群之间传输数据，训练运行的 MFU 就可能暴跌。

最后，每个服务商的支持水平也参差不齐。有些厂商彬彬有礼，有些冷漠敷衍，还有一些会像 ChatGPT 一样，提供程式化的回复，把所有问题都归咎于用户。

总而言之，我们尝试过的每一个集群都仿佛拥有自己独特的气质、挑战和故障模式。几乎每个集群都需要针对其特有的一系列问题进行修复，有些问题可以忍受，有些问题则让人抓狂。不过，这也让我们深刻意识到故障转移的重要性，以及快速修复集群问题的能力是多么关键。

在过去的几个月里，我们投入了大量精力来确保可用性，例如监控工具、高效的检查点保存以及各种其他优化措施，甚至自研了可扩展数据存储的文件系统，而这仅仅是荒野炼丹的冰山一角。通过这些工具的组合，我们在一定程度上改善了 MFU 的利用率，同时最大限度地减少了因硬件问题导致的停机时间。


GPU vs TPU：一个过来人的经验

在 Reka，我们主要使用 GPU 训练模型。我之前在谷歌工作时，一直使用 TPU 来训练超大语言模型。CUDA 和 nccl 对我来说简直是外星语言。（直到最近我才知道“nccl”读作“Nickel”，还是一位曾经在 Nvidia工作的同事告诉我的呢！）

让我惊讶的是，与我在谷歌使用 TPU 的经验相比，GPU 的故障率实在太高了。老实说，我几乎不记得 TPU 在大型训练任务中出现过故障，即使是在我并不清楚是否存在专门的硬件团队负责维护的情况下。事实上，UL2 20B 模型（在谷歌）是在一次意外中运行了一个月才完成训练的，期间从未出现过故障。如果换成 GPU，估计在几天之内就会出问题。

当然，这可能与管理加速器的硬件团队的能力有关，而不是芯片本身的问题。拥有优秀的硬件支持（来自你的计算资源供应商）非常重要。很多事情都依赖于他们的能力，这也再次验证了“硬件彩票”的说法。

在 GPU 领域，多节点训练感觉更像是事后诸葛亮，而不是像 TPU Pod 那样将分布式训练作为一等公民。在 GPU 领域，感觉不同供应商以不同的方式将它们连接起来，以实现多节点训练，这导致了不同地方的做法存在很大差异。虽然我不是硬件专家，但这只是我的印象。

多集群设置的痛苦

在 Google 的基础设施上工作了多年，我习惯了 Borg、Xmanager 和 Colossus，在那里我可以从任何地方访问一切。因此，在不同的集群中设置新环境对我来说是一个全新的概念。

在当今世界，拥有多个加速器池集群似乎是不可避免的，除非你专门为一个地方的大量集群而构建。此外，GPU 的供应（或缺乏）也自然导致了这种集群采购模式，即资源被分散在不同的地点。训练大型模型还需要大量的 terabytes 数据，即使只是在集群之间移动这些数据也会造成很大的不便。同时，大规模复制数据也不是一件容易的事，而且在极大规模上也是不可行的。

显然，最理想的情况是建立某种编排层，专门将作业发送到不同的服务器。我相信，许多注重人工智能的头部公司一般都会有某种基础设施来提高人工智能研究人员的生活质量。但是，对于一家初创公司来说，在开始阶段建立这种复杂而花哨的ML训练基础设施其实是不可能的。

目前，我们已经开发了许多内部工作流程来缓解这些问题，并正在不断朝着世界一流的实验基础设施的目标努力。

（有人告诉我，对于非顶级/大型公司来说，这种拼凑式的设置是比较正常的。）

代码的荒野

众所周知，我最喜欢的代码库一直是 T5X 和 Mesh Tensorflow（命名张量 FTW），但由于以下原因，这些选项很快变得不可行：

  1. 在谷歌之外，它们的支持度不高。

  2. 它们已经被某种程度上弃用了。

  3. 对于团队中不是谷歌员工的人来说，它们不太友好。

最终，我们选择了 PyTorch，因为它相对简单、稳定、流行，并且团队中的大多数人都可以接受（除了我）。在我的最初几个月里，我一直在与 pip、git、docker 等各种工具作斗争。不过，我也不确定在外部使用谷歌代码库会是多么的稳定或用户友好（我猜可能会相当糟糕）。

说句实话，我不得不承认，外部代码库的质量明显落后于我在谷歌使用过的代码库。主要原因是谷歌内部的代码库通常是由机器学习领域的顶尖人才编写的（例如，Noam Shazeer、Barret Zoph、Adam Roberts、Hyung Won Chung 等），并且在感觉上（例如，高级的氛围）优于我尝试过的外部代码库。特别是，当我使用其他公司构建的工具时，我发现代码质量非常令人沮丧（有些公司比其他公司更糟糕）。

此外，我以前一直不知道改变模型并行性不是自动的（免费的），直到一些代码库要求我编写转换器来改变模型的并行性。这对我来说绝对是 WTF 时刻。

另一个引人注目的是，这些代码库对大型编码器-解码器训练甚至 prefixLM 训练的支持非常有限。为此，即使是 Flash Attention 也一直拒绝为 prefixLM 训练（即自定义掩码）提供支持，尽管他们的 Github issue 上有合理的需求。

我知道我应该使用 Jax。一位朋友最近因为我使用 PyTorch 而嘲笑我，但这是一家初创公司，我们决定快速行动。我很抱歉，我们下次会做得更好。我对此并不自豪。

少一些原则，多一些 YOLO

原则上，要系统地扩展模型，需要从小到大进行，即在多个阶段（1B->8B->64B->300B 等）进行实验，选择赢家并不断扩展它们。在一家初创公司，我们没有足够的计算资源来执行这些大规模的搜索以检查超参数。最终，我们不得不进行许多 YOLO 运行（幸运的是，结果很成功）。

最终，我们只用了一些小规模和短时间的消融实验就获得了强大的 21B Reka Flash 和 7B 边缘模型（以及我们即将推出的最大的核心模型）。在搜索空间巨大无比的情况下，找到一个包含少量运行的可靠配方是一项挑战，需要同时改变许多变量。为了做到这一点，必须放弃大型科技公司的系统性，更多地依赖“YOLO”，直觉和本能。

值得庆幸的是，我和团队中的许多成员在我们的机器学习职业生涯中已经积累了相当多的直觉，能够在短时间内取得成功。虽然我们在之前的工作中训练过非常好的模型，但训练基础设施、数据、新想法的纳入以及其他环境因素的差异仍然会导致结果的非平凡差异。也就是说，强大的先验知识可以帮助显著缩小搜索空间，这可能是我们能够在如此少的尝试、资源和实验的情况下训练出强大模型的最简单解释。

在荒野中探索是一次有趣的经历。不幸的是，这并不轻松。计算资源的稀缺以及不可靠的计算资源供应商使事情变得比预期困难得多，但我们很高兴通过强大的技术实力克服了这些困难。

总而言之，这只是我们如何创办公司、筹集资金、购买芯片并在不到一年的时间内从零构建一切与 Gemini Pro/GPT 3.5 匹配并超越许多其他公司故事的一小部分。
