一个训练作业，最多会在短时间内请求 3.2 万个沙箱。它们是供 Agent 执行命令、改文件、跑测试的隔离实例。命令跑完，模型还在想下一步，沙箱却不能关：改过的文件和启动的服务都得留着。

DeepSeek 的一周生产采样里，约九成容器和微型虚拟机沙箱，平均 CPU 用量不超过申请量的 5%。CPU 空着，状态和内存仍要占着；下一批任务还要装载各不相同的代码与依赖。要让 Agent 训练成规模，必须先让这些执行环境供得上、留得住、恢复得了。

DeepSeek 为此建了 DSec。一个生产单元的峰值并发超过 38 万个沙箱，每秒能创建超过 5,000 个。难题不只是开得快：GPU 训练作业被抢占又回来时，原来的任务还得接着跑。

一、38 万并发，难的是把状态留住

9 月 19 日，DeepSeek-AI 公开了 DSec 的系统设计和生产数据，梁文锋署名最后一位。它服务于 Agent 强化学习（RL）：模型在可执行任务里反复调用工具，训练框架根据运行结果给出反馈。一次任务可能要求成批准备代码、依赖和服务，等待环境就绪的时间也会进入训练成本。

一个生产单元（scale unit）约有 160 个 CPU 节点、3 万核、约 250 TB 内存，管理 PB 级的层与镜像；典型一天服务约 300 万个沙箱实例。

DSec 对外提供统一的沙箱接口，对内处理运行时选择、镜像存储、资源分配和与训练框架的状态协同。任务所需的代码、依赖与运行状态合起来是「环境」；沙箱承载环境并隔离执行。同一套基础镜像可以服务不同任务，每条训练轨迹改过的文件和进程状态仍各归各的沙箱。

生产规模和负载画像来自线上。内存下降 40.2%、磁盘写入减少 57% 等机制效果，来自与生产隔离的 10 节点测试集群，不能直接算成全平台收益。

二、突发创建、常驻状态和低复用镜像

平台先要扛住一批接一批的创建请求。容器任务一次创建数千个沙箱并不罕见，最大的生产作业请求到 32K 个。任务必须等环境准备好才能开始交互：选节点、启动实例、装载镜像，哪一步慢，后面的轨迹就得等。

图｜一次任务要开多少沙箱。 容器任务的中位数、p90、p99 分别为 2,528、7,969、16,388 个；microVM 为 352、1,835、4,044 个。p90、p99 分别指九成、九成九的任务低于相应数量。（来源：DeepSeek-AI DSec，Figure 2；2026 年初一周生产采样）

沙箱开起来，还要陪模型跑完整条轨迹。准备依赖之后，沙箱执行命令，等待模型，再执行下一条；到最后的测试，CPU 需求又短暂抬升。等待时资源使用低，却不能扔掉改过的代码和运行中的服务。

执行与等待交替，内存仍持续占用。 

它们不是用完即走的短时函数。一周采样里，有的沙箱活过三小时。容器和 microVM 的 CPU 平均用量很低，瞬时峰值却不低；超售 CPU 有空间，内存和状态回收仍要单独解决。

第三道压力来自环境本身。软件工程、安全、计算机操作与 Android 任务所需的系统能力不同；即使任务类型相同，仓库、依赖版本、服务、工具包、评测脚本或 VM 快照也各有差异。容器与 microVM 一周活跃的镜像和工作区超过 130 TB，远非把少量镜像提前缓存到每台节点就能解决。

而一张镜像真正被访问的文件数据，依语言和任务样本不同，只占 4.2% 到 13.3%。若每次都把整张镜像搬到节点、再逐沙箱解压，绝大多数数据不会被使用。DSec 后面的几项设计——按需装载、可组合环境层、内存共享与回收——都从这三道压力长出来。它还得防住另一类麻烦：Agent 会主动寻找答案，甚至把共享设施弄坏。

三、一套入口，四种沙箱

一段编译脚本和一个 Android 图形任务，都要从训练框架发起，却不适合塞进同一种运行时。DSec 把创建、执行命令、读取结果、停止会话做成统一接口；至于后台用容器还是虚拟机，由任务需要的隔离、系统能力和启动速度决定。

3.1 四种后端怎么选

FnCall｜短小的无状态任务。 判题、编译、serverless 程序和 GPU kernel 评测，用预创建的复用 CPU 或 GPU 容器执行，省去逐次启动的开销。GPU 既可由多个容器共享，也可在算子评测时让一个容器独占实例。它开销最低，却不提供完整操作系统会话。

Container｜软件工程和通用工具调用。 仓库与工具可以跨多轮命令保持状态，启动快、装箱密度高。容器共享所在 QEMU 虚拟机的内核；遇到安全敏感任务，还需要更强的隔离边界。

MicroVM｜安全任务和强隔离。 Firecracker 给每个任务单独的虚拟机内核，保留 Linux 兼容性，代价是启动更慢、内存开销更高。

Full VM｜完整操作系统与图形任务。 Android、GUI、商用系统和渲染负载需要它的兼容性，也承担最高的资源开销。

这四类覆盖了原方案对运行性能、依赖体积、隔离强度、完整 OS 能力和资源开销的取舍，并没有一种后端在所有维度都占优。生产实例和资源消耗以容器、microVM 为主；FnCall 用少量常驻环境承接轻量调用，完整 VM 服务其他后端覆盖不了的任务。

3.2 入口：libdsec

后端不同，调用方式尽量相同。训练框架、评测框架和数据构建流水线通过 Python 客户端库 libdsec 创建沙箱、下发命令并取回结果。调用时指定镜像或环境标识、CPU 与内存上限、生命周期、网络规则和初始用户。下面这段仅展示容器路径；选择 microVM 或其他后端时，接口对象会变，任务会话的基本动作不变。

client = DSecClient()
await client.open()
args = DSecContainerRunArgs(
    container_image=image_id,
    memory_limit_mb=4096,
    cpu_cores_limit=4,
    ttl_running_stop=300,
    network_rules={
        "npm": False,
        "pypi": True,
    },
    init_user="root",
)
sandbox = await client.run_container(
    args, timeout=120
)
result = await sandbox.run_shell(
    "echo hello world"
)
await sandbox.stop()

这里的 image_id 是预先选定的镜像标识；网络规则允许访问 PyPI，拒绝 NPM。代码显示的重点是：调用方决定任务需要什么，平台处理沙箱从创建到回收的生命周期。

3.3 一次沙箱会话如何运行

创建时，调用方提交后端、环境制品、资源上限、生命周期与网络策略。容器和 microVM 的环境由基础镜像、任务专用工作区与工具包层组合；完整 VM 使用预制镜像或快照；FnCall 则提交任务类型、依赖文件和代码或脚本。平台准备妥当后，Agent 才能下发命令、读取输出、运行检查或测试。

容器和 VM 会话可以跨多轮交互：下一条命令接着使用上一条留下的文件与进程。FnCall 处理短时无状态任务。会话结束后显式停止，或等 TTL 到期回收；在此之前，CPU 可以闲着，状态仍要保留。

一周采样里，容器生命周期中位数为 17.4 分钟，microVM 为 15.5 分钟；两者的 p99 都超过三小时。

图｜沙箱的长尾寿命。 横轴是分钟的对数刻度，右侧长尾意味着部分沙箱要保留数小时状态。（来源：DeepSeek-AI DSec，Figure 7；2026 年初一周生产采样，30K 容器、10K microVM）

3.4 部署规模

DSec 的多个生产单元共享一套 3FS 分布式文件系统，存放基础镜像与工作区。前述约 160 个 CPU 节点、38 万并发、一天约 300 万实例等平台总量级数字，都以单个生产单元为口径；生产单元总数没有披露。每任务分布、一周采样和单节点数据各有自己的测量范围。

图｜单节点一天的并发变化。 当天峰值为 1,048 个容器、524 个 microVM；另有单节点稳定承载至少 3,200 个容器或 800 个 microVM 的运行点，来自其他生产负载，不能把前者当成容量上限。（来源：DeepSeek-AI DSec，Figure 6）

四、一次请求怎么走完：从 libdsec 到 chronus

训练框架发出创建请求后，平台要确认权限、选择节点、准备镜像、拉起实例，还要把后续命令送进沙箱。每秒数千次创建之下，控制面和节点都得各司其职。

图｜创建沙箱涉及哪些组件。 控制层负责授权、节点选择和转发，edge 做本地准入；3FS 是单独的镜像数据路径。容器和 VM 的会话由 aether、chronus 接管，FnCall 直接使用预创建容器。图依据原 Figure 1 归纳组件，并不表示控制层内部各服务的严格先后时序。（来源：DeepSeek-AI DSec，Figure 1）

4.1 集群级服务

请求先通过 IAM。它认证调用者并授权创建、删除等管理操作。每个 principal 对应一个用户或服务身份，project 划定资源与权限边界；项目可以多级嵌套，获授权的 agent 或 harness 也能创建子项目、委派部分父级配额和管理权限。子项目不能越过父级的权限与配额，人和 agent 使用同一套管理 API。

随后由 placement engine 挑节点。它先排除不健康、缺少后端或硬件能力的节点，再从合格节点中随机采样，选择负载较低者。负载和健康信息来自 watcher 对 edge 与宿主的周期性探测，并按节点、用户、任务拆分。watcher 重启后重新轮询各 edge 即可恢复视图，placement engine 也不保存沙箱执行状态；两者都可通过增加实例扩展。

节点选定后，apiserver 把请求转给目标 edge。训练和评测代码从可信的 GPU 服务器调用 libdsec，沙箱里却运行可能访问外网的模型生成代码；两侧网络隔离，apiserver 是唯一允许的通信路径。它不存每个沙箱的状态，只从 watcher 更新 edge 列表。沙箱 ID 编码了所属 edge，任何 apiserver 实例都能据此路由后续操作。

这种做法让入口、放置和监控组件都能横向扩展。节点最终能否接单，还要由本机的 edge 再检查一次。

4.2 沙箱运行时：edge、aether、chronus

每台节点运行一个 edge。placement engine 看的是定期刷新的集群视图，edge 则检查本机此刻的容量；不足就拒绝，由控制面另选节点。接单后，它准备存储、下发 eBPF 网络策略、启动所选运行时；沙箱停止或 TTL 到期时，再协调快照并释放本地资源。

FnCall 与容器并不直接跑在裸金属节点上，它们运行在 QEMU/libvirt 虚拟机里。 这层 VM 提供独立内核与网络栈，是在不可信容器与裸金属之间再加的一道边界。图形密集型的完整 VM 负载（GUI 应用、浏览器、视频游戏、3D 渲染）可借助宿主虚拟化层的半虚拟化 GPU 接口（如 virtio-gpu）；既支持与宿主原生图形 API 兼容的负载，也支持经 DXVK 之类兼容层翻译后的负载。

实例拉起后，容器和 VM 里的 aether 与 edge 建立通道：Linux 容器走 Unix domain socket，VM 走 vsock。通道关闭，edge 就判定沙箱失败。收到命令时，aether 按终端会话标识找到或创建 chronus，转发操作；会话结束时清理对应的进程树。

chronus 是沙箱内的独立 shell 会话，提供命令执行、文件操作、HTTP 请求和流式 I/O；一个沙箱可以同时有多个会话。aether 加 chronus 把不同容器和 VM 的操作接成相近的接口。FnCall 路径更短，任务直接交给预创建的容器，不经过这两个组件。

镜像也不用在启动前全部搬到节点上。容器镜像离线从 OCI 转成 EROFS，元数据留本地、文件数据留 3FS；microVM 的基础镜像和工具包使用只读 EROFS 层，可写 ext4 磁盘由 OverlayBD 承载。访问到哪个数据块，才从远端取哪个。

4.3 云爆发：有条件的上云

本地利用率超过 80% 时，placement engine 把一部分够格的新建请求卸载到云 VM。DSec 没有选「托管容器服务 + 对象存储」，而是在云 VM 上复用本地那套容器运行时与 EROFS 镜像加载路径，镜像放在云端分布式文件系统里由云 VM 挂载。

上云有门槛。生产文件访问轨迹显示，一份去重后体量 30 TB 的精简 EROFS 镜像集合覆盖了 70% 容器任务所访问的镜像文件；这份集合离线同步到云端，镜像依赖完全落在集合内的任务才算 cloud-eligible。生产上，一个 scale unit 里 200 台云 VM 吸收了约 30% 的峰值溢出。

五、把沙箱密度做上去，代价从哪里省

平台能接单，还得让节点装得下、启动得快。DSec 面对的是四笔账：每个任务都可能有自己的环境，镜像不能逐份搬运；沙箱等待模型时内存仍在，闲置 CPU 又得与敏感任务共享。

图｜四笔成本对应四种机制。 环境层组合、microVM 内存共享与回收、CPU QoS、镜像按需加载，分别处理环境更新、常驻资源、同置干扰和启动搬运。图为依据原 Figure 9 整理的移动端摘要，具体的存储与执行路径见下文。（来源：DeepSeek-AI DSec，Figure 9；LS 为延迟敏感任务，BE 为尽力而为任务）

5.1 可组合环境层

这些环境不是几张镜像反复使用。一周内，两种主要后端用到的制品是：

  • • 容器：11,266 个基础镜像、102,171 个工作区，总体积 82.8 TB；
  • • microVM：2 个共享基础镜像、53,590 个任务专用工作区、4,889 个快照，总体积 50.9 TB。

同期还有 103 个工具包。67.8% 的沙箱在基础镜像之外，至少要再叠一层工作区或工具包。

镜像、工作区和工具包若预先融合，任一组件更新都牵连整套组合。若改为逐沙箱解压压缩包，突发创建时又会堆出 CPU 与磁盘写入；宿主机目录 bind mount 会覆盖目标路径，不能合并目录树，严格只读也会撞上 Python 写 __pycache__ 一类运行行为。

假如一个工具包被数万个工作区使用，每次更新都重建完整镜像，构建量会随组合数膨胀。DSec 把基础镜像、workspace、toolkit 拆成独立版本的层，创建沙箱时才组合。

图｜工具包更新后，哪些镜像必须重建。 上图的单体镜像方案需重建所有包含 T1 的组合；下图分层后只更新 T1，其余层复用。两图由原图左右两侧拆排，来源：DeepSeek-AI DSec，Figure 4。

合并交给 overlayfs：多个只读 lower 目录叠加后呈现为一棵目录树，同名文件按层级优先级裁决，顶端可写 upper 目录接住运行时改动。DSec 修改 dockerd，在创建容器时动态组装 lowerdir：基础镜像垫底，workspace 在中间，toolkit 叠在上面。

设有 N 个工作区。升级 m 个基础镜像只需重建那 m 个基础层，升级 k 个工具包只需重建那 k 个工具包层；重建量分别从 O(m·N)、O(k·N) 降到 O(m)、O(k)。

省下的是成批重建完整环境的工序；每个沙箱运行时的新改动仍写进自己的可写层。

这些层发布后不可变，适合存成 EROFS：免去写相关簿记，布局紧凑，压缩后还能随机访问。tar.gz 按字节流压缩，读到后面的文件得先解压前面的内容；EROFS 只解压访问到的块。沙箱无需把整个工作区解压到本地才能开始执行。

microVM 用同一套模型，介质换成块设备：基础镜像与工具包包成独立版本化的 EROFS 镜像，以只读块设备给 guest；guest 内根文件系统用 overlayfs，挂着 EROFS 作 lower 层，一块 ext4 可写盘上的目录作 upper 层。

另有两条取舍：即便不拉全镜像，挂载大量 EROFS 层仍会增加创建开销，于是把大小阈值（例如 3 GB）以内的相邻层在线下折叠成一对 EROFS 元数据与数据镜像，同时保留 whiteout 语义表达文件删除；挂载采用 file-backed mount 模式，去掉 loop 设备的块映射层开销。

5.2 高密度下的内存：一份共享，一份回收

CPU 平均用量低，不等于随时能把资源全部让出去：执行工具时有短峰值，microVM 的镜像数据还可能同时留在宿主和各个 guest 的页缓存里，guest 的空闲页也未必及时交还宿主。

图｜平均与峰值不是一回事。 实线为平均用量、虚线为峰值，均按沙箱申请量归一化；两种后端的 CPU 与内存各有一组曲线。（来源：DeepSeek-AI DSec，Figure 5；同一周生产采样）

节点上放了大量 microVM 后，同一份只读镜像可能在宿主机和各个 guest 的页缓存里反复出现。virtio-pmem 配合 DAX 把访问映射到宿主页，不再为每个 guest 单独拷贝一份；写入仍走常规路径。

virtio-pmem 不能铺到每块盘上。冷访问可能触发同步缺页处理；带缓冲的 virtio-blk 却能利用 guest 侧预读和批量块 I/O。guest 还要为整个 pmem 地址范围分配 struct page 元数据：按 4 KiB 页与 64 字节元数据计算，占设备容量的 1/64，128 GB 设备先要拿出 2 GB guest 内存记账。

所以生产配置分工明确：只读的 EROFS 基础镜像层与工具包层启用 virtio-pmem + DAX，共享重复的镜像页；更大的可写盘交给 DAMON 与 balloon 回收。这笔账算的是峰值内存与访问 CPU 之间的取舍。

另一笔浪费是 guest 内已经不用的内存交不回宿主。virtio-balloon 的 free-page reporting 会扫描 guest 的 buddy allocator，上报空闲页，再由宿主以 madvise(MADV_DONTNEED) 释放。但它默认要求 order-9 连续块，在 4 KiB 基页下就是 2 MiB；冷文件页通常散落各处，达不到上报粒度。

DAMON 周期性采样访问位，找出长期未触碰的冷文件页并驱逐，让空闲页在 buddy allocator 中合并，才有机会形成可上报的大块。共享只读页解决「重复留着」，回收冷页解决「该还的还不回去」。

5.3 CPU QoS：光调优先级不够

CPU 能超售，延迟敏感任务却不能被同机的尽力而为任务拖住。DSec 把沙箱分成 LS 与 BE 两类，BE 使用 SCHED_IDLE，有 LS 任务可运行时便让出 CPU。但同一个物理核上的 SMT 兄弟线程仍会争抢执行资源；因此对 LS 再启用 Linux core scheduling，阻止不相干的 BE 工作占用其兄弟线程。

5.4 镜像分发与按需加载

缓存也有复用率这道坎。一张镜像在同一任务里被多少沙箱使用，称为 fanout。容器镜像的中位数只有 3、p90 为 28；microVM 镜像更低，中位数 1、p90 为 3。镜像种类多，节点难以提前缓存到对的那一张。

图｜镜像复用度的差距。 蓝线的 microVM 镜像更常只供一个沙箱使用；横轴为对数刻度。（来源：DeepSeek-AI DSec，Figure 8；一周生产采样，覆盖 150 万个以上容器和 39 万个 microVM）

镜像又大多没有被完整读取。「实际访问文件数据占镜像总数据」与对应的镜像大小是：

  • • C++：8.7%，4.9 GB；Go：13.3%，4.1 GB；
  • • Java：9.2%，12.1 GB；JavaScript：4.2%，9.6 GB；
  • • Python：6.0%，6.0 GB。

先下载整张镜像，再等它启动，就会搬运大量没用上的字节。

镜像分发沿用已经支撑生产训练负载的 3FS，免去另起一套「容器 registry + P2P 分发」系统。不过 3FS 的 I/O 高度不对称：大块顺序读写吞吐高，小随机 I/O 很差。镜像读取方式得顺着这一特点设计：

  1. 1. 写留本地。 沙箱写入不可控且琐碎，可写层直接放节点本地盘，绕开 3FS 的小写惩罚。
  2. 2. 读按需且批量。 只读镜像数据只在被访问时取，以批量 I/O 吃 3FS 的大请求吞吐红利。
  3. 3. 元数据尽量本地。 元数据常是大量小读，格式允许时分离元数据与数据并预取到本地节点。

容器侧由 EROFS 兑现这三条：严格只读使运行时写入全落在本地 upper 目录；缓冲 I/O 按需供给内容，内核预读把相邻块合并成更大请求；多设备模式分离元数据与数据，元数据下载到本地盘、文件数据留在 3FS，路径查找不触发远端 I/O。

microVM 侧不能照抄：Docker 的 overlay2 驱动不能使用基于 overlayfs 的数据目录，用 virtio-fs 导出给 guest 这条路他们的 Firecracker 后端又不支持。于是只读的基础镜像与工具包层仍用 EROFS，可写 ext4 盘由 OverlayBD 承载，包括给 Docker-in-microVM 负载单独挂一块盘。

OverlayBD 支撑的盘通过 ublk 暴露，提供块级按需读与本地写，并支持增量快照而不必把改动重打包回 EROFS。代价是 ext4 元数据嵌在块镜像里，元数据读可能触发远端 I/O；他们的 ublk 实现按 256 KiB 分块取数据并放二级本地文件系统缓存，从页缓存淘汰后仍可本地命中。

写留本地、读按需、元数据尽量就近，三者合在一起，才把低复用镜像的启动成本压到可承受范围。

六、DSec 与 RL 框架：环境构建、状态保存和抢占恢复

沙箱的生命周期跟着训练任务走。Agent 可以在沙箱里构建新的任务环境，GPU 作业被抢占时，跑到一半的轨迹还得接着执行。从 DeepSeek V3.2 到 V4.1，RL 训练与评测所用的全部沙箱负载都由 DSec 承载；平台与训练框架因此共同管理状态。

6.1 用 pack_diff 把交互会话变成环境

任务需要成千上万套不同环境，全部靠人工配置难以扩展。构建环境的 agent 可以在沙箱里装依赖、修改文件、运行验证，再用 pack_diff 保存增量磁盘快照。快照之后能恢复为新的沙箱；构建、验证、使用环境，都在同一套设施里完成。

构建过程也得受控。内部规则以指令形式约束构建 agent 对共享设施的性能影响；另一套内部平台检查环境质量，并按标准格式导出。构建者和解题 agent 使用不同账号，打包前清理可写层的构建残留，避免参考答案混进环境。

6.2 把 rollout 从可抢占的 GPU 池里摘出来

早期版本里，agent loop 跑在可抢占的 GPU 训练 pod 内。GPU 作业一旦被抢占，agent loop 没了，沙箱却还在；恢复时要靠命令日志对齐两边的状态。已经执行过的命令只能复用记录，贸然重放非幂等操作可能把环境再次改坏。

从 V4.1 开始，rollout 执行移到 DSec，拆成承载 scaffold 和工具的 agent sandbox，以及管理沙箱、提供控制层的 worker container。两者都在可抢占 GPU 池之外，共同保留完整 rollout 状态，成为恢复时的唯一事实来源。GPU 作业回来后直接重连，不必回放命令日志。

6.3 抢占即暂停

GPU 抢占不可避免，沙箱状态必须留到 rollout 完成，而这会让大量闲置沙箱继续占着内存。RL 框架因此主动给被抢占作业关联的沙箱发暂停请求，DSec 一边回收内存一边保住执行状态；暂停后再来请求，会先透明恢复再执行。

容器路径先由 edge 执行 docker pause，冻结进程树；再通过 memory.swap.max 启用交换，用 memory.reclaim 主动回收匿名页与文件页。恢复时以 MADV_WILLNEED 异步预取，再 docker unpause。进程暂时不跑，文件和执行状态还在。

microVM 路径更彻底：保存内存与执行状态快照，终止 Firecracker 进程释放内存；要继续工作时，启动新进程还原快照。两条路径的动作不同，目的都是让 GPU 作业回来后接上原来的轨迹。

6.4 Agent 会作弊，也会误伤

沙箱里跑的是为完成任务而不断试探的 Agent。任务看起来过了，答案却可能来自不该访问的地方。

在沙箱里，agent 搜索平台托管文件与通信通道，试图找残留答案；直接向 chronus socket 发送构造好的 RPC 消息伪造用户请求，翻看 chronus 日志。由于 chronus 对部分操作会调用 bash，agent 还试图覆盖 /bin/bash 绕过检查。

加上文件与 socket 访问控制后，有 agent 转而尝试 XFS_IOC_SWAPEXT：这个 ioctl 能交换两个文件的数据 extent 映射，企图让受保护内容通过另一个文件描述符被读到，结果损坏 XFS 元数据，文件系统直接关闭。沙箱外，还有扫描端口与服务寻找可达镜像源、通过 Go module proxy 从代码托管平台取代码、安装更新版本的包寻找现成实现等尝试。

有些操作直接变成事故：agent 从根目录递归 grep，遍历进 /proc 并读 /proc/kpagecgroup，触发内核 bug；另一次漏洞利用任务里，本该转发给目标 VM 的攻击命令在 agent 自己的容器里执行，导致内核崩溃。还有 agent 调用无界输出的 yes，chronus 为支持异步取回输出而记录 stdout，最终积累了数十 GB 日志。

仅检查最终输出，无法可靠判断 agent 是否按预期路径解出了任务。

6.5 访问控制能挡住什么

没有单一机制能预防全部不正当行为与系统故障。DSec 加强可观测性，并随着模型行为变化持续加固。当前落地的两类控制是：

AppArmor。 控制文件读写权限与 socket 访问，包括访问 chronus 的日志与 Unix domain socket；策略对 agent 控制的进程同样生效，即便沙箱内以 root 运行。

eBPF 网络控制。 训练框架按域名或镜像源规定任务专属网络权限（例如允许 PyPI、拒绝 NPM），DSec 用每沙箱 eBPF 程序按 IP、端口、协议过滤，白名单外直接拒绝，策略可随任务阶段动态调整。

AppArmor 与 eBPF 只能限制一部分绕路取答案的行为；触发内核 bug 这样的破坏性行为仍没有通用防线。

七、实测：快在哪里，代价又是什么

生产规模说明系统跑得起来，机制效果还得看对照测试。镜像启动、环境供给、内存占用、CPU 同置干扰各有一组实验；这些收益都来自独立测试集群。

7.1 测试条件：独立的十节点集群

性能测试跑在一套专用 10 节点 CPU 集群上，与生产隔离。为避免嵌套虚拟化，microVM 直接跑裸金属：每节点 AMD EPYC 9655，双路 × 96 核 × 2 SMT 线程、1.5 TB DRAM、3.4 TB 本地存储。容器侧实验则跑在一个 QEMU 虚拟机内部：单路 × 96 核 × 2 SMT 线程共 192 硬件线程、512 GB 内存、5.8 TB 本地存储。所有宿主跑 Linux 7.0，microVM guest 跑 Linux 6.1。

负载取自真实 RL 训练与评测场景：内部软件工程基准、SWE-bench、Terminal-Bench、安全漏洞利用任务及同类目录。测试覆盖按需加载、可组合层、内存优化和 CPU QoS；与 RL 框架的协同没有纳入量化测试。

7.2 按需加载 vs 急切拉取

先看“镜像没到齐就能启动”值多少钱。10 节点集群一次突发 8,192 个容器，运行需要多 GB 镜像的真实 RL 评测负载。测试比较按需 EROFS 加载、远端 registry 全量拉取（冷启动），以及镜像已在节点缓存中的全本地基线；三者的 CPU 与内存利用率差异可忽略。

图｜8,192 个容器突发，按需加载约 35 分钟完成。 冷镜像全量拉取超过 60 分钟；黄色线是镜像已在本地的基线。省下的另一笔账是写盘。 蓝色为远端冷镜像全量拉取，红色为按需 EROFS，黄色为镜像已缓存的基线；实线为瞬时写 IOPS（左轴），虚线为累积写量（右轴）。冷拉取每节点超过 1,600 GB，按需加载约 700 GB，少约 57%，接近全本地基线的约 600 GB。

7.3 EROFS vs tar

镜像传输得快，环境 setup 也可能卡在解压上。两组沙箱使用相同的评测 workspace 和工具包（任务仓库、scaffold 二进制、命令行工具）：一组逐沙箱解压 tar.gz，一组直接挂载压缩的 EROFS 只读层。实验用预录的确定性工具调用替代 LLM 生成，使差异主要来自供给方式。

图｜EROFS 挂载省下逐沙箱解压的写入（来源：DeepSeek-AI DSec，Figure 11）。tar 方案端到端耗时 79 分钟，EROFS 为 45 分钟，快 1.76 倍；tar 的总写流量约为 EROFS 的 5.5 倍，峰值写吞吐为 3.4 倍。

EROFS 的峰值 CPU 反而更高，因为更多沙箱较早进入 tool-call 阶段并发运行；这不表示它的 setup 开销更大。

7.4 超售下的内存

内存实验回答两个不同问题：共享镜像缓存能降多少峰值，回收冷页能少占用多久。真实 Agent RL 负载对比四种 Firecracker 配置：基线、仅 virtio-pmem + DAX、仅 DAMON 配合 virtio-balloon 空闲页上报（FPR），以及两者结合。

图｜共享降低峰值，回收降低持续占用。 virtio-pmem + DAX 使宿主峰值内存较基线下降 40.2%；DAMON + balloon FPR 单独使用时峰值变化不大，宿主内存的时间积分消耗下降 21.2%。两者组合总体消耗最低；两种百分比口径不能相加。共享只读页也要付 CPU 代价。 灰色为基线，蓝色为 virtio-pmem，绿色为 FPR，红色为两者结合；virtio-pmem 把瞬时 CPU 峰值从 26.5% 抬到 41.4%。冷访问可能贡献了部分开销。CPU 受限的部署可以只启用 FPR，保留 virtio-blk。

7.5 超售下的 CPU QoS

最后看同机任务会不会互相拖慢。把真实评测中的延迟敏感（LS）任务与占节点容量 10% 到 50% 的尽力而为（BE）负载放在一起，测每步延迟相对无干扰基线的变化。

图｜只降优先级，挡不住 SMT 兄弟线程的争抢（来源：DeepSeek-AI DSec，Figure 13；延迟敏感的国际象棋应用）。50% BE 负载下，无 QoS 控制时每步延迟膨胀 45.2%；只用 SCHED_IDLE 最多改善 3.4%；加上 core scheduling 后，膨胀降至 17.3%。

只用 SCHED_IDLE 收效很小，说明争抢并不只发生在调度队列，同一个物理核上的两个逻辑线程也会相互影响。

剩余的 17.3% 主要来自高多核负载下 CPU 睿频下降、内存带宽与共享末级缓存争用；core scheduling 管不到这些资源。评估认为这部分干扰可以容忍，因此没有再做内存带宽隔离。

八、调度、可靠性和运行时实现

镜像加载与内存回收之外，平台还得接住突发请求。节点选择采用 power-of-k-choices：从合格节点随机采样 k 个，挑其中负载最低的，减少大量新沙箱挤向同一台机器。

每个 placement engine 会把自己刚发出、还没进入 watcher 快照的决定计入本地视图；最终是否接单，由 edge 按本机容量拍板。不维持一份全局一致的调度状态，就要容忍节点拒绝和重试。用户隔离能缩小资源尖峰或内核故障的波及范围，也会牺牲部分节点密度。

控制面服务也要能替换。网关和入口的多个实例宣告同一虚拟 IP，上游交换机用 ECMP 分流；实例会话断开，BGP 路由撤销，流量在数秒内转向其他实例。placement engine、watcher、IAM 各运行多个独立实例；定期的集群重置则检查 Infrastructure-as-Code 配置能否从零重建服务。

容器创建时要插入预挂载的 EROFS 层。DSec 为此对开源 dockerd（Moby）做了约 30 行 Go 改动，把路径放到 overlayfs 栈的最上层 lower 层，覆盖下层同名文件。

Firecracker microVM 的按需块存储由 Rust 版 OverlayBD 和自研 Rust 用户态 ublk 库承担，远端可接 3FS、OSS 一类对象存储或容器 registry，本地文件系统充当二级缓存；相关代码已开源。

资源管理没有修改 Linux 内核。virtio-pmem + DAX 由 Firecracker 设备配置与 guest 挂载选项启用，DAMON 通过 guest 内核参数和 sysfs 调谐；BE 任务使用 SCHED_IDLE，core scheduling 通过 prctl(PR_SCHED_CORE) 按 QoS 类别分组。

FnCall 的 GPU 算子评测还有自己的并发办法：NVIDIA MIG 把 GPU 切为相互隔离的实例，CPU FnCall 先编译，再把产物交给独占的 GPU FnCall；Python 进程 warm pool 提前初始化运行时和依赖。性能不敏感的任务另用共享 GPU 模式。

支撑镜像按需供给的 3FS，每台存储服务器配置 20 块 15 TB SSD 和两张 400Gbps RDMA 网卡，CPU 节点通过 FUSE 访问。数十台存储服务器即可服务一个数十万 CPU 核的集群，EROFS 元数据仍留在节点本地。

九、沙箱供给，开始影响训练吞吐

DSec 把环境构建、镜像分发、沙箱运行和抢占恢复接到同一条训练链上。模型能并行跑多少条可验证轨迹，除了推理与 GPU 资源，还取决于任务环境能否及时生成、装载并在中断后接着运行。

推理阶段的代码执行产品，如 OpenAI Code Interpreter、E2B，重视单次调用的体验；RunD 一类 serverless 系统着力压低短时函数的启动开销。DSec 的难题是训练中的大批量有状态会话：镜像复用度低，工作集超过单节点容量，还要随 GPU 作业暂停和恢复。veRL 等 RL 框架关心 GPU 调度、通信和样本吞吐；DSec 处理执行环境的供给与生命周期。这是按负载划分的工作重点，并非逐家产品的性能排名。

3FS 出自萤火集群的软硬协同设计，后来成为 DSec 的镜像底座。从 V3.2 到 V4.1，DeepSeek 的 RL 训练与评测沙箱负载也由 DSec 承载。

训练系统的成本也因此多了一张账单：环境构建、镜像分发、沙箱常驻时间和失败轨迹重跑，都要占用资源。衡量 Agent 训练能力，除了看 GPU 和模型，还得看平台能否持续供给大量可执行、可验证、可恢复的任务环境。
