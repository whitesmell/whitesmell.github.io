一次意外的源码泄露，让我们拿到了 AI Coding 领域最完整的 Agent Harness 样本。

你大概听说了：Claude Code 的源码因为 npm 包里的 source map 文件被意外带出，完整暴露了。

57MB 的 .map 文件，4756 个源文件，约 1900 个 Claude Code 自身的 TypeScript 模块，51 万行代码。不是模型权重，不是后端，是客户端——那个你每天在终端里敲 claude 就启动的 CLI 程序。

热闹过了，八卦也扒完了。但这件事真正有价值的地方，大多数文章都没写到：

我们第一次拿到了一个 shipped product 级别的 Agent Harness 完整实现。

这里的关键词是 Harness。模型是引擎，Harness 是底盘。引擎决定了车能跑多快，但底盘决定了它能不能安全地跑起来、拐弯、刹车、不翻车。

今天这篇文章不聊八卦。我想做一件事：用 Claude Code 这份真实的工程样本，把"一个自主 Agent 到底需要什么"这个问题拆透。

先搞清楚一件事：什么是自主 Agent？

在拆 Claude Code 之前，先把概念理顺。

过去两年，"Agent"这个词被用烂了。套个 function calling 就叫 Agent，写个 prompt chain 就叫 Agent。但真正的自主 Agent 有一个明确的技术范式，学术界叫它 ReAct（Reasoning + Acting），工程界更常说的是 Agentic Loop。

核心思想很简单，就四步循环：

感知（Observe）→ 思考（Reason）→ 行动（Act）→ 观察结果（Observe）→ 继续思考……

你可以把它理解成一个永不停歇的 OODA 循环（Observe-Orient-Decide-Act）。一个真正的 Agent 不是"你问一句我答一句"的聊天机器人，它是一个有目标、能行动、会根据环境反馈调整策略的自治系统。

但从论文里的四步循环到一个能用的产品，中间差了十万八千里。

因为这四步里的每一步都藏着一堆工程问题：

  • • 感知：Agent 能"看到"什么？文件系统？终端输出？Git 历史？它的感知边界在哪？
  • • 思考：上下文窗口就这么大，历史越来越长怎么办？哪些信息该记住，哪些该丢掉？
  • • 行动：模型说要执行 rm -rf /，你让不让它执行？权限怎么控制？
  • • 观察：工具执行的结果怎么喂回模型？结果太长了截不截断？截断了会不会丢关键信息？

Claude Code 的源码之所以有价值，就在于它用 51 万行代码，给出了这四个问题的工程实现。

不是论文里的理论框架，不是 demo 里的玩具代码，而是每天服务数百万开发者的、经过真实场景打磨的 shipped code。

下面一层一层拆。

第一层：Agentic Loop——Agent 的心脏

Claude Code 的心脏是一个叫 queryLoop 的函数，定义在 src/query.ts 里。

大多数人对 AI 编程工具的心智模型是：

用户输入 → 调 API → 返回结果 → 显示

真实的流程是这样的：

用户输入
  → 组装上下文（系统提示词 + 历史对话 + 项目记忆 + 附件）
    → 流式调用模型 API
      → 模型输出文本？→ 显示给用户
      → 模型输出 tool_use？→ 进入工具执行管线
        → 执行工具，拿到结果
          → 结果回注到对话历史
            → 检查：任务完成了吗？token 用完了吗？
              → 没完成 → 回到"组装上下文"，开始下一轮
              → 完成了 → 退出循环

一个用户的 prompt，可能触发十几轮甚至几十轮这样的循环。 每一轮，模型都在"思考→行动→观察→再思考"。这就是 Agentic Loop 的工程落地。

queryLoop 在技术上是一个异步生成器（async generator），向 UI 层持续 yield StreamEvent 对象。这个设计很关键——它意味着 UI 可以实时渲染模型的思考过程和工具调用状态，而不需要等整个循环跑完。你在终端里看到的那些 spinner、进度条、工具调用提示，全靠这个异步生成器在驱动。

但真正让 queryLoop 从"demo 级循环"升级为"production 级引擎"的，是它身上挂着的那些"附加系统"：

  • • StreamingToolExecutor：在模型还在流式输出的时候就开始准备工具执行环境，JSON 参数一解析完立刻启动执行——不等模型说完
  • • tokenBudget：追踪每轮的 token 消耗，防止循环失控
  • • handleStopHooks：在特定条件下强制终止循环
  • • autoCompact / reactiveCompact：上下文快满了时自动压缩历史

这些东西和 queryLoop 组合在一起，构成了一个完整的执行运行时。

我的洞察： 很多团队在做 Agent 时，花 90% 的精力在"让模型调用工具"上。但 Claude Code 的源码告诉你，"调用工具"只是 Agentic Loop 的一小部分。真正的工程量在循环控制——什么时候继续、什么时候压缩、什么时候回退、什么时候停。 这些"元控制"逻辑的代码量，远超工具调用本身。

第二层：上下文工程——Agent 的记忆系统

如果说 Agentic Loop 是心脏，上下文管理就是大脑的短期记忆。

200K token 听起来巨大，但在真实的编程 Agent 场景里，消耗速度远超你的想象。做个简单计算：

  • • 系统提示词：~3K token
  • • 一次 BashTool 调用（命令 + 输出）：~500-5K token
  • • 一次 FileReadTool（读一个文件）：~2K-10K token
  • • 十轮工具调用的累积历史：轻松 50K-100K token

也就是说，一个稍微复杂的任务，跑个二十轮，上下文就可能接近 200K 的上限了。

Claude Code 对此的解法是一套四级压缩策略，设计思路很像操作系统的内存管理——从轻量回收到激进释放，逐级递进：

但压缩只是一半。另一半是注入——确保关键信息不会因为压缩而丢失。

源码里的 getAttachmentMessages（src/utils/attachments.ts）做了一件很聪明的事：它把项目级上下文（MEMORY.md 里的项目规则、用户偏好、当前任务状态）在每一轮都重新"冒泡"注入到下一条消息中。

压缩历史是在丢弃"过程"，冒泡注入是在保留"结论"。

这意味着即使前面二十轮的对话全被压缩成一段摘要，模型依然知道"这个项目用 pnpm 不用 npm""用户偏好 TypeScript 而非 JavaScript"这些关键规则。

还有一个容易被忽略的细节：消息在发给 API 之前，会经过 normalizeMessagesForAPI（src/utils/messages.ts）做标准化处理。包括把连续的同角色消息合并（API 要求严格交替）、把系统指令提升到专用字段、确保每个 tool_use 都有对应的 tool_result。你在终端里看到的"对话"，和 API 实际收到的"请求"，是两个东西。

我的洞察： 行业里讨论 Agent 的上下文管理，经常陷入"给模型更大的窗口"这种思路。Claude Code 的做法揭示了一个更深的道理——上下文管理的核心不是"装得下"，而是"装什么"。 在有限的窗口里，什么信息该保留、什么该丢弃、什么该在每轮重新注入，这才是真正的工程难题。更大的窗口只是延缓了这个问题，不能消除它。

第三层：工具执行管线——Agent 的手脚

模型能"想"，但不能"动"。让它动手的，是工具系统。

Claude Code 的工具生态相当完整：

但更有意思的不是"有哪些工具"，而是工具从被请求到被执行之间经历了什么。

runToolUse（src/services/tools/toolExecution.ts）编排了一条完整的管线：

模型发出 tool_use 请求
  → ① 解析：按名称找到工具，用 Zod schema 校验参数
    → ② Pre-Hooks：调用 runPreToolUseHooks，允许外部脚本修改输入或直接阻止执行
      → ③ 权限门控：useCanUseTool 检查权限状态机
        → ④ 执行：调用工具的 run() 方法
          → ⑤ Post-Hooks：调用 runPostToolUseHooks，后处理结果
            → ⑥ 结果转换：截断过长输出、折叠连续搜索操作、存储完整结果供 UI 渲染

六个阶段，每一个都在模型的"意图"和真实的"操作"之间插入了一层缓冲。

其中最复杂的是第③步权限门控。它不是一个简单的 allow/deny 布尔值，而是一个状态机。源码里的 ToolPermissionContext 同时维护着：

  • • 始终允许规则（alwaysAllowRules）
  • • 始终拒绝规则（alwaysDenyRules）
  • • 始终询问规则（alwaysAskRules）
  • • 自动模式开关（isAutoModeAvailable）
  • • 后台分类器前置（awaitAutomatedChecksBeforeDialog）

这里有一个精彩的设计：YOLO 分类器。

对 BashTool，管线在解析工具参数的同时，就在后台并行启动一个轻量分类器，推测性地判断这条命令是否安全。如果分类器说"安全"，直接执行，不弹确认框。

为什么要这样做？因为 Anthropic 在自己的工程博客里承认了一个真实数据：用户会接受 93% 的权限提示。 这意味着弹框确认基本是走过场。更危险的是，频繁弹框会导致"确认疲劳"——用户开始无脑点"允许"，这比自动判断更不安全。

YOLO 分类器的设计哲学是：与其让一个疲劳的人类做 93% 正确率的判断，不如让一个专门训练的分类器做 99% 正确率的判断。 把人类的注意力留给那 1% 真正需要决策的场景。

我的洞察： 工具执行管线揭示了 Agent 安全设计的一个深层逻辑——安全不是加限制，而是分层过滤。 用 schema 校验拦住格式错误，用 hooks 拦住业务规则违规，用权限状态机拦住危险操作，用分类器加速安全操作——每一层解决一类问题，而不是把所有安全责任都压到一个"确认弹框"上。

第四层：模型调度——Agent 的大脑不止一个

你以为 Claude Code 背后只有一个模型？不是的。

从源码（src/utils/model/model.ts 和 src/query.ts）可以看到一套三级模型调度机制：

默认模型：Sonnet。 快，便宜，能处理 80% 的日常编码任务。

向上回退：Opus。 当 Sonnet 遇到复杂度上限或 API 过载时，FallbackTriggeredError 触发，系统自动切换到更强的 Opus。这就是你偶尔觉得 Claude Code "突然变聪明了"的原因——不是它开窍了，是换了个更强的脑子。

向下回退：Haiku。 上下文压缩、历史总结这类"苦力活"，用最快最便宜的 Haiku 就够了。没必要用 Opus 去做一件 Haiku 就能胜任的事。

模型之上还有一个 Token 预算系统（src/query/tokenBudget.ts），控制着整个循环的"油门和刹车"：

  • • 续航机制：当模型因为 max_tokens 限制停下来、但任务没完成时，系统注入一条 getBudgetContinuationMessage（"你已完成 X%，继续工作"），推动模型保持动力
  • • 收益递减检测：如果连续几轮模型只产出了不到 500 token（DIMINISHING_THRESHOLD），系统判定为空转，强制停止
  • • 90% 预警：当 token 消耗达到预算的 90%（COMPLETION_THRESHOLD），系统开始提示模型收尾

这两个东西——模型调度 + token 预算——组合起来解决的是同一个问题：用最小的成本完成任务，同时避免模型在无效循环里烧钱。

我的洞察： 模型调度揭示了一个行业里很少被正面讨论的事实——没有一个模型是"够用"的。 Opus 太贵不能当默认，Sonnet 太弱处理不了复杂任务，Haiku 只适合做后台苦力。一个成熟的 Agent 产品必须在多个模型之间做动态调度。这不是"未来的优化方向"，这是今天的工程现实。

第五层：工具池装配——Agent 的能力边界

最后一层也是最容易被忽略的：Agent 能用哪些工具，不是一个写死的列表。

从 src/tools.ts 和 src/Tool.ts 可以看到，Claude Code 的工具池是动态装配的。根据不同的条件，同一个 Agent 在不同场景下看到的工具集完全不同：

  • • 内置工具：所有场景都可用的核心工具（Bash、FileRead、FileEdit 等）
  • • Feature-gated 工具：通过 feature flag 控制的实验性工具，比如 KAIROS（持续助手模式）、AGENT_TRIGGERS（Agent 触发器）等
  • • MCP 工具：通过 Model Context Protocol 连接的第三方服务提供的工具
  • • 模式相关工具：REPL 模式和 Coordinator 模式下各自可见不同的工具组合

关键是：工具池的过滤发生在模型"看到"工具之前。filterToolsByDenyRules 在装配阶段就把不该暴露的工具剔除了。

这意味着权限控制不是"让模型看到所有工具，然后在调用时拦截"——而是在认知层面就限制了模型的能力边界。模型根本不知道有某个工具的存在，自然不会试图调用它。

还有一个精妙的优化：工具定义的延迟加载。当 MCP 服务器提供了上百个工具时，把所有工具的完整 JSON schema 都塞进每次 API 调用是对 token 的巨大浪费。所以系统只发送工具名称列表给模型。模型如果需要某个工具的详细定义，调用 ToolSearchTool 按需获取。

我的洞察： 工具池装配揭示了 Agent 设计中一个被严重低估的维度——Agent 的能力边界应该是动态的、可裁剪的，而不是一个固定的能力集。 你给模型看到越多的工具，它就越容易"分心"或做出错误选择。反过来说，精准地控制模型在当前场景下能看到什么工具，本身就是一种引导策略——不是通过 prompt 告诉它"不要用 X"，而是直接让 X 从它的世界里消失。

自下而上看：API 提供了原始的模型能力，Agentic Loop 把它变成可持续运转的自主循环，上下文工程让循环能"记住"必要信息，工具执行管线让循环能"动手"，模型调度让循环能"省钱"，工具池装配让循环的能力边界可控。

自上而下看：用户的一个自然语言 prompt，经过五层工程的加工、过滤、控制和优化，最终变成一系列精确的 API 调用、文件操作和 shell 命令。

这五层合在一起，就是一个完整的 Agent Harness。

这套架构给做 Agent 的人什么启示？

拆完五层，跳出来说几个我觉得真正重要的结论。

1. Harness 的价值正在超过 Prompt

行业里做 Agent 的团队，很多还在"调 prompt"的阶段——改改系统提示词、换换 few-shot examples、试试不同的 prompt 模板。

但 Claude Code 的源码清楚地表明：在一个成熟的 Agent 产品里，prompt 只是整个系统的一小部分。 真正决定 Agent 表现的，是循环控制的稳定性、上下文管理的精准度、权限系统的可靠性、模型调度的经济性。

这些东西写不进 prompt 里。它们是工程。

2. "护城河"在模型，"生死线"在 Harness

这次泄露后有一个广泛的共识：Claude Code 的代码里没有什么"秘密武器"。人们用 Claude Code，核心原因是 Anthropic 的模型能力——特别是 Opus 的编程能力。

但反过来说，如果 Harness 做得烂，再强的模型也发挥不出来。 模型再聪明，上下文管不好它会"忘事"，权限管不好它会"闯祸"，循环控不好它会"空转"，调度管不好它会"烧钱"。

护城河是模型，但生死线是 Harness。

3. 自主 Agent 的范式已经收敛

从 Claude Code 的架构，到 OpenAI 开源的 Codex，到 Google 开源的 Gemini CLI——你会发现一件事：大家的核心架构惊人地相似。 都是 Agentic Loop + 工具系统 + 上下文管理 + 权限控制。

这说明自主 Agent 的基本范式已经收敛了。就像 Web 应用最终收敛到了 MVC 架构，自主 Agent 正在收敛到 ReAct Loop + Tool System + Context Manager + Permission Layer 这个四件套。

差异不在架构，在工程深度。同样是上下文压缩，你做一级还是四级？同样是权限控制，你用布尔值还是状态机？同样是模型调度，你用一个模型还是三个模型动态切换？

架构范式相同的情况下，产品的差距来自每一层的工程纵深。

4. AI 编程工具的竞争，正在从"模型战"转向"系统战"

今天 Claude Code 能领先，是因为 Opus 的编程能力确实强。但模型的领先优势是有保质期的。

一旦竞品的模型能力接近（而这个趋势已经在发生），竞争就会转向 Harness 层面：谁的上下文管理更精准、谁的工具系统更稳定、谁的权限设计更优雅、谁的成本控制更经济。

到那时，51 万行代码里的每一个工程决策，才是真正的战场。
