"不同的数据访问方式不是一个需要被消灭的问题，而是一个需要被服务的现实。"

这句话来自 AWS S3 团队负责人 Andy Warfield，出自他昨天发表的一篇 6000 字长文。一个做了 20 年对象存储的团队，花了两年时间把文件系统接口塞进 S3 里——而真正让我眼前一亮的，不是这个功能本身，是他们在这个过程中撞上的一个更大的命题：

Agent 正在放大数据摩擦。

从向日葵说起

Andy 的故事开头很有意思。十年前他还在 UBC 教书的时候，跟一个研究向日葵 DNA 的植物学家合作。他们发现了一个让所有科学家都头疼的问题——不是分析数据，而是搬数据。

"Researchers were forever copying data back and forth, managing multiple, sometimes inconsistent copies."

"研究人员永远在来回复制数据，管理着多个经常不一致的副本。"

数据存在 S3 上，分析工具要求本地文件系统。两个世界之间隔着一条巨大的鸿沟，研究人员的大量时间不是花在科学研究上，而是花在写脚本搬数据上。

Andy 把这个问题叫做数据摩擦（data friction）。

十年过去了，这个问题不但没解决，反而因为一件事变得更严重了。

Agent 把数据摩擦放大了 10 倍

你应该已经注意到了：AI Agent 正在改变软件开发的方式。写代码的门槛在急剧下降——不是因为代码变简单了，是因为 Agent 替你写了。

Andy 在文章中有一段观察特别精准：

"Agents are illustrating just how prohibitively high the barrier to entry for writing software has always been, and are suddenly allowing apps to be written by a much larger set of people—people with deep skills in the domains of the applications being written, rather than in the mechanics of writing them."

"Agent 正在揭示写软件的门槛一直有多高，并突然让更多的人能写应用——那些精通业务领域而非编程技术的人。"

这意味着什么？ 应用的生命周期在加速。从想法到可运行代码的时间在急剧压缩。一个 Agent 可以在几分钟内搭出一个应用，用完就扔。但数据不会跟着应用一起死掉——数据永远比应用活得久。

"As the cost of building applications collapses... it really feels like the code/data division is becoming more meaningful than it has ever been before."

"当构建应用的成本崩塌式下降……代码和数据之间的分界变得前所未有地重要。"

说白了：在 Agent 时代，应用是一次性的，数据才是资产。

而这恰恰暴露了一个基础设施级的痛点——如果你观察过 Agent 工具写代码的方式，你会发现它们本能地使用 Unix 命令操作本地文件系统。ls、cat、grep、pandas.read_csv()。Agent 天然就是文件系统原住民。

但你的数据在哪？在 S3 上。

这就是矛盾：Agent 说文件系统语言，数据住在对象存储里。

S3 的"中年危机"和三次进化

S3 已经 20 岁了。这 20 年它一直是"对象存储"，但 AWS 的团队显然意识到，光做对象存储已经不够了。

过去两年，S3 连续做了三件事：

第一步：S3 Tables（2024）

大量客户在 S3 上存 Parquet 数据——光 Parquet 格式每秒就有 2500 万次请求。Apache Iceberg 让表格数据更好用了，但管理安全策略很痛苦，表维护和压缩需要手动操作。于是 S3 Tables 把"表"变成了 S3 的一等公民数据类型。今天已经有超过 200 万张表存在 S3 Tables 上。

第二步：S3 Vectors（2025）

AI 时代催生了向量索引的需求。客户发现一个尴尬的事实：向量索引的数据量往往比被索引的数据还大，而且存在更贵的介质上。S3 Vectors 把向量索引做成了弹性的、S3 原生的数据类型——从几百条记录到数十亿条，按需扩展。

第三步：S3 Files（今天）

让任何 S3 数据都能直接当文件系统来用。

一条主线串起这三步：S3 正在从"存东西的地方"变成"用数据的地方"。存储系统的角色不再只是安全地保管数据，而是要让数据用最自然的方式被使用。

S3 Files 的设计：一场"不可调和的矛盾"

这部分是整篇文章最精彩的地方。

Andy 的团队最初的想法很朴素——把 EFS（弹性文件系统）和 S3 搅在一起，取两者的优点。他们甚至给项目起名叫"EFS3"（幸好没用这名字）。

然后他们就撞墙了。

文件和对象，从骨子里就是不同的东西：

  • • 文件是操作系统的概念。你可以原地修改一个文件的中间部分，别人能几乎实时看到你的改动。mmap() 把文件当内存用。
  • • 对象的核心假设是不可变性。往一个对象的中间写数据？那简直是亵渎。应用依赖对象的版本控制、内容哈希、创建通知——S3 每天发送超过 3000 亿条事件通知。

团队把高级工程师关在会议室里（Andy 说"亚马逊的会议室其实没有锁"），吵了好几轮，最后承认：把文件和对象融合成一个统一系统，得到的不是"两全其美"，而是"最低公约数"。

"A battle of unpalatable compromises."

"一场令人难以下咽的妥协之战。"

有个有趣的细节：因为 S3 没有目录的概念，你可以创建一个以 "/" 结尾的对象——看起来像目录，其实是文件。团队兴奋了 20 分钟，还给它起了个名字叫 "filerectory"（文件+目录）。幸好这个名字也没保留下来。

"Stage and Commit"：最好的设计来自接受现实

2024 年圣诞节假期后，团队换了一个思路：不再试图让边界消失，而是把边界本身变成一个功能。

他们从 Git 借了一个概念——Stage and Commit（暂存与提交）：

  1. 1. 挂载：把 S3 的 bucket 或前缀挂载到 EC2、容器或 Lambda 上，变成一个本地目录
  2. 2. 文件操作：用任何文件系统工具正常读写——vim、pandas、训练脚本，随便用
  3. 3. 同步到 S3：修改大约每 60 秒自动同步回 S3，作为完整的 PUT 操作
  4. 4. 双向同步：其他应用通过 S3 API 修改了对象，文件系统视图自动更新
  5. 5. 冲突处理：如果两边同时改，S3 是真理源，文件系统版本进 lost+found

还有几个技术细节很巧妙：

  • • 懒加载：首次访问目录时，128KB 以下的文件连数据一起拉，大文件只拉元数据，读的时候才取——所以挂载百万级对象的 bucket 可以秒开
  • • 读绕过（read bypass）：高吞吐顺序读时，自动绕过 NFS，直接并行 GET S3，单客户端 3GB/s，多客户端可达 Tb/s 级别
  • • 30 天淘汰：30 天没访问的文件数据从文件系统视图驱逐，但 S3 上不删，存储成本只与活跃工作集成正比

Andy 坦诚地列出了已知的局限：

  • • rename 很贵——S3 没有原生 rename，改名一个目录意味着复制+删除每个对象
  • • 50M 对象警告——挂载超过 5000 万对象时会收到警告
  • • 60 秒同步窗口——对大多数工作负载够用，但不是所有

"We'd rather be clear about them than pretend they don't exist."

"我们宁愿坦诚地说出来，也不愿假装它们不存在。"

说实话，我很喜欢这种态度。

对你意味着什么？

如果你是 AI 开发者

这可能是 Agent 基础设施里一块缺失的拼图。你的 Agent 不需要再学 boto3，不需要写 S3 上传下载的逻辑，直接 open('/mnt/s3/data.csv') 就行。Agent 可以用最自然的方式操作数据，不需要为存储系统改变自己的工作方式。

如果你是数据工程师

Tables + Vectors + Files 这三件套意味着 S3 正在变成一个统一数据湖。结构化数据用 Tables，向量索引用 Vectors，非结构化数据用 Files——同一份数据，不同的访问方式，不再需要在系统之间搬来搬去。

如果你是架构师

"Stage and Commit"模式值得认真研究。它不是一个 hack，它是一种哲学——承认不同访问模式的差异，显式管理边界，而不是假装差异不存在。这个思路对很多系统设计问题都有启发。

我的判断

S3 Files 本身是一个很实用的功能，但更有意思的是它背后的信号。

AWS 正在把 S3 从一个"存储服务"重新定义为一个"数据平台"。对象、表、向量、文件——四种数据原语，覆盖了你能想到的几乎所有数据访问模式。

而推动这一切的底层逻辑是：Agent 时代，应用越来越"轻"，数据越来越"重"。当构建应用的成本趋近于零，存储和数据管理反而成了真正的基础设施竞争力。

20 年前 S3 定义了云存储。现在它在尝试定义 Agent 时代的数据基础设施。这个方向对不对，我觉得是对的。但能不能跑出来，还要看 60 秒同步窗口能不能缩到亚秒级，rename 的性能问题能不能解决，以及——最关键的——开发者是不是真的会拿它来喂 Agent。

你的 Agent 现在是怎么操作数据的？直接读文件，还是调 API？ 这个问题的答案，可能决定了你需不需要关注 S3 Files。评论区聊聊。
