"The Evolution of AI Agents: Solo → Swarm."

这是港大 HKUDS 团队在 ClawTeam 项目首页写的第一句话。翻译过来就是：AI Agent 的进化方向，是从单兵作战到集群智能。

听起来像是又一个 Multi-Agent 框架的营销话术？

我一开始也这么想。直到我看完它的架构设计文档——整个系统没有数据库，没有消息队列，没有微服务，消息传递就是往文件夹里写 JSON。

就这？就这能让 8 个 AI Agent 同时跑在 8 张 H100 上，自主完成 2430 个 ML 实验？

还真就这。

先搞清楚：它和 CrewAI、AutoGen 有什么不同

Multi-Agent 框架不新鲜。CrewAI、AutoGen、MetaGPT……这些名字你多少听过。但 ClawTeam 和它们有一个根本性的区别——

用 ClawTeam 官方的话说：

"Who uses it: The AI agents themselves."

"谁在用它：AI Agent 自己。"

传统框架里，人是编排者。你定义角色、写 workflow、配 YAML、管状态。Agent 只是你编排逻辑中的执行单元。

ClawTeam 反过来了。它是一个 CLI 工具，Agent 自己调用它来建团队、分任务、发消息、看进度。 人只需要给一个目标，Leader Agent 自己决定拆几个子任务、spawn 几个 worker、谁先做什么、谁等谁。

这里面最关键的一行是"任何 CLI agent"。原文写得很直白：

"Any CLI agent can participate in a ClawTeam team — it just needs to run shell commands. No custom SDK, no API integration, no framework lock-in."

"任何 CLI agent 都能加入 ClawTeam 团队——只要能跑 shell 命令就行。不需要专用 SDK，不需要 API 集成，没有框架锁定。"

Claude Code、Codex、OpenClaw、Kimi CLI、nanobot……甚至你自己写的 Python 脚本，都能当 worker。

这才是真正的范式转换：不是人在编排 Agent，是 Agent 在编排 Agent。

一句话进去，一个团队出来

来看一个具体场景。你对装了 ClawTeam skill 的 Claude Code 说：

"Build a full-stack todo app with auth, database, and React frontend."

然后你就可以去泡杯咖啡了。

Leader Agent 会自己完成以下全部操作：

第一步，建团队：

clawteam team spawn-team webapp -d "Full-stack todo app"

第二步，拆任务、建依赖链：

T1: "设计 REST API schema"          → architect
T2: "实现 JWT 认证" --blocked-by T1   → backend1
T3: "搭建数据库层" --blocked-by T1    → backend2
T4: "Build React 前端"               → frontend
T5: "集成测试" --blocked-by T2,T3,T4  → tester

注意 --blocked-by。T2 和 T3 被 T1 阻塞，T5 被 T2、T3、T4 同时阻塞。这不是简单的任务列表，是一张有向无环图（DAG）。

第三步，spawn 5 个 worker，每个拿到独立的 git worktree 和 tmux 窗口：

clawteam spawn --agent-name architect --task "Design the API schema"
clawteam spawn --agent-name backend1  --task "Implement JWT auth"
clawteam spawn --agent-name backend2  --task "Build PostgreSQL models"
clawteam spawn --agent-name frontend  --task "Build React UI"
clawteam spawn --agent-name tester    --task "Write pytest tests"

这里有一个很巧妙的设计：每个 worker 被 spawn 时，会自动注入一段"协调协议"提示词（Coordination Protocol），教它怎么跟团队协作：

- 📋 Check your tasks: clawteam task list <team> --owner <your-name>
- ▶️ Start a task:     clawteam task update <team> <id> --status in_progress
- ✅ Finish a task:    clawteam task update <team> <id> --status completed
- 💬 Message leader:   clawteam inbox send <team> leader "status update..."
- 📨 Check inbox:      clawteam inbox receive <team>
- 😴 Report idle:      clawteam lifecycle idle <team>

不需要任何额外配置。Worker 天生就"知道"怎么查任务、报进度、发消息。这就是为什么任何 CLI agent 都能参与——只要能跑 shell 命令。

第四步，依赖自动解锁、Worker 持续轮询：

architect 完成 → backend1 和 backend2 自动从 blocked 变成 pending。所有后端完成 → tester 自动启动。

而且 Worker 不是做完一个任务就退出。它会进入一个持续轮询循环：

# 1. 检查分配给自己的任务
clawteam task list my-team --owner worker1
# 2. 做完后检查收件箱，看有没有新指令
clawteam inbox receive my-team --agent worker1
# 3. 如果闲了，通知 Leader
clawteam lifecycle idle my-team

Leader 可以随时给它派新活。这不是"一次性执行"，是一个活的工作循环。

Worker 之间还能直接通信：

architect → backend1: "Here's the OpenAPI spec: ..."
backend1 → tester: "Auth endpoints ready at /api/auth/*"
tester → leader: "All 47 tests passing ✅"

最后 Leader 把所有 worktree 合并回 main 分支。整个过程，你只说了一句话。

8 张 H100、2430 个实验、零人工干预

搭个 todo app 还不够刺激？来看这个。

基于 Karpathy 的 autoresearch 项目，ClawTeam 编排了 8 个 AI Agent 分别跑在 8 张 H100 上，做 LLM 训练优化。

人类的输入就一句：

"Use 8 GPUs to optimize train.py. Read program.md for instructions."

Leader Agent 接手后的操作链：

🦞 Leader agent's actions:
├── 📖 Read program.md, understand the experiment protocol
├── 🏗️ clawteam team spawn-team autoresearch
├── 🚀 Assigned each GPU a research direction:
│   ├── GPU 0: "Explore model depth (DEPTH 10-16)"
│   ├── GPU 1: "Explore model width (ASPECT_RATIO 80-128)"
│   ├── GPU 2: "Tune learning rates and optimizer"
│   ├── GPU 3: "Explore batch size and accumulation"
│   ├── GPU 4-7: Codex agents, more directions
│   └── 🌳 Each agent: own git worktree, own branch
├── 🔄 Every 30 minutes:
│   ├── clawteam board show autoresearch
│   ├── Read each agent's results.tsv
│   ├── 🏆 Identified best findings
│   └── 📡 Cross-pollinated: told new agents to start from best config
├── 🔧 When agents finished:
│   ├── Killed idle agents, cleaned worktrees
│   ├── Created new worktrees from the best commit
│   └── Spawned fresh agents with combined optimization directions
└── ✅ After 2430+ experiments: val_bpb 1.044 → 0.977

最终结果：2430+ 个实验，val_bpb 从 1.044 降到 0.977（提升 6.4%），大约 30 GPU-hours。

说实话，6.4% 的提升在超参搜索里算正常水平。真正让我觉得厉害的是两个细节：

第一，交叉授粉。 Leader 不是让 8 个 agent 各跑各的。它每 30 分钟汇总一次结果，把最优配置"喂"给新 spawn 的 agent。这是一种涌现式的集体智能——单个 agent 的发现会变成整个团队的起点。

第二，动态资源回收。 Agent 闲了就回收 GPU，重新分配方向。不是静态的"8个任务分8张卡"，是一个活的调度系统。

全程零人工干预。人类只按了一下回车。

一条 TOML 命令，7 个 AI 分析师帮你炒股

如果你觉得 ML 实验离自己太远，来看一个更"接地气"的案例——AI 对冲基金。

ClawTeam 支持用 TOML 模板定义团队原型。一条命令就能启动一个完整的 7 人投资分析团队：

clawteam launch hedge-fund --team fund1 \
  --goal "Analyze AAPL, MSFT, NVDA for Q2 2026"

然后自动发生的事情：

🦞 Portfolio Manager (leader) spawns and receives the goal
├── 🎩 Buffett Analyst    → 价值投资（护城河、ROE、DCF）
├── 🚀 Growth Analyst     → 颠覆性增长（TAM、网络效应）
├── 📈 Technical Analyst  → 技术指标（EMA、RSI、布林带）
├── 📋 Fundamentals       → 财务比率（P/E、D/E、FCF）
├── 📰 Sentiment Analyst  → 新闻舆情 + 内部交易信号
├── 🛡️ Risk Manager       → 等所有分析师信号，汇总风控报告
└── 💼 Portfolio Manager  → 最终买入/卖出/持有决策

5 个分析师从不同维度独立研究，Risk Manager 汇总所有信号后出风控报告，Portfolio Manager 做最终决策。

一个 TOML 文件定义角色、任务、提示词。一条命令启动整个团队。 你可以用同样的方式定义自己的团队模板——DevOps 团队、内容生产团队、数据分析团队，随你想象。

拆解架构：一封消息的旅程

好了，案例看够了。作为技术人，你一定想问：这东西底层到底怎么跑的？

ClawTeam 的架构文档写得非常清楚。我把它的核心架构拆成四层，跟你走一遍"一封消息从 Alice 发到 Bob"的完整旅程。

第一层：CLI 调用层

所有操作的入口。Agent 通过 shell 命令调用 clawteam：

clawteam inbox send my-team bob "Start implementing the auth module"

这一层包括 commands.py（命令路由）、watcher.py（收件箱监听）、lifecycle.py（生命周期管理）、plan.py（计划审批）、collector.py（信息收集）。

第二层：MailboxManager——消息的"翻译官"

CLI 层把请求交给 MailboxManager，它干三件事：

  1. 1. 构建 TeamMessage（Pydantic 模型）——把"Alice 发给 Bob 的一段文字"结构化为标准消息对象
  2. 2. 序列化为 JSON bytes——统一格式
  3. 3. 委托给 Transport 层做实际投递——自己不碰 I/O

MailboxManager 提供四个核心方法：send()、broadcast()、receive()、peek()。上层只跟它打交道，完全不需要知道底层用的是文件还是 ZeroMQ。

第三层：Transport 抽象层——真正的精华

这是整个架构最巧妙的部分。Transport 是一个抽象基类（ABC），定义了四个接口：

方法
作用
deliver(recipient, data)
投递原始字节
fetch(agent, limit, consume)
取消息（consume 控制是否删除）
count(agent)
未读计数
list_recipients()
列出所有收件人

然后有两个实现：

FileTransport（默认）——消息就是文件：

teams/{team}/inboxes/{agent}/msg-*.json

发消息 = 先写一个 .tmp-xxx.json，再 rename 成 msg-*.json。原子写入，不会出现写到一半崩溃导致的脏数据。 收消息 = sorted glob 读取所有 msg-*.json，读完 unlink 删除。

简单到什么程度？整个消息系统就是"往文件夹里扔文件、从文件夹里捡文件"。 没有守护进程，没有端口监听，没有连接池。

P2PTransport（可选，需要 pip install clawteam[p2p]）——ZeroMQ 直连：

P2P 模式下，每个 agent 启动时会：

  1. 1. 绑定一个 ZMQ PULL socket，监听某个端口
  2. 2. 把自己的地址写入 peers/{agent}.json（Peer 发现机制）

发消息时，先读对方的 peers/B.json 拿到地址，检查对方 PID 是否存活，然后 ZMQ PUSH 直连发送。

关键设计：如果对方不在线怎么办？

读 peers/B.json → 不存在 或 PID 已死
  ╔══════════════════╗
  ║ ZMQ 不可达       ║
  ║ 回退到文件兜底    ║
  ╚══════════════════╝
→ 调用内部的 FileTransport.deliver() 写文件

P2PTransport 内部组合了一个 FileTransport 实例作为 fallback。对方在线就 ZMQ 直连（微秒级延迟），不在线就降级到文件模式（对方上线后自动捡到）。

收消息时也是双通道：先 PULL.recv(NOBLOCK) 尝试从 ZMQ 拿，再 fallback.fetch() 从文件目录捡。两个通道完全正交，互不干扰。

这个"P2P + 文件兜底"的设计，用架构文档的原话说：

P2P 消息通道                    共享文件系统
• 临时的，读完即删               • 持久的，所有人可见
• 传信号/通知/请求               • 传内容/配置/状态
• ZMQ PUSH/PULL                • 普通文件读写

        完 全 正 交，互 不 干 扰

第四层：存储层

所有持久化状态都在文件系统上：

~/.clawteam/
├── teams/{team}/
│   ├── config.json     → 团队配置
│   ├── plan.md         → 计划文档
│   ├── tasks.json      → 任务看板
│   ├── members/        → 成员信息
│   ├── board/          → 看板数据
│   ├── inboxes/{agent}/ → 每个 agent 的收件箱
│   │   └── msg-*.json   → 消息文件
│   └── peers/{agent}.json → P2P 地址发现
└── workspaces/          → git worktree 隔离空间

没有数据库。没有 Redis。没有 etcd。 所有写入都是 tmp + rename 原子操作，崩溃安全。

配置解析：三级优先级

Transport 的选择遵循一个清晰的优先级链：

环境变量 CLAWTEAM_TRANSPORT → 配置文件 config.transport → 默认值 "file"

如果值是 p2p，走 P2PTransport（从 AgentIdentity 读取 bind_agent）；否则走 FileTransport。

模块依赖关系

commands.py ─────┐
watcher.py ──────┤
lifecycle.py ────┤
plan.py ─────────┼──► MailboxManager ──► Transport (ABC)
collector.py ────┘                          │
                                    ┌───────┴───────┐
                                    ▼               ▼
                              FileTransport    P2PTransport
                                    ▲               │
                                    └── fallback ───┘

上层五个模块只依赖 MailboxManager，MailboxManager 只依赖 Transport 抽象接口，FileTransport 和 P2PTransport 是可插拔的实现。经典的依赖倒置。

说实话，看完这个架构我有一种"就这？"的感觉。但仔细想想，"就这"恰恰是它最厉害的地方。

它没有追求"生产级"的架构，而是选择了最低技术门槛的方案——只要你有个文件系统和 tmux，就能跑。一台笔记本就能玩，不需要 Docker、不需要 K8s、不需要云服务。

而且 Roadmap 已经规划了 v0.4 Redis Transport（跨机器消息）和 v0.5 Shared State Layer（跨机器状态共享）。文件系统是起点，不是终点。

几个值得单独说的：

Plan Approval——Worker 可以先提交计划给 Leader 审批，批了再执行。这在高风险任务（比如数据库迁移）中很关键。

Context Inject——在把任务从一个 agent 交接给另一个时，可以把 git diff、文件变更、冲突检测等上下文注入给接手的 agent。避免"接力棒掉了"。

对你意味着什么

ClawTeam 目前是 v0.3，3 月 18 日才公开发布，还很早期。但它指向的方向很清晰：

AI Agent 的下一步进化，不是单个 agent 变得更强，而是多个 agent 学会协作。

原文用了一个很形象的比喻：

"Human provides the goal. The Agent Team orchestrates everything else."

"人类提供目标。Agent 团队搞定剩下的一切。"

几个你可以立刻行动的事：

1. 如果你在做 ML 实验—— 多 GPU 并行研究模式是最成熟的场景。一个人盯 8 张卡跑超参的日子可能到头了。pip install clawteam，试试让 Leader 帮你编排实验。

2. 如果你在做全栈开发—— 给 Claude Code 装上 ClawTeam skill（放到 ~/.claude/skills/clawteam），然后说"用 clawteam 拆分任务并行开发"。5 个 agent 并行写代码，理论上开发速度有数倍提升。

3. 如果你想搞自己的 Agent 团队—— 写一个 TOML 模板，定义角色、任务、提示词，clawteam launch 一键启动。对冲基金只是个例子，你可以做 DevOps 团队、内容生产团队、数据分析团队。

4. 三步上手：

pip install clawteam          # 安装
tmux -V && claude --version   # 确认依赖
# 然后对 Claude Code 说：
# "Build a web app. Use clawteam to split the work across multiple agents."

演进方向

当然，问题也不少。

文件系统当消息队列，能扛多大并发？ 单机几十个 agent 没问题，但跨机器通信依赖 SSHFS 或 NFS，延迟和可靠性都是问号。好在 Roadmap 里 v0.4 就是 Redis Transport。

Leader Agent 的调度能力有上限。 当前的 LLM 在长上下文推理上还不够稳定。5 个 agent 的团队没问题，50 个呢？任务依赖图变复杂后，Leader 能不能做出正确决策？v0.7 规划的"Adaptive Scheduling（自适应调度）"就是为了解决这个问题，但还在探索阶段。

成本是实打实的。 5 个 agent 并行 = 5 份 API 费用。8 张 H100 跑 30 GPU-hours，电费和算力成本不是小数目。Multi-Agent 的 ROI 需要认真算。

调试是噩梦。 一个 agent 出 bug 已经够难调了，5 个 agent 同时跑、互相发消息、共享状态——出了问题翻哪个 agent 的日志？好在 clawteam board attach 能平铺所有 agent 的 tmux 窗口，--json 输出也方便脚本化监控。但这离"好调试"还有距离。

不过这些都是工程问题，不是方向问题。

从独狼到狼群

回到开头那句话：Solo → Swarm。

就像"单机版"软件最终都走向了分布式，AI Agent 也会从单打独斗走向团队协作。区别只在于：谁来定义协作的方式？

传统框架说：人来定义，Agent 来执行。

ClawTeam 说：人给目标，Agent 自己定义。

"One Command Line: Full Automation."

"一条命令，全自动。"

这个项目的 Roadmap 也很有野心——v0.6 计划做 Agent Marketplace（社区共享 agent 模板），v1.0 目标是生产级（认证、权限、审计日志）。

能不能走到那一步？不知道。但至少有一点可以确认——AI 的下一个里程碑，可能不是更大的模型或更强的推理，而是 Agent 之间的协作智能。
