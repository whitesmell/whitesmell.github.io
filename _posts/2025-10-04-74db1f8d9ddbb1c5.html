Claude Agent SDK重磅发布，带来两大革命性特性：
进程内自定义工具，告别繁琐的子进程管理和IPC开销，实现性能与开发体验的双重飞跃；
Hooks（钩子）机制，以“中间件”模式为Agent行为注入确定性规则，带来前所未有的安全与可控性。

本文将从API设计、核心功能、内部架构、通信协议、逐文件代码实现、及高级实战场景等多个层面进行终极深度剖析，揭示其如何成为构建下一代专业级AI应用的利器。

AI Agent开发，正在告别“玩具时代”

在我们上一篇文章《Claude Agent SDK：代码之外，Anthropic的智能体新哲学》，我们探讨了Anthropic将“Code SDK”更名为“Agent SDK”背后的哲学飞跃——即认识到“编码能力”的本质是通往通用智能体的钥匙，而终端和文件系统则是其与数字世界交互最理想的界面。

但宏大的理念，若无坚实的工程基础，终将是空中楼阁。这篇文章将完成从“为什么”到“怎么做”的关键跨越。我们将深入SDK的“骨髓”，从架构原理到源码实现，为你提供一份将Agent哲学转化为可靠、高效代码的终极实战指南。

而当你掌握了这套坚实的工程“术”之后，下一步便是探索如何设计AI自主工作流的“道”——《Agentic Loops：少数人正在掌握的AI权力新范式》。

一、API 设计：简洁与强大的双重奏

Claude Agent SDK的设计哲学在API层面就体现得淋漓尽致：它深知开发者需求的多样性，因此提供了两种截然不同的交互模式。

1.1 query(): 简单任务的“瑞士军刀”

对于一次性的、无状态的任务，query()函数是一个优雅的异步迭代器，让你用最少的代码完成任务。

import anyio
from claude_agent_sdk import query

async def main():
    async for message in query(prompt="法国的首都是哪里?"):
        print(message)
# anyio.run(main)

query()的本质是“发完即走”，适合集成到自动化脚本、CI/CD流水线或进行数据批处理。

1.2 ClaudeSDKClient: 构建复杂会话的“重型机甲”

当你的应用需要进行多轮对话、维护上下文时，ClaudeSDKClient是你的不二之选。它是一个全功能的、有状态的客户端，专为构建复杂的交互式应用（如智能客服、开发助手）而设计。

import anyio
from claude_agent_sdk import ClaudeSDKClient

async def interactive_session():
    async with ClaudeSDKClient() as client:
        await client.query("帮我规划一个为期三天的北京旅游路线。")
        async for msg in client.receive_response():
            print(msg)
        await client.query("很棒的计划！请在第二天加入攀登长城的活动。")
        async for msg in client.receive_response():
            print(msg)
# anyio.run(interactive_session)

ClaudeSDKClient的双向、持续通信能力是构建真正“智能”应用的基石。

二、核心创新（一）：“内生”工具——告别IPC的性能飞跃

进程内工具（In-Process Tools） 是SDK最具颠覆性的设计，它彻底改变了Agent与外部能力的交互方式。

2.1 @tool 装饰器的一行魔法

传统Agent框架依赖外部进程或API调用，存在性能、部署、调试等诸多痛点。Claude Agent SDK通过@tool装饰器和create_sdk_mcp_server，将工具的定义和执行完全内化到Python应用进程中。

import anyio
from claude_agent_sdk import tool, create_sdk_mcp_server, ClaudeSDKClient, ClaudeAgentOptions

@tool("greet", "向用户问好", {"name": str})
async def greet_user(args):
    return {"content": [{"type": "text", "text": f"你好, {args['name']}!"}]}

server = create_sdk_mcp_server(name="my-tools", tools=[greet_user])
options = ClaudeAgentOptions(
    mcp_servers={"tools": server},
    allowed_tools=["mcp__tools__greet"]
)

async def use_tool():
    async with ClaudeSDKClient(options=options) as client:
        await client.query("和 Alice 打个招呼")
        async for msg in client.receive_response():
            print(msg)
# anyio.run(use_tool)

这种从“外部依赖”到“内生能力”的思维转变，极大地提升了性能和开发体验。

三、核心创新（二）：Hooks——为Agent行为注入“确定性”

Hooks（钩子）机制为解决LLM的不确定性提供了强大的工程化方案。它允许你在Agent生命周期的关键节点（如PreToolUse - 工具使用前）注入确定性的Python代码。

3.1 HookMatcher 实现深度解析

HookMatcher是配置Hooks的关键，其定义HookMatcher(matcher: str | None, hooks: list[HookCallback])看似简单，实则体现了SDK与CLI运行时的精妙分工。

  • • matcher: str: 这个字符串不是在Python SDK内部进行匹配的。它会作为配置信息，在会话初始化时通过控制协议发送给claude-code CLI。真正的匹配逻辑发生在Node.js运行时中。CLI会根据matcher字符串（如 "Bash" 或 "Write|MultiEdit|Edit" 这样的管道分隔列表）来决定，当LLM提议使用某个工具时，是否需要通过RPC回调Python端。
  • • hooks: list[HookCallback]: 这是一个Python异步函数列表。当CLI匹配成功后，它会向SDK发送一个control_request，其中包含一个callback_id。SDK的Query模块会用这个ID在内部查找并await执行这个列表中的相应函数。

这个设计的核心是责任分离：

  1. 1. CLI (Node.js): 负责高效的、特定于Agent运行时的事件匹配。
  2. 2. SDK (Python): 负责执行用户定义的、复杂的、特定于业务的回调逻辑。

四、架构原理：本地RPC与三层解耦

理解了上层API后，让我们深入一层，看看这一切是如何工作的。这正是Claude Agent SDK区别于其他“高级封装”框架的地方——它拥有一个清晰、健壮的底层架构。

4.1 核心通信模型：基于子进程的本地RPC

首先要明确一点：这个Python SDK不是直接通过HTTP API与Anthropic后端通信的。它是一个本地Agent运行时的控制器。其核心架构是一种基于标准输入输出（stdio）的、进程间的远程过程调用（RPC）。

这个架构的优势是高效和解耦。它避免了网络开销，利用了操作系统最高效的IPC机制之一（管道）。同时，Python SDK与Node.js运行时是两个独立的进程，可以独立迭代和更新，只要双方遵守同一套基于JSON的通信协议。

4.2 控制协议揭秘：control_request 与 control_response

SDK与CLI之间的双向通信不仅仅是传递用户和助手消息，更关键的是一套控制协议。当CLI（Agent运行时）需要Python端执行某些操作时（如调用工具、触发钩子），它会通过stdout发送一个特殊类型的JSON消息：

{
  "type": "control_request",
  "request_id": "req_12345",
  "request": {
    "subtype": "hook_callback",
    "callback_id": "hook_0",
    "input": { "..." }
  }
}

SDK内部的Query类会捕获这个请求，根据subtype找到对应的Python函数（你的Hook函数），执行它，然后将结果封装成control_response，通过stdin发回给CLI：

{
  "type": "control_response",
  "response": {
    "subtype": "success",
    "request_id": "req_12345",
    "response": {
      "hookSpecificOutput": { "permissionDecision": "deny" }
    }
  }
}

request_id是实现这种异步RPC的关键。正是这套控制协议，让你的Python代码能够无缝地嵌入到Agent的决策循环中，实现了进程内工具和Hooks这两大核心功能。

4.3 依赖清单：运行时与服务

要成功运行此SDK，你的环境需要满足以下依赖：

  • • 本地运行时依赖 (Client-Side):
    1. 1. Python 3.10+: SDK本身的要求。
    2. 2. claude-agent-sdk: 通过pip安装的Python包。
    3. 3. Node.js: claude-code CLI的运行环境。
    4. 4. @anthropic-ai/claude-code: 通过npm install -g安装的Claude Code CLI。这是必须的，因为SDK的本质是控制这个CLI进程。它才是真正的“Agent运行时”，负责与Anthropic后端通信、管理工具、维护状态等。
  • • 服务端依赖 (Server-Side):
    • • Anthropic Account & API Access: SDK本身不直接依赖，但它所控制的claude-code CLI需要配置有效的Anthropic API密钥才能与后端LLM服务通信。

五、源码剖析：从API到协议的实现之旅

现在，让我们戴上工程师的眼镜，逐一审查构成SDK骨架的关键文件。

5.1 src/claude_agent_sdk/client.py & query.py - 公共API层

  • • 文件角色与架构定位:
    这是SDK的公共API门面（Facade），是开发者唯一的交互入口。它位于整个架构的最顶层，其核心设计目标是易用性和封装性，将所有底层的进程管理、协议通信、消息解析等复杂性完全隐藏。
  • • 关键设计与实现:
    • • query()函数: 体现了函数式和流式的设计思想。它是一个无状态的、一次性的操作，返回一个AsyncIterator，这使得处理响应数据既直观又内存高效。
    • • ClaudeSDKClient类: 采用了面向对象和上下文管理器的设计模式。
      • • 类图:
        ClaudeSDKClient
        +options: ClaudeAgentOptions
        -_transport: Transport | None
        -_query: Query | None
        +init(options, transport)
        +connect(prompt)
        +disconnect()
        +query(prompt)
        +receive_response() : AsyncIterator<Message>
        +aenter() : "ClaudeSDKClient"
        +aexit(...) : bool
      • • __aenter__ / __aexit__ (RAII模式): 这个组合是ClaudeSDKClient最优雅的设计之一，它实现了“资源获取即初始化”（Resource Acquisition Is Initialization）。进入async with块时自动connect，退出时（无论正常或异常）自动disconnect，完美地管理了子进程和IO流的生命周期，杜绝了资源泄露的可能。

5.2 src/claude_agent_sdk/types.py - 数据契约层

  • • 文件角色与架构定位:
    这是整个SDK的**数据契约（Data Contract）**层。它不包含任何执行逻辑，但其重要性无与伦比。它定义了所有模块间、以及SDK与CLI之间通信的数据结构，是系统的“单一事实来源”，确保了类型安全和通信协议的一致性。
  • • 关键设计与实现:
    • • ClaudeAgentOptions (配置对象模式): 将所有可配置项聚合到一个dataclass中。这避免了“上帝构造函数”（God Constructor），使得配置可传递、可扩展，并且在IDE中有极佳的自动补全支持。
    • • AssistantMessage & ContentBlock (组合模式): AssistantMessage包含一个ContentBlock列表，ContentBlock又可以是TextBlock、ToolUseBlock等。这种设计使得Agent的响应可以灵活地由多种类型的内容块组成，极具扩展性。
    • • SDKControlRequest (协议绑定): 这是对底层JSON RPC协议的TypedDict实现，是类型安全地处理控制消息的关键。

5.3 src/claude_agent_sdk/_internal/transport/subprocess_cli.py - 物理传输层

  • • 文件角色与架构定位:
    这是架构最底层的物理传输层。它的职责非常纯粹：管理claude CLI子进程的生命周期，并将上层传来的字符串写入stdin，同时从stdout异步读取行，供上层解析。
  • • 关键设计与实现:
    • • _build_command() (配置翻译): 这是一个经典的适配器模式的体现。它将Python世界的ClaudeAgentOptions对象，适配成命令行世界的list[str]参数。
    • • _read_messages_impl() (健壮的流解析): 解决了TCP/IP编程中同样存在的“粘包/半包”问题。由于stdout是一个流，一个JSON对象可能被分成多次读取，或者多个小JSON对象在一次读取中返回。该函数通过缓冲和推测性解析的循环，健壮地解决了这个问题，确保了消息的完整性。

5.4 src/claude_agent_sdk/_internal/query.py - 协议与路由层

  • • 文件角色与架构定位:
    这是SDK的大脑和中枢神经系统。它位于Transport层之上，是控制协议的实现者和消息分发路由器。它理解消息的“含义”，并根据其类型执行相应的逻辑。
  • • 关键设计与实现:
    • • 时序图：一个完整的RPC调用
      claude-code CLI_internal.Transport_internal.QueryClaudeSDKClientclaude-code CLI_internal.Transport_internal.QueryClaudeSDKClientInitialization phase (not shown) registers hooks.stdout: control_request(subtype="hook_callback", id="req_abc")raw_dict_read_messages() routes to _handle_control_request()Finds user's hook_function via callback_idresult = await hook_function()write(control_response(id="req_abc", result))stdin: JSON response
    • • _read_messages() (事件循环): 这是一个典型的事件驱动设计。它在一个后台任务中不断地“监听”来自Transport的消息，然后像一个交换机一样将消息分发到不同的处理路径（RPC或用户消息）。
    • • _send_control_request() (异步RPC客户端): 这是Future/Promise模式的教科书式实现。它通过anyio.Event来同步异步操作。当它发送请求后，它await一个Event，将自己挂起。当远端（CLI）的响应通过_read_messages到达时，后者会set这个Event，从而唤醒前者并传递结果。这个request_id -> Event的映射是实现多个并发RPC调用的关键。

六、工程实践：从基础模式到“专家团队”

6.2 高级模式：agents.py 中的“专家团队”

agents.py文件揭示了一个更为强大和可扩展的应用模式：定义和使用自定义Agent。这允许你在同一个会话中，根据任务的不同，调用具有不同“专业技能”的Agent。

  • • 核心概念：AgentDefinition
    AgentDefinition是一个dataclass，用于封装一个特定角色的完整配置，包括它的描述、独特的系统提示、被授权的工具集，甚至可以指定使用哪个模型（如sonnet或opus）。
  • • 模式四：构建和调用“专家Agent”
    你可以预先定义一个或多个“专家”，比如一个“代码审查员”。这个审查员有自己的行事准则（prompt）和工具箱（tools）。
    # From examples/agents.py
    async     def code_reviewer_example():
        options = ClaudeAgentOptions(
            agents={
                "code-reviewer"    : AgentDefinition(
                    description="Reviews code for best practices and potential issues",
                    prompt="You are a code reviewer. Analyze code for bugs...",
                    tools=["Read", "Grep"],
                    model="sonnet",
                ),
            },
        )
        # 在Prompt中通过名字 "code-reviewer" 来调用这个专家
        async     for message in query(
            prompt="Use the code-reviewer agent to review the code in src/...",
            options=options,
        ):
            # ... process message ...

    模式解析:

    1. 1. 我们在ClaudeAgentOptions的agents字典中，定义了一个名为code-reviewer的专家。
    2. 2. 在随后的query中，我们通过在prompt里明确指示Use the code-reviewer agent to...，来激活这个特定的专家。
    3. 3. 运行时，CLI会加载code-reviewer的配置（特定的prompt, tools, model）来处理这个任务，而不是使用默认配置。
  • • 模式五：组建“多专家协作团队”
    你可以同时定义多个专家。这在构建复杂的、多步骤工作流的Agent时尤其有用，你可以先让“分析员”找出问题，再让“测试员”编写测试用例。
