从 Anthropic 的 Founder’s Playbook 到可执行工作流，AI-native 创业真正稀缺的不是代码，而是判断、上下文和时间沉淀。

Anthropic 发布的《The Founder’s Playbook》真正值得读的，不是它介绍了多少 Claude 功能，而是它重新定义了 AI 原生创业的四个阶段：Idea、MVP、Launch、Scale。

这份 Playbook 最重要的判断是：AI 不只是让创业更快，它也让错误方向被更快执行。过去创始人可能卡在不会写代码、没有工程师、做不出 Demo；现在这些门槛下降了，真正稀缺的变成了判断：什么问题值得做，什么时候该停，哪些数据只是热闹，哪些能力能变成护城河。

所以，我们后来把这套方法论进一步落成了开源项目 ai-native-founder-skills。它不是 Playbook 摘要，而是把其中最值得执行的判断流程做成可调用 Skills：验证问题、寻找反证、定义 MVP 范围、沉淀项目上下文、建立指标框架、审计创始人瓶颈。

一、Anthropic 的 Playbook 真正讲的，不是工具，而是创业顺序变了

很多人第一次看到《The Founder’s Playbook》，会把它理解成一份 Claude 工具指南。里面确实讲到了 Claude Chat、Claude Code、Claude Cowork，也确实给出了不同阶段如何使用 Claude 的练习。

但如果只读成“Claude 怎么帮创业者提效”，这份材料就被读浅了。

它真正讲的是：AI 正在改变创业公司的生长顺序。

传统创业有一条默认路径：验证想法，融资，招人，构建产品，再融资，再招人，再增长。每进入一个新阶段，公司都需要更多人、更多技能和更多资金。想做产品，要工程师；想卖产品，要销售；想跑运营，要运营；想进入企业客户，要安全、合规和客户成功。于是，headcount 长期被视为公司成熟度的信号。

AI-native startup 挑战的是这个假设。

在 AI 原生公司里，研究、构建、运营的一部分能力，可以更早被系统化。市场研究可以先由 AI 做结构化整理，代码可以由 coding agent 生成和测试，访谈归纳、指标周报、文档同步、CRM 更新，也可以进入自动化工作流。

创始人不再只是“亲自完成每一件事的人”，而更像一个编排者：他要判断哪些任务交给 Claude，哪些任务交给人，哪些判断必须留在自己手里。

这也是 Playbook 最核心的线索：

AI 不只是压缩执行成本，也提前暴露了创始人的判断质量。

过去，一个坏想法可能会死在执行门槛前。不会写代码、找不到工程师、融不到第一笔钱、Demo 做不出来，这些摩擦会让很多方向停在纸面上。现在，坏想法也能快速长出产品外壳。

一个创始人只是想验证一个想法，Claude Code 很快就能生成登录页、数据库、支付流、后台和测试。浏览器里的 Demo 能点、能跳、能保存数据，看起来已经像一个产品。

危险也正在这里发生：它只是能跑，还没有证明有人需要。

所以，AI-native 创业的第一课，不是更快构建，而是重新排序：

先证明问题值得做，再证明产品能做出来。

二、Idea 阶段：构建越容易，验证越不能省

Playbook 最值得反复咀嚼的部分，是 Idea 阶段。

AI 创业最危险的诱惑，是刚有一个想法，就能把它做出来。过去，一个原型可能需要几周甚至几个月。这个成本很烦，但它也会逼创始人先想清楚：用户是谁，痛点多强，现有替代方案是什么，用户是否愿意付钱。

现在不同了。一个看起来像产品的 Demo 可以在一天内出现，原本用于阻止冲动的摩擦力消失了。于是，最容易发生的误判是：把“构建”误认为“验证”。

Playbook 提醒创始人，Idea 阶段真正要做的不是写代码，而是找到 problem-solution fit。你要证明这个问题真实、具体、频繁，证明你的方案解决的是验证后暴露出来的真实问题，而不是你一开始脑补出来的问题。只有当你有足够定性证据，进入 MVP 才不是凭信仰开工。

这里有一个非常重要的角色转变：Claude 在 Idea 阶段最不应该做啦啦队，而应该做红队。

很多创始人会这样使用 Claude：“帮我证明这个方向有机会”“帮我整理市场空间”“帮我写一份竞品分析”。Claude 很擅长顺着你说。如果你让它找支持材料，它通常能很快生成一套看起来有理有据的论证。但创业早期最需要的往往不是支持，而是反证。

更好的问法是：

这个方向为什么可能根本不成立？

失败竞品、负面市场信号、用户行为障碍、结构性风险、你自以为很强但其实很脆弱的差异化，都应该在写第一行代码之前被摆到桌面上。

Idea 阶段至少有四个基本动作。

第一，把一句情绪改成一个可验证假设。

“合同审查太慢”不是好假设，“中型公司法务团队因为 redline 散在邮件线程里，每份合同多花 3 天审查”才有测试价值。“报销很烦”也不是好假设，“财务经理每周因为报销系统和会计系统不互通，多花 4 小时核对记录”才像一个可以验证的问题。

一个可验证假设，至少要说清楚：谁，在什么场景里，因为现有方案的什么缺陷，每周损失多少时间、钱或机会，以及他们现在如何凑合解决。

第二，替竞品说话。

创始人很容易低估竞争对手，尤其是那些看起来“不够性感”的替代方案。真正的竞品未必是另一个 AI 产品，可能是 Excel、邮件、外包、人肉流程，甚至是用户“不解决也能忍”的习惯。竞品官网往往不够诚实，用户评论里的抱怨、绕路和妥协，反而更接近真实需求。

第三，别迷信 TAM。

TAM/SAM/SOM 可以做，但市场规模不是机会本身。你还要知道谁有预算，谁影响决策，购买流程怎么走，市场是在扩大、收缩还是已经成熟，监管、技术、人口结构在未来两年是顺风还是逆风。市场很大，不代表你能进去；市场很热，也不代表你该进去。

第四，听真实用户讲过去。

客户访谈里最没价值的问题之一是：“如果有一个产品，你会用吗？”这类问题很容易得到礼貌回答。更好的问题是：“上一次你遇到这个问题是什么时候？当时发生了什么？你怎么处理？花了多久？谁参与？哪里最烦？”

过去行为，比未来承诺更值钱。

Idea 阶段结束时，创始人不应该只是“有一个想法”。他应该能说清楚：这不是脑子里的幻觉，而是一群真实用户愿意认真对待的问题。只有到这一步，Claude Code 才应该进入场内，去做一个单一核心交互的轻原型。

三、MVP 阶段：AI 技术债不是代码烂，而是上下文断裂

很多人把 MVP 当施工阶段。Playbook 的提醒更准确：MVP 仍然是证据收集阶段，只不过这次验证的不是问题，而是方案。

用户会不会用，会不会回来，会不会付钱，会不会推荐给别人，这些才是 MVP 的核心。Claude Code 让构建变快，但快不是壁垒，快只是默认值。真正难的是，在高速度里保持边界和清醒。

MVP 阶段最容易被低估的新问题，是 AI 技术债。

传统技术债通常是：为了速度写了烂代码，以后再重构。AI 原生开发的技术债更隐蔽。它未必表现为某段代码很烂，而是每一次 AI coding session 都可能重新猜你的架构、边界、依赖、命名和取舍。

今天让 Claude Code 加登录，明天让它加账单，后天让它改权限。每次单看都能跑，但几十次会话之后，代码库可能变成一个功能不少、没人真正理解的系统。

为什么模块这样拆？为什么依赖这样选？为什么权限这样设计？哪里是临时妥协，哪里是长期边界？没人说得清。

这份债不会立刻报错。它会在下一次迭代时，让系统脆成一堆碎片。

MVP 开工前，至少要写清三份东西。

第一，项目上下文。它回答代码应该按什么原则长出来。Claude Code 需要知道：产品为什么存在，服务谁，架构原则是什么，哪些依赖不要碰，哪些边界不能跨。没有这个上下文，每一次 session 都像一个新工程师重新入职。

第二，MVP 范围文档。它写清楚做什么、不做什么，什么用户证据才允许加功能。过去，工程成本会天然限制范围；现在，功能太便宜，反而需要人为设置证据门槛。一个功能能不能做，不再是好问题；真正的问题是：是否有足够多真实用户证明，没有这个功能就无法获得核心价值？

第三，度量框架。它提前定义 activation、retention、Day 7、Day 30 和 false positive。早期数据很会骗人：朋友注册、投资人资源导流、社交媒体转发、Product Hunt 或 Hacker News 的短期流量，都可能制造漂亮曲线。但这些不一定代表 PMF。

真正有价值的是冷却后的行为。第 6 周、第 12 周，最初那波热情退掉以后，用户还在不在。

一个好的 MVP，不是更小的产品，而是更聚焦的验证系统。

四、Launch 阶段：产品跑起来后，公司还没长出来

MVP 证明产品值得存在，Launch 要证明业务值得增长。这个阶段最容易出现一种错觉：产品跑起来了，用户来了，公司就自然长出来了。事实不是这样。产品旁边，还要长出一家公司。

Launch 阶段有三个退出标准：增长可重复，产品能承受生产负载，运营不再卡在创始人身上。

也就是说，增长不能只靠朋友圈、投资人介绍和偶然曝光，而要知道具体渠道、CAC、LTV 和回本周期；基础设施、安全、合规、可靠性不能只在 Demo 条件下成立；支持、triage、sprint planning、报表、反馈整理、文档更新，也不能都靠创始人记得去做。

早期，创始人在每个环节里是优势。用户说什么，创始人直接听；产品怎么改，创始人当场判断；bug 怎么排，创始人立刻处理。增长以后，同样的习惯会变成堵点。

一个支持请求只有创始人知道怎么回，一个 bug 只有创始人知道该不该修，一个客户反馈只有创始人能翻译成产品语言，一个周报只有创始人记得要拉。

公司看起来很忙，其实只是创始人很忙。

这时要做的不是“创始人消失”，而是把创始人的注意力从低价值流程里释放出来。

最直接的方法，是做一次创始人注意力审计：哪些任务反复出现，哪些决策总是回到创始人这里，哪些流程只有创始人想起来才会发生，哪些可以自动化，哪些可以授权，哪些必须保留创始人判断。

这张表很关键。公司扩张最大的成本，不只是人力成本，更是创始人的注意力被低价值流程持续吃掉。

公司不是因为人多才成熟，而是因为流程能离开某个人继续运行，才开始成熟。

五、Scale 阶段：当代码不再值钱，护城河只能来自时间

到了 Scale 阶段，问题不再是产品能不能跑，而是：如果一个资金更足、渠道更强的大公司今天复制你的功能，用户为什么还留下？

这正是标题里的问题：当代码不再值钱，什么才是护城河？

答案不是“更强的模型”。模型能力会扩散，coding agent 会普及，产品功能会被追平。一个 dashboard、一个聊天入口、一个自动报告生成器、一个 CRUD 工作流，都很难长期挡住别人。真正难复制的，是时间沉淀下来的东西。

Playbook 里有一个重要概念：accumulated depth。可以理解为“累积出来的深度”。它不是单一能力，而是多个层次叠加：领域知识、用户数据、工作流锁定、组织成熟度。

第一层，是领域知识深度。

法律、医疗、采购、供应链、养老护理、非营利组织募资，每个行业都有外行不知道的术语、流程、例外、灰度判断和隐性经验。AI 可以帮助创始人把这些经验外化，逐渐变成产品上下文、验证规则、测试用例、系统集成和工作流。

第二层，是用户数据深度。

用户在产品里接受哪些输出，拒绝哪些输出，在哪一步修改，在哪个环节卡住，哪些流程反复触发，这些不是网上买得到的数据，而是时间锁定、场景特定、与真实工作流绑定的数据。后来者可以复制功能，但复制不了一群用户过去一年如何在你的系统里工作、修正、积累偏好。

第三层，是工作流锁定。

工具容易替换，工作流很难替换。当客户只是登录你的产品试用，切换成本很低；当客户把你的产品接入 CRM、ERP、邮件、文档、审批系统，并在上面跑自动化流程，你就不再只是一个软件，而是客户运营的一部分。切换你，不是换工具，而是重做流程、重训团队、重连系统。

第四层，是组织成熟度。

Scale 阶段，客户不只看产品，也看你是不是一个可靠的长期基础设施伙伴。SLA 是什么，支持响应时间是多少，文档能不能让工程团队看懂，事故怎么处理，有没有日志、监控、告警、审计，合规材料是否齐全，财务、合同、客户成功、续约流程是否稳定，这些都会成为企业客户和外部审查者衡量你的标准。

所以，Scale 阶段的护城河不是代码，而是被时间锁住的知识、数据、集成和工作流。

六、从 Playbook 到 Skills：方法论最终要变成可执行工作流

前面讲的是 Playbook 的核心方法论。到这里，才轮到 skills 项目出场。

我们做 ai-native-founder-skills，不是为了把 Playbook 摘要成一组文件，也不是为了给 Claude 做宣传。真正的动机是：这套方法论如果只停留在文章里，很容易被读完、收藏，然后在真实创业现场被忘掉。

创始人真正需要的是运行时约束。

当他刚有一个想法时，需要有人提醒：先把模糊想法改成可验证假设。
当他只看到支持证据时，需要有人提醒：主动寻找反证。
当他设计客户访谈时，需要有人提醒：问过去行为，不问未来意愿。
当他准备做 MVP 时，需要有人提醒：先定义不做什么。
当他让 Claude Code 写代码时，需要有人提醒：先写项目上下文。
当他看到早期数据时，需要有人提醒：先定义 false positive，再谈 PMF。

这也是我们把 Playbook 的关键判断拆成 Skills 的原因。

比如：

problem-hypothesis-refiner，负责把“我有个想法”改成“谁在什么场景里，因为现有方案的什么缺陷，每周损失多少”。

disconfirming-evidence-finder，负责让 AI 先证明你可能错，而不是默认帮你找支持材料。

customer-discovery-designer，负责把“你会不会用”改成“上一次你怎么处理”。

mvp-scope-definer，负责明确 MVP 做什么、不做什么，什么证据才允许加功能。

project-context-architect，负责把项目上下文写成 AI coding agent 可以读取的长期记忆。

这些 Skills 不是文章的附件，而是方法论的运行时形态。项目 README 也把它定位为一组可复用 founder workflows，用于验证想法、定义 MVP 范围、审计创始人瓶颈，并构建可防守的创业壁垒。(github.com)

七、Skills 不是护城河本身，但它是沉淀护城河的基础设施

当代码不再值钱，护城河来自哪里？

来自长期沉淀下来的判断、上下文、流程和数据。

而这些东西如果只存在创始人脑子里，就很难复制给团队，也很难被 AI 使用；如果只存在会议纪要和散落文档里，也很难在关键时刻被调用。它们必须变成更结构化的形式：项目上下文、验证模板、访谈框架、指标定义、流程审计、集成地图、用户行为分析。

这正是 Skills 的意义。

Skills 不是护城河本身。护城河仍然来自真实用户、真实场景、真实数据和真实工作流。但 Skills 可以成为沉淀护城河的基础设施：它把一次性的经验变成可复用流程，把创始人的隐性判断变成团队可以调用的显性规则，把零散方法论变成 AI 可以执行的工作流。

这也是 AI-native 和普通“用了 AI 工具”的根本区别。

用了 AI 工具，只是效率提升。
把知识、判断、流程和上下文变成可运行系统，才是 AI-native。

结语：Claude 给出油门，Skills 把刹车装回去

Founder’s Playbook 最值得记住的一句话是：

The bottlenecks are no longer what you can build, but what you choose to build.

瓶颈不再是你能构建什么，而是你选择构建什么。

这句话放在今天，比任何时候都更现实。Claude 会让更多人跨过执行门槛：不会写代码的人也能做产品，融不到第一笔钱的人也能做 Demo，招不到工程师的人也能启动原型。但坏想法不会因为执行成本降低就变好，它只会更快变成一个看起来像产品的东西。

所以，AI 原生创业最该训练的不是“怎么让 Claude 多写点代码”，而是五种更笨、更硬的能力：

写出可验证假设。
主动寻找反证。
锁住 MVP 范围。
先建指标仪表盘。
把知识沉淀进系统。

Playbook 让我们看见了这套新规则。Skills 的意义，是把这些规则带进真实工作流。

如果你现在手里有一个 AI 产品想法，不要先打开 Claude Code。先把问题讲清楚，找反证，设计访谈，定义 MVP 边界，写好项目上下文，再开始构建。

因为今天的创业不缺油门。

真正稀缺的是：知道什么时候不踩。
