很多人用 Claude Code，像是在终端里打开了一个更聪明的 ChatGPT。

问一句，等它写。

错了，再骂一句。

能跑，就收工。

这当然也有用。但说实话，这只是 Claude Code 的浅水区。

真正把它用顺的人，不是 prompt 写得多漂亮，而是把它当成一个可以被训练、被配置、被验证、被分工的工程系统。

原文作者 Arpan Patel 在《Beyond the Prompt: Claude Code》里把这件事讲得很透。原文发布于 2026 年 5 月 26 日，信息量很大，从 .claude 目录、CLAUDE.md、Skills、Subagents、Plugins、MCP，一路讲到 Anthropic 团队自己的工作习惯。

我读完最强烈的感受是：

Claude Code 的上限，不在一次 prompt，而在一套工作流。

原文收束处有一句话特别准：

“The setup is the work.”

设置本身，就是工作。

这句话听起来有点反直觉。

你以为你在用 AI 写代码。

其实你是在搭一套“让 AI 能稳定写好代码”的环境。

别把它当自动补全

Claude Code 的第一层变化，是心态变化。

别把它当一个“prompt-and-wait”的聊天框。

要把它当一个需要护栏的 autonomous agent。

这里最重要的一条原则来自 Boris Cherny 和 Anthropic 团队：

“Give Claude a way to verify its output.”

给 Claude 一种验证自己输出的方法。

没有验证，反馈回路只有你。

有了验证，Claude 可以自己跑测试、看报错、修复、再跑测试。原文里说，Boris 认为这件事单独就能带来 2 到 3 倍质量提升。

这也是很多人用 AI 编程卡住的原因。

他们把 Claude 当写手，却不给它验收标准。

一个更稳的工作方式是：

探索，再计划，再写代码。

Plan mode 可以用 Shift+Tab 两次进入。这个模式下 Claude 只读不写。让它先读文件、追数据流、理解模型和边界，再出计划，再执行。

小修小补可以跳过这一步。

但只要一次改动跨多个文件，我建议都先 plan。

更硬一点的做法，是让一个 Claude 写计划，再开一个全新 session，让另一个 Claude 以 staff engineer 的视角审计划。因为第二个 session 没有“我刚刚已经想过了”的上下文偏见，更容易挑出洞。

如果执行跑偏，不要一路在原 session 里打补丁。

回到 plan mode，重写计划，并把验证步骤写进去。

另一个高频误区是描述太模糊。

不要说“看看 auth 模块”。

直接给路径：@src/auth/login.py。

不要手动复述错误。

把日志管进去：cat error.log | claude。

精确上下文，永远比大概描述强。

Cat Wu 的建议也很狠：把 Claude 当成一个你要委派任务的工程师，而不是一个你逐行带着写的 pair programmer。

先写清楚 brief。

然后让它跑。

如果你想改 Claude 的计划，可以按 Ctrl+G，把计划打开到编辑器里直接改。计划本质上就是文本。先把文本捏对，再让它变成代码。

还有一条我觉得特别值得立刻抄走：

Claude 每犯一次错，就让它把规则写进 CLAUDE.md。

比如它又忘了跑测试，你不要只说“下次记得”。你直接说：

Update CLAUDE.md so you do not repeat this.

原文说 Boris 觉得 Claude 很擅长从自己的错误里写规则。这个习惯会复利。

一次错误，是一次失败。

一条规则，是以后少犯十次。

.claude 不是杂物间，是控制台

很多人打开过 .claude/，看到 CLAUDE.md，然后就没再往里看。

但原文提醒，这其实是一套分层配置系统。

有两个 scope。

Project scope 放在 repo 里的 .claude/，适合提交到 git，让团队共享。

Global scope 放在 ~/.claude/，适合跨项目使用，描述你个人的偏好和习惯。

一句话心智模型：

project files 描述项目，global files 描述你。

一个典型结构大概长这样：

my-repo/
├── .claude/
│   ├── settings.json
│   ├── agents/
│   │   ├── pr-review.md
│   │   └── test-writer.md
│   ├── skills/
│   │   └── api-conventions/SKILL.md
│   └── rules/
│       ├── frontend.md
│       └── migrations.md
├── CLAUDE.md
├── CLAUDE.local.md
└── .mcp.json

这里有三个细节很容易被低估。

第一，CLAUDE.md 会 cascade。

如果你在 monorepo 里工作，根目录的 CLAUDE.md 会加载，子目录比如 services/billing/CLAUDE.md 也会加载。不同服务可以有自己的约定。

第二，rules/*.md 可以 path-gated。

只对 db/migrations/ 生效的规则，不该塞进全局 CLAUDE.md。把它放到 .claude/rules/migrations.md，按 glob 触发，干净很多。

第三，新东西优先写 Skills，不要只写 commands。

.claude/commands/*.md 和 .claude/skills/<name>/SKILL.md 都能变成 slash command，但 Skills 支持辅助文件、disable-model-invocation、allowed tools、agent overrides。后面你会发现，这些能力很关键。

还有一个交接机器前很实用的小命令：

claude project purge ~/path/to/repo --dry-run

它可以先预览 Claude 对某个项目持有了哪些本地状态。

CLAUDE.md 要短，狠，能救命

CLAUDE.md 每次 session 开始都会加载。

写差了，Claude 就稳定重复你的项目坑。

写好了，同样的 prompt 会像换了一个人。

Boris 对 CLAUDE.md 的态度很简单：

短。

每一行都问自己一句：删掉它，Claude 会不会更容易犯错？

如果不会，删。

原文提到，Claude Code 团队自己 repo 里的 CLAUDE.md 非常克制。核心就是开发流程：

  • • 永远用 bun，不用 npm
  • • 先改代码
  • • 跑 bun run typecheck
  • • 单测可以按 test name 或 file glob 跑
  • • commit 前跑 lint
  • • PR 前跑 bun run lint:claude && bun run test

就这些。

没有漂亮话。

没有代码库旅游。

没有“请保持代码高质量”这种空气。

它只放 Claude 猜不到、但必须遵守的东西。

更妙的是，Boris 会在 PR review 里直接让 @claude 把规则写回去。

比如 review 里发现不该用 TS enum，而应该用 literal union，就让 Claude 把这条加进 CLAUDE.md。

原文把这叫 Compounding Engineering。

我很喜欢这个说法。

每一次 PR review，不只是修一次代码。

它还在训练下一次 Claude。

一个好用的 CLAUDE.md，通常包括四块：

  • • Code style：只写项目特殊约定，比如 ES modules，不写通用废话。
  • • Workflow：必须跑哪些命令，什么时候能 claim done。
  • • Architecture：API route 必须经过哪个 middleware，新 query 放哪里。
  • • Gotchas：Claude 真的犯过的坑，比如 User 和 UserRecord 是两种类型。

其中最值钱的是 Gotchas。

每一条都是被现实打过的补丁。

哪些东西不该进 CLAUDE.md？

标准语言规范、逐文件代码介绍、长教程、API 文档、频繁变化的内容。

如果内容只是“参考资料”，可以用 @path import：

See @README.md for project overview and @package.json for scripts.
@~/.claude/my-preferences.md

IMPORTANT、YOU MUST 这类词确实能提高遵守率，但别滥用。

全篇都是警报，警报就失效了。

原文还给了几个 CLAUDE.md 学习来源：

  • • mattpocock/skills 的 CLAUDE.md，看 skills 怎么写、怎么测。
  • • anthropics/claude-code-action，看 Anthropic 自己怎么对待公开工具。
  • • awesome-claude-code，收了很多不同技术栈的公开 CLAUDE.md。
  • • claudelog.com，社区按 stack 整理的例子。

CLAUDE.local.md 是你的私人纠错本

CLAUDE.local.md 和 CLAUDE.md 一样会加载。

区别是，它不提交。

它只属于你。

原文作者的用法很朴素：每次 PR review 收到反馈，就把高频反馈丢进去。几周以后，它就变成一份私人训练集。

比如：

  • • 新 SQS consumer 同一个 PR 里必须带 DLQ 和 alarms。
  • • 新 endpoint 的测试必须包含 auth failure。
  • • 加 endpoint 时别忘了更新 OpenAPI spec。
  • • 不要 console.log，用项目 logger。
  • • 返回 3 个以上字段时，优先 named tuple，不要裸 dict。

下次你让 Claude 写 endpoint，它已经知道要补 auth-failure test。

这不是记忆力。

这是把 reviewer 的碎碎念，变成自动化规则。

我建议分成两块：

项目特定反馈 和 个人坏习惯。

不要混在一起。

也要定期删。

已经变成肌肉记忆的东西，就从 CLAUDE.local.md 拿掉。这个文件记录的是你还在学习的东西，不是人生传记。

Skills：把重复 prompt 变成团队资产

Skills 是 Claude Code 里最容易被低估的能力之一。

它让 Claude 从“什么都能做一点”，变成“某件事特别会做”。

一个 skill 本质上是一个文件夹。

项目级放 .claude/skills/<name>/。

全局级放 ~/.claude/skills/<name>/。

里面有一个 SKILL.md，带 frontmatter 和 instructions。文件夹名就是 slash command。

最简单的例子：summarize-changes。

它的说明可以是：当用户想知道当前 diff、要 commit message、要 review changes 时使用。

调用时，它可以跑：

!`git diff HEAD`

然后把当前 diff 注入上下文，再按固定格式输出风险点：错误处理缺失、硬编码、测试要不要补。

Skills 强在三件事。

Progressive disclosure。

Claude 启动时只读 frontmatter description，大约每个 skill 100 tokens。完整 SKILL.md 和辅助文件，只有真的用到时才加载。

Skills 是文件夹。

你可以塞 templates、references、scripts、config。SKILL.md 只是入口，不是全部。

Inline shell。

以 ! 开头的行会运行命令，并把输出注入。

frontmatter 也能加很多控制项：

---
name: my-skill
description: When to use this skill
disable-model-invocation: true
allowed-tools: Read, Grep, Bash
agent: read-only
---

有副作用的 skill，建议加 disable-model-invocation: true。

比如 /ship 这种可能部署的动作，只能用户明确输入，不能让 Claude 自己觉得“相关”就触发。

原文还给了一个 Go API conventions 的完整 skill 思路。

结构像这样：

.claude/skills/go-handler/
├── SKILL.md
├── templates/
│   └── handler.go.tmpl
└── examples/
    └── healthz.go

这个 skill 会告诉 Claude：

  • • 技术栈是 Go 1.22、chi router、sqlc、zap、testify。
  • • handler 里不要写 raw SQL，走 sqlc typed queries。
  • • 不要 fmt.Println，用 structured logging。
  • • 测试优先 table-driven tests。
  • • chi.URLParam 缺参数时返回空字符串，不返回 error，所以要检查。
  • • httperr.Wrap 不会自动 log，要先 h.log.Error。
  • • auth middleware 通过 context.Value(authkey.User) 注入用户，要 type assert 到 *models.User。
  • • sqlc nullable string 用 pgtype.Text，读 .String 前要看 .Valid。
  • • handler 测试用 httptest.NewRecorder 和 httptest.NewRequest，别开真实 server。

这就是 skill 的价值：

新工程师不用先读完整个代码库，也能加一个符合团队习惯的 endpoint。

原文推荐的 Skills 资源也不少。

mattpocock/skills 被原文称为最热门的 skills repo，约 100k stars。里面几个代表：

  • • /grill-me：写代码前先拷问你的计划。
  • • /tdd：强制 red-green-refactor。
  • • /diagnose：按 reproduce、minimize、hypothesize、fix、regression test 调 bug。

安装命令：

npx skills@latest add mattpocock/skills

Jeffallan/claude-skills 则有 66 个语言或角色 profile，比如 go-pro、python-pro、java-architect、typescript-pro、rust-engineer、sql-pro。它们可以组合。Next.js 任务可以同时拉 nextjs-developer 和 typescript-pro。

Anthropic 官方 skills 也很值得看：

  • • /code-review：四个 parallel agents 审 diff，只给 confidence-scored findings。
  • • /simplify：看最近代码有没有复用和效率问题。
  • • /batch：把迁移任务分给几十个 parallel agents，各自 worktree。
  • • /webapp-testing：给 Claude Playwright 控制权，测试本地 web app。

判断标准很简单：

一天重复一次以上的事，就该变成 skill。

把 skills 提交到 git。

它们会变成团队知识。新人 clone repo 的时候，也把团队踩过的坑一起 clone 下来了。

Subagents：别让主线程背所有上下文

Subagent 的价值特别直白：

它有自己的 context window。

它可以读 50 个文件，然后只把 summary 汇报回来。你的主 session 不会被塞爆。

一个 subagent 是 .claude/agents/ 或 ~/.claude/agents/ 下的 markdown 文件。frontmatter 声明 name、description、tools、model。

原文拆了一个 /pr-review agent。

它的设定很像一个 senior staff engineer：

  • • 看当前分支相对 main 的 diff。
  • • 看 commit log。
  • • 读完整文件，不只看 diff 上下文。
  • • 交叉检查 CLAUDE.md、CLAUDE.local.md 和 .claude/rules/。
  • • 找 correctness bugs、security issues、缺测试、N+1 queries、项目约定违规。
  • • 不报没有规则依据的个人风格偏好。
  • • 不对能工作的代码随便建议重构。
  • • 不碰 diff 之外的问题。

输出按严重程度分组：Critical、High、Medium、Low。

每条都要有 file、line、issue、suggested fix。

结尾给 verdict：SHIP、FIX FIRST 或 REWORK。

这个 agent 的两个设计选择很关键。

tools 是只读。

因为会改代码的 reviewer，很容易偏向维护自己的修改。

model 选 opus。

高风险 review，别省这点模型成本。

我最建议你立刻试的是 writer/reviewer 模式。

Session A 实现。

然后叫 code-reviewer subagent 查。

reviewer 在新上下文里看代码，没有“这是我刚写的”的自我辩护。

如果是大规模迁移，可以在 agent frontmatter 里加 worktree isolation，让每个 subagent 在自己的 git worktree 里跑。

这才是 parallel AI coding 的正确姿势。

Plugins：把一组能力打包安装

Plugins 是更大的封装。

它可以把 skills、hooks、subagents、MCP servers 打成一个安装单元。

运行 /plugin 可以打开 marketplace browser。

也可以用：

/plugin marketplace add owner/repo

添加社区 marketplace。

原文建议 day-one installs 先看这些：

/code-review。

它会启动四个 parallel agents：两个查 CLAUDE.md compliance，一个扫 bug，一个用 git blame 看上下文。重点是 confidence-scored，尽量少噪音。

/feature-dev。

这是官方 marketplace 上最热门的 skill。它把 feature brief 变成七阶段流程：requirements、exploration、architecture、implementation、testing、review、docs。

Language server plugin。

它提供精确 symbol navigation，并在每次 edit 后自动 diagnostics。原文说团队普遍认为这是最高影响力插件。

/security-guidance。

Anthropic 官方安全 skill，在问题进生产前先把风险抬出来。

插件类别也很广。

原文给出的口径是，截至 2026 年中，75+ marketplaces 里有 1000+ plugins。方向包括 Git workflow、code intelligence、文档生成、测试、Playwright 浏览器自动化、Figma design system、Sentry 和 Datadog 观测等。

我的判断是：

团队共享的 .mcp.json，加少数几个认真挑过的 plugins，会直接改变新人 onboarding。

新人 clone repo，不只是拿到代码。

他还拿到了团队的工具面。

很多人没用过的命令，才是真效率

大多数人只知道 /clear、/compact、/init。

/compact 和 /clear 的区别要搞清。

真正的新任务，用 /clear，再手写一个干净 brief。

相关任务还需要旧上下文，用 /compact，并给 hint。

/compact 是有损 LLM summary。

/clear 是你重新定义任务。

差别很大。

/rewind 也很重要。

每个 prompt 都会形成 checkpoint，跨 session 也会保留。

Claude 走错路时，不要继续说“刚才不对，试试这个”。这样只会污染上下文。

更好的做法是 rewind，然后带着新认识重新 prompt。

还有两个小技巧。

用 ! 做 shell escape：

!git status
!npm test

输出会直接进入上下文。

也可以设置：

CLAUDE_CODE_AUTO_COMPACT_WINDOW=400000

原文说 1M context 模型在 300k 到 400k tokens 附近会开始出现 context rot，所以可以提早 compact，让 session 保持锋利。

大规模 fan-out 的思路也很粗暴：

先在 3 个文件上测试 prompt。

修好 prompt。

再把 2000 个文件丢给 claude -p 批量迁移。

示意是：

claude -p "Migrate this file from React to Vue. Return OK or FAIL." \
  --allowedTools "Edit,Bash(git commit *)" \
  --bare

重点不是这段命令本身。

重点是先小样本校准，再大规模放大。

/goal：让 Claude 不要半路收摊

/goal 是原文专门拎出来讲的能力。

它设定一个完成条件，Claude 会持续工作，直到条件为真。每次它想停下来，都会对照 transcript 检查目标是否达成。

例子：

/goal all tests in test/auth pass and the lint step is clean

更实际一点：

/goal all integration tests in tests/api pass without flaking 3 runs in a row
/goal the OpenAPI spec validates and matches the actual response shapes
/goal docker compose up runs cleanly and the healthcheck endpoint returns 200
/goal coverage on src/billing/ is above 80% and all new tests are not placeholders

条件必须可验证、确定、能被命令或文件状态判断。

“代码质量很好”这种目标没用。

它不是验收条件，只是愿望。

/goal 可以和几个东西搭配：

  • • /loop：定时重复，适合 burn down backlog。
  • • /schedule：云端按节奏跑。
  • • Stop hook：用你自己的 test suite 或 CI endpoint 做闸门。
  • • Auto mode：减少权限确认，避免长目标卡住。

原文把 /goal + auto mode + /focus 视为 Boris 和 Cat Wu 推崇的 Opus 4.7 工作流。

写清 brief。

设置目标。

走开。

回来拿 PR。

听起来很爽，但我会泼一点冷水：

这个模式的前提不是“AI 很强”。

而是你的目标足够可检验，项目规则足够清楚，测试足够可信。

否则它只是在很努力地把错事做完。

MCP：让 Claude 接上真实系统

MCP，也就是 Model Context Protocol，会把 Claude Code 从 coding agent 变成 system-aware coding agent。

没有 MCP，Claude 主要读文件、跑命令。

有了 MCP，它可以读 Linear tickets、查 Postgres、拉 Figma component、看 Sentry stack traces、读 Obsidian vault。

工程里常见 MCP 大概是这些：

MCP
解锁什么
GitHub
repo、PR、issues、code search
Context7
最新 library docs，prompt 里加 use context7
Sentry
真实错误上下文、stack traces、breadcrumbs
Linear
读写 tickets、更新 status
Playwright
基于 accessibility snapshots 的浏览器自动化
Figma
live design tree、auto-layout、spacing tokens、component refs
Postgres / Supabase
直接查 dev DB
Slack
读 thread、总结讨论、草拟回复

本地 server 常用 stdio。

厂商托管 server 常用 HTTP + OAuth。

比如 Sentry：

claude mcp add --transport http sentry https://mcp.sentry.dev/mcp

团队共享 MCP 放项目根目录 .mcp.json。

个人 MCP 放 ~/.claude.json。

但别看到 MCP 就全装。

每加一个 MCP，Claude 要推理的 tool list 就膨胀一点。工具太多，决策质量会掉。

原文建议 starter set 很克制：

GitHub、Context7，再加一两个领域特定 MCP。

排查 MCP 连接时，先跑：

/mcp

它会列出活跃 server 和连接状态。

Obsidian：把记忆分冷热

原文里我很喜欢的一段，是 Obsidian + Claude Code workflow。

关键不是“Claude 能读 vault”。

关键是把 Obsidian 当三层 memory architecture。

设置方式是：在 Obsidian 里装 obsidian-claude-code-mcp，它会在本地 WebSocket 暴露 vault，端口是 22360。Claude Code 可以 auto-discover。然后在 vault 里放一个 CLAUDE.md，说明你的文件夹结构。

推荐结构：

vault/
├── 00-Inbox/
├── 10-Daily/
├── 20-Projects/
│   └── billing-v2/
│       ├── README.md
│       ├── decisions/
│       └── sessions/
├── 30-Decisions/
├── 40-Atoms/
└── 90-Archive/

三层记忆是：

Hot storage：daily session log。

每个 Claude session 写一个带时间戳的 log 到 10-Daily/。Stop hook 可以自动在 agent 结束后追加结构化 summary。

Warm storage：project notes。

每个项目在 20-Projects/ 下有自己的 folder。新 session 开始前，让 Claude 读项目 README 和最近 2 到 3 个 session logs。30 秒找回两周上下文。

Cold storage：decisions and atoms。

架构决定升格到 30-Decisions/，变成 ADR。可复用知识提炼到 40-Atoms/，再用 wikilinks 串起来。

日常 prompt 可以很简单：

  • • 我的 inbox 里有什么？帮我总结并建议归档位置。
  • • 查 30-Decisions/，有没有和 retry policies 相关的内容。
  • • 读 billing-v2 最近 3 个 session logs，告诉我上次停在哪里。

这比“每次从零解释项目”舒服太多。

AI 编程真正累人的不是写代码。

是反复给一个健忘的聪明人补课。

Obsidian 这套，就是给它补一块外置海马体。

一天怎么用，才像工程师

原文给的 daily workflow 很具体。

早上打开项目里的 Claude Code。

先看 subagents 和 scheduled jobs 昨晚干了什么。

每周跑一次 /insights，看看自己的使用模式。

做新 feature：

Plan mode，读代码，出计划。

Ctrl+G 改计划。

执行。

再叫 /pr-review subagent 或开新 Claude session 做 review。

修 bug：

先复现。

把错误 pipe 给 Claude：

cat error.log | claude

先让 Claude 写一个能复现问题的 failing test。

再让它修。

否则它只是猜。

迁移或大规模修改：

用 /batch。它会先采访你，弄清楚变更，再把任务分给 parallel agents。每个 agent 在自己的 worktree 里测试和创建 PR。

不熟的代码：

直接用 subagent。

比如：

Use a subagent to investigate how our auth handles token refresh.

让它在自己的 context 里读几十个文件，然后回一份 summary。

主 session 保持干净。

并行 session：

Boris 和团队把这称为最大 productivity unlock。

开 3 到 5 个 git worktrees，每个 worktree 一个 Claude session。用 agent view，也就是 claude agents，当控制台。

Writer/Reviewer 模式：

Session A 写。

Session B 用新上下文审。

把 review 拷回 A，修，再循环。

阶段性完成后 /compact：

提示它保留 decisions、files changed、test commands。

收工前，千万别让 Claude 无证据 claim success。

测试、截图、真实命令输出，至少要有一个。

信任 Claude 可以。

让它自证更好。

Anthropic 团队的实战心法

原文收尾处整理了一组来自 Boris、Cat Wu、Thariq 和 Anthropic 团队的习惯。

我把它们翻成更容易执行的清单。

给 Claude 验证输出的办法。

这是 Boris 最常重复的建议。测试、截图、CLI exit code、CI endpoint，都可以。

高价值任务默认用 Opus，并开 high 或 xhigh effort。

原文里 Boris 的理由很现实：小模型如果需要你反复纠正，整体反而更慢。

同时跑 3 到 5 个 sessions。

用 worktrees，不要只在一个 checkout 里来回切。可以用 claude --worktree 或 Desktop app，agent view 统一看。

每个项目维护 notes directory。

每次 PR 后更新。再让 CLAUDE.md 指向它。代码库会积累自我知识。

做一个 /techdebt slash command。

每个 session 结束前跑一下，找重复代码和可以顺手杀掉的小债。

CLAUDE.md 是 living document。

团队每周多次更新。任何人看到 Claude 犯错，都加规则。

Esc 两次打开 rewind。

配合 checkpoints，适合大胆试错，失败了干净回退。

UI 改动配 Playwright MCP。

Boris 做 web code 时会让 Claude 打开浏览器、点击、验证。不是只看 DOM 想象。

装 language server plugin。

每次 edit 后抓 type errors 和 unused imports。原文称这是最高影响力插件。

用 /voice。

你说话比打字快三倍，prompt 会自然变长、变具体。

auto mode + /focus + /goal。

清晰 brief，加可验证目标，减少中间噪音。

Ctrl+G 改计划。

比在聊天框里来回解释快。

让 Claude 画 ASCII diagrams。

遇到新协议、新代码库，让它先画结构图，理解会快很多。

我的判断：prompt 时代结束了

很多 Claude Code 教程都在教 prompt。

但这篇原文真正想说的不是 prompt。

它讲的是一件更工程化的事：

不要只使用 Claude Code，要运营 Claude Code。

CLAUDE.md 是团队宪法。

CLAUDE.local.md 是私人纠错本。

Skills 是可复用 expertise。

Subagents 是上下文隔离。

Plugins 是能力包。

MCP 是系统连接器。

/goal、/loop、/schedule 是持续执行。

Playwright、tests、CI、language server 是验证回路。

这些东西合起来，才让 Claude Code 从“会写代码的模型”变成“能被训练的工程队友”。

我觉得未来的 AI 编程分水岭会很明显。

一类人继续比 prompt 谁写得更玄。

另一类人开始建设自己的 agent operating system。

前者每次都从零开始。

后者每次都在复利。

如果你今天只想做一件事，我建议别先装 20 个 plugin。

先打开你的项目，写一个短到不能再短的 CLAUDE.md：

  • • 用什么包管理器。
  • • 怎么跑单测。
  • • 怎么跑 lint。
  • • 哪些架构边界不能破。
  • • Claude 上次犯过什么错。

然后下一次它犯错时，让它自己补一条规则。

就从这里开始。

AI 编程不是让你少思考。

它是逼你把思考变成系统。
