软件行业正在经历一个相当反常的时刻：造这些工具的人，自己先被工具改变了。

Anthropic 今年 6 月披露，公司内部超过 80% 的合并代码由 Claude 编写;7 月进一步透露，产品团队 65% 的代码变更来自内部版的 Claude Tag;工程师人均季度代码交付量，已经达到过去几年水平的约 8 倍。

听起来像一场生产力革命。但一个问题很快浮现：如果写代码的速度快了 8 倍，而需求评审、设计、测试、Code Review、安全审批和发布流程仍然按人的速度运行，会发生什么?

答案不是"软件交付快了 8 倍"，而是堵车。

8 月 21 日，Anthropic 应用 AI 团队发布《The AI-Native SDLC Playbook》，第一次系统性地回答了这个问题。三天后，GitLab CEO Bill Staples 发表长文《When Code Is Abundant》，把问题继续向前追问了一步：如果代码真的从稀缺走向充裕，软件工程里真正稀缺的东西是什么?

他给出的答案是：信任。代码生成正在变得便宜，但"这个改动到底对不对、能不能上线、会不会出事故"，一点也没有变便宜。

把这两篇文章放在一起读，可能比最近任何一次 SWE-bench 排名变化都更值得关注。因为 AI 编程真正的战场，正在从"模型会不会写代码"，转移到"企业敢不敢让它持续交付软件"。

一、AI 编程撞上的第一堵墙，恰恰在代码之外

传统的软件开发生命周期(SDLC)大体遵循 Plan → Design → Build → Test → Deploy → Maintain 这条链路。这套体系过去为什么合理?因为 Build 太贵。一个复杂功能可能需要几周甚至几个月才能完成，于是团队愿意在前面花几轮会议打磨需求、写几十页 PRD，后面再花数天做测试、Review 和安全审批——笨重，但放进以月为单位的开发周期里，尚可接受。

Agent 打破了这个比例。Anthropic 在 Playbook 开篇给出的判断很直接：代码已经不再是瓶颈，你的 SDLC 才是。Build 已经可以压缩到小时级，但它两侧的 Plan、Review/Test、Deploy 仍然按人的速度运行。代码写得越快，Review Queue、CI、安全审批和发布，反而越容易变成新的瓶颈。

这是一个典型的阿姆达尔定律(Amdahl's Law)问题：系统整体提速的上限，取决于没有被优化的那部分占多大比重。假设过去一次交付的时间构成是需求 10% + 设计 10% + 编码 50% + 测试/评审/发布 30%，即便 AI 把编码效率提高十倍，总周期也不可能缩短十倍，因为剩下的 50% 没有动。更糟的是，Agent 还会制造更多并发任务和更多 Diff——以前是开发在等流程，现在可能反过来，流程开始等不住开发。

Anthropic 自己先撞上了这堵墙，所以它真正想改造的，不是 Claude Code 本身，而是 Claude Code 周围的整套软件生产系统。

这也是 AI-native SDLC 最容易被误解的地方。它不是"Plan 用一下 AI，Design 用一下 AI，Test 再用一下 AI"这种零散拼贴，而是要把原本依赖人力推动的 SDLC，改造成一条 Agent 能持续运行、系统能持续验证、人只在关键判断点介入的闭环。

二、真正的变化不是"六阶段"，而是一条新的生产链

Anthropic Academy 给出的完整 Playbook 共 14 课、12 个具体 Play，覆盖传统六阶段。但真正贯穿全程的，是另一条更重要的线——一条由 Markdown 文件串起来的"产物链"：

业务意图 / 生产事件
    ↓
  intent.md   ← 为什么做
    ↓
   spec.md    ← 做成什么样
    ↓
   plan.md    ← 准备怎么做
    ↓
 code + tests
    ↓
PR + review evidence
    ↓
   deploy
    ↓
metrics / incident
    ↓
新的 intent.md(循环开始)

乍看之下，不过是多了几份 Markdown 文件。但这恰恰是整份 Playbook 最重要的设计，Anthropic 把它称为 Artifact-driven Development(产物驱动开发)。

过去，不同角色之间主要靠人来传递信息：业务讲给产品听，产品写给研发，研发解释给测试，测试再把问题交回研发。每转一道手，就丢失一些上下文，这也是绝大多数团队"需求跑偏"的根源。Anthropic 想用结构化产物重构这条链路：intent.md 记录"为什么做"，spec.md 定义"做成什么样"，plan.md 说明"准备怎么做"，代码和测试是执行结果，PR 保存 Review 与批准证据，生产指标和 Incident 又反过来成为下一轮需求的输入。

每个阶段产生的东西，都能被下一个人或 Agent 直接读取和消费——更关键的是，它们全部进入 Git。于是 Git 保存的不再只是"代码发生了什么变化"，而开始保存"为什么要改、准备怎么改、最终怎么改、谁批准了、生产效果怎样"。Anthropic 把这条 Commit 链直接当作 Audit Trail(审计轨迹)。

这比"AI 自动写代码"高出了一个层级：代码库正在从 Software Repository(软件仓库)，演化为 Software Decision Repository(软件决策仓库)。

三、Intent → Spec → Plan：Review 开始向代码之前迁移

这套体系里最有价值的改变之一，是把大量 Review 从"代码写完以后"搬到了"代码还没写的时候"。

先看 intent.md。假设一位客服负责人发现，大量来电只是在询问订单进度。传统流程可能要走完提需求、进 Backlog、产品访谈、写 User Story、排优先级、需求评审这一整套动作，耗时数周。Anthropic 的做法是，让最接近问题的人直接与 Agent 一起，把问题澄清成：问题是什么、谁受影响、期望的结果是什么、有哪些约束、还有哪些问题没有答案——然后提交一份 intent.md。产品负责人不需要重新写一遍，只需要判断这个 Intent 是否值得继续推进。

Intent 通过后，Agent 会读取公司的安全、品牌、UX、合规要求，生成 spec.md。工程师拿到 Spec 后仍然不能直接写代码——Claude Code 会先进入 Plan Mode：可以读代码库，但不能修改代码，必须先产出 plan.md，回答清楚：改哪些文件、按什么顺序、最危险的一步是什么、可能破坏什么、有没有其他方案、最后用什么测试证明自己做对了。只有工程师接受这份 Plan，Agent 才会开始 Build。

这看起来像是重新发明瀑布开发，实际上正相反。过去重视 Planning，是因为写代码太贵;现在重视 Plan，是因为写错代码太便宜。一个 Agent 一晚上就能生成海量 Diff，方向错了以后再逐行 Review，是最昂贵的纠错方式;而在十几行 plan.md 上把方向纠正过来，反而是最便宜的方式。

所以 AI-native SDLC 并没有减少 Review，它只是把 Review 移到了杠杆最高的位置。

四、真正硬核的部分，是把"公司经验"编译给 Agent

如果只看到 intent.md → spec.md → plan.md，这套体系仍然只是一个升级版的需求工程。真正决定 Agent 能否进入企业生产环境的，是另一组机制：CLAUDE.md、Skills、Hooks、Evals。它们解决的是一个更深的问题——同一个 Claude，为什么在一家公司的代码库里工作得很顺畅，到另一家公司却不断犯低级错误?模型相同，组织上下文不同。

CLAUDE.md：把老员工脑子里的东西写给 Agent

CLAUDE.md 更像一份专门给 Agent 准备的"代码库入职手册"，只保存真正影响工作的知识：怎么 Build、怎么 Test、架构如何划分、有哪些编码惯例、哪些目录不能碰、Claude 最容易犯什么错误。Anthropic 的经验很朴素：同一种错误出现第二次，就把纠正方法写进 CLAUDE.md，并且尽量控制在一页以内，因为 Agent 每次 Session 都要重新读取它。

这背后的意义不小。传统 Wiki 里的知识存在，但员工得主动去找、去读、去记;CLAUDE.md 里的知识则直接进入执行上下文。于是一次人工纠错就变成一次永久性的能力沉淀：Agent 犯错 → 人纠正 → 写回 CLAUDE.md → 后续所有 Agent Session 都能获得这份经验。组织经验开始拥有复利。

Skills：把"项目经验"提升成"组织能力"

代码库规范只是局部知识，安全规范、API 设计规则、品牌要求、UX 标准、合规要求往往属于整个组织。Anthropic 用 Skills 解决这个问题：安全部门可以维护一份统一的 Secure API Skill，告诉 Agent 什么时候必须鉴权、如何做输入校验、哪些操作必须写 Audit Log、哪些 PII 永远不能进日志、完成后要跑什么检查。政策变化时，不需要给全公司工程师重新培训，只需要修改 Skill、走审批、Merge——下一次 Agent 工作时，新规则就自动进入上下文。

这已经不太像 Prompt Engineering，更准确地说，是把组织知识转化成机器可消费的运行时 Context。

Hooks：规则不能只靠"请你遵守"

问题随之而来。LLM 是概率系统，Skill 告诉 Claude"不要修改冻结目录"，Claude 大概率会遵守——但如果这个目录绝对不能碰呢?这时就需要 Hook 上场。Hook 是确定性代码，可以在 Agent 执行动作前直接判断 allow / ask / block：保护目录不能改、.env 不能读、凭据不能进入 Diff、生产发布未经授权直接 Block。这一层控制不仅用在 Build 阶段，只要 Agent 在采取行动，Hook 就能介入，发布审批这类"必须有人点头"的场景同样靠它实现。

Anthropic 对两层控制的划分很清晰：Skill 是 advisory control(建议性控制)，Hook 是 deterministic control(确定性控制)。也就是说，概率系统负责判断，确定系统负责边界——这可能是整份 Playbook 里最成熟的一条工程原则：Agent 越强，越不能把所有安全希望都寄托在 Prompt 上。

五、Test 被重新定义：不只测代码，还要测 Agent 本身

AI Coding 真正的分水岭，其实不是"能生成代码"，而是 Agent 有没有能力看见自己的执行结果，并自己纠错——Anthropic 把这称为 Feedback Loop。

写后端，就要求 Agent 具备 Build → Test → Lint → 修复 → 再 Test 的完整回路;写前端，就给 Agent 配上浏览器或截图工具，让它实现 → 截图 → 与设计稿比对 → 调整 → 再截图。Anthropic 还特别要求：Agent 修 Bug 时不能为了让红灯变绿而偷偷改测试代码，因此干脆用 Hook 禁止它在修复任务中碰测试文件。

这一点很关键。没有 Feedback Loop 的 Coding Agent，本质上只是更高级的代码生成器;有了 Feedback Loop，它才真正成为一个"执行—观察—纠错"的系统。

更进一步的是：连 Agent 自己也必须回归测试。传统 CI 测的是代码，但 Agent 的输出还受模型版本、Prompt、CLAUDE.md、Skills、Hooks、工具权限等因素影响，这些一变，Agent 的行为也可能跟着变。因此 Anthropic 又加了一层 Continuous Evals：建议从真实开发中抽取 20~50 个历史任务，保存可接受的结果作为基准。此后无论是换模型、改 Prompt、改 CLAUDE.md、升级 Skill 还是修改 Hook，都要重新跑一遍 Eval Suite。更重要的是，每一次 Production Incident，都应该沉淀为一个新的 Eval Case。

于是事故处理的路径从"出事故 → 修 Bug → 写复盘"，变成"出事故 → 修 Bug → 形成永久 Eval → 以后所有模型和 Harness 变更都会自动回归检验"。这可能是整份 Playbook 最有价值的设计之一——事故开始变成系统的免疫记忆。

一个不容忽视的现实缺口：Kubernetes 基础设施厂商 mirrord 在评论这份 Playbook 时指出，它没有回答一个更底层的问题——Agent 到底在什么环境里测试自己?现实中的微服务往往依赖十几个其他服务、数据库、消息队列，如果多个 Agent 同时对着本地 Mock 跑测试，"Test Passed" 只能证明它和 Mock 相处融洽，证明不了它和今天真实运行的系统相处得好不好。这也是为什么 Agent 越往后发展，测试环境、Sandbox、可重复执行的基础设施，反而会成为 AI Coding 竞争中越来越核心的能力。

六、人的角色没有消失，而是从执行链路上移

当一个工程师可以同时启动多个 Agent，个人效率会出现第二次变化。Anthropic 建议用 Git Worktree 跑多个独立 Session，再用 Subagent 拆分角色：一个 Builder 可以同时调用 Research Agent、Security Reviewer、Code Simplifier、Verifier。

最终负责验证的 Verifier，最好拥有一份"干净"的上下文——因为写代码的 Agent 在此前的推理过程中已经形成了自己的假设，让它审核自己，很容易沿着原有假设继续证明自己是对的。新的 Verifier 需要重新启动程序、走一遍真实流程、检查周边功能，甚至可以不拥有 Edit 权限：它只能证明，不能偷偷修改。

这其实一点也不新，只是把软件工程几十年的一条老原则重新实现了一遍：职责分离。过去是 Writer 和 Reviewer 两个人，以后可能先是两个 Agent Context，但最终的高风险判断仍然留在人这一端——Agent 写代码时无权批准自己的代码，PR 的合并权限始终由人经过分支保护(branch protection)后授予。Anthropic 在自身的安全实践中说得很明确：Claude 可以生成和 Review 大量代码，但高风险、受监管和关键系统的改动仍然保留人工批准，所有审批都要留下相应的信号和理由。

有一组数据值得关注：Anthropic 今年 3 月上线的 Claude Code Review 功能，在内部几乎所有 PR 上运行数月后，获得实质性 Review Comment 的 PR 比例从 16% 提升到 54%，超过 1000 行的大改动中有 84% 被发现问题，工程师标记为"误报"的比例低于 1%。回溯过去 claude.ai 的历史事故，Anthropic 估计这套自动化流程目前大约能提前拦截其中三分之一的相关 Bug。

所以所谓 AI-native，并不是把人从 Loop 中移出去，而是把人从机械性的 Loop 中移出去，留在真正的 Judgment Loop 里。

七、真正的终局，是 Production 自己启动下一轮开发

如果 Playbook 到 CI/CD 就结束，它仍然只是一条更自动化的开发流水线。Anthropic 最激进的部分其实在 Maintain 阶段。

8 月 18 日，Anthropic 公开了一个已经真实运行数月的案例：Claude Tag 担任其 CI/CD 故障的第一响应者。一次晚上 10 点发生的故障中，一位工程师的同事在 Slack 上报告新服务上约 44 个测试突然不再执行，过去这意味着一个多小时的排查——翻配置、查最近合并、看日志、猜原因。这次工程师只是在值班频道里 @Claude，几分钟后得到结论：测试消失是因为当天开启的一个 Feature Flag，回滚是安全的。建议回滚后 3 分钟，Claude 主动在 Slack 确认跳过规则已移除、错误率已恢复基线。Anthropic 表示，在最近有完整记录的 CI 事故中，Claude 都承担了第一份分析工作，中位数用时约 15 分钟给出初步判断。

这正是 Maintain 阶段真正想实现的事：不是让一个 LLM 24 小时盯着监控大盘瞎猜，而是让确定性监控先做判断——正常波动只记录;明显异常，Agent 只做只读诊断;严重异常，Agent 可以提出 PR 或执行预先批准的 Rollback;涉及 Production Gate 的操作，仍然必须经过人工授权。

最终形成的闭环是：Production Signal → 确定性异常检测 → Agent Diagnosis → 新的 intent.md → Spec → Plan → Build → Test → Review → Deploy → 再回到 Production。这时软件开发第一次真正闭合——生产环境不再只是软件生命周期的终点，而是开始成为下一轮开发的起点。

八、真正优秀的后续讨论，都在补 Anthropic 没讲透的部分

Playbook 发布三天后，GitLab CEO Bill Staples 在《When Code Is Abundant》里把判断又向前推进了一步：代码生产正在变得充裕，但好软件没有——真正的瓶颈正从 Code Production 转向 Trust。他从今年 1 月就开始思考这个问题，5 月在 GitLab《Act 2》里发表过部分论点，这篇文章是过去八个月观察 GitLab 自身工程团队以及 Stripe、Spotify、Amplitude 等公司实践后的延续思考。

他因此提出，软件工程应该换一个衡量单位。过去我们习惯算代码行数、Developer Productivity、一个工程师能写多少功能;但 Agent 时代真正该算的是 Cost per Accepted Change——每一个最终被接受的软件变更，到底花了多少成本，这其中包括生成、环境准备、上下文、验证、Review、返工和治理。AI 主要压缩的是"生成"这一环：如果代码生成快了十倍，但 CI 还是半小时、Review 还是排一天队、测试环境还是两小时才能起来，组织根本不会快十倍，只会把 Queue 挪到另一个地方。这可能是比"AI 代码占比"更值得管理层关注的指标。

第一块缺口：Harness 之外，还需要 Platform Harness

云原生开发者协同平台 Port.io 在 8 月底的分析里指出了另一个问题：intent.md 很好，但企业里真正的 Intent 往往来自 Slack 请求、客户工单、Sentry Error、PagerDuty Incident。谁判断它属于哪个 Repo?谁知道这个 Service 的 Owner 是谁?谁能算清楚改动会影响哪些下游系统?谁判断这个系统是不是一级关键业务?谁决定该找哪个 Reviewer?这些信息既不在模型里，也不在 CLAUDE.md 里，它们属于企业的平台上下文。

所以真正大规模的 AI-native SDLC，很可能需要两层 Harness：Agent Harness 管一个 Agent 怎么工作，Platform Harness 管几百个 Agent 如何在整个组织里协同工作，后者需要掌握服务目录、依赖关系、Owner、权限、风险等级、Incident History 和组织政策。这可能才是企业级 Agent 和个人使用 Claude Code 之间最大的分水岭。

第二块缺口：Verification 最终是基础设施问题

mirrord 母公司 MetalBear 的文章戳中了 Playbook 更现实的软肋：Playbook 建议用 Git Worktree 同时跑多个 Claude Code Session，但这只解决了代码层面的隔离，没有解决它们要连接的那个 Staging 集群该怎么办——多个 Agent 同时指向同一个测试环境，会互相干扰，也会打扰正在使用它的真人工程师，这也是很多组织最终放弃共享 Staging、退回"每个 Agent 一套慢而浅的独立环境"的原因。真正的解法是让基础设施本身支持并发：按请求头分流每个 Agent 的流量、给消息队列切分独立分区、给数据库做分支(branching)，让一套 Staging 集群同时服务任意多个 Agent Session。

当 Agent 逐渐承担真正的软件交付工作后，测试环境、Sandbox、真实依赖访问、Observability 和可重复执行的环境，都会从后台基础设施变成 AI Coding 的核心产品能力。这也是为什么 AI Coding 越往后发展，竞争反而越不像"一个更好的聊天框"。

九、十二个 Play，不应该从头到尾一次性改完

有一个大量二手解读容易忽略的细节：Anthropic 给出的六个阶段是运行顺序，却不是建设顺序。官方明确给出了一张 Dependency Graph——有些 Play 没有前置依赖，可以先做;有些则必须建立在前面的能力之上。

对绝大多数团队来说，最先该做的其实很朴素：把 Intent 结构化、写一份短小的 CLAUDE.md、让 Agent 每次都能 Build/Test/Lint、加一两个真正有用的 Hook、让复杂任务先 Plan 再 Build。之后再逐步增加 Skills、Subagents、Continuous Evals、AI Review、CI/CD Agent、Production Closed Loop。

这一点很重要，因为 AI 自治并不是一个 Feature，而是 Context、Feedback、Verification、Permission 和 Governance 足够成熟之后自然长出来的结果。如果前面这些没有打好基础，直接追求"无人开发"，基本等于把技术债和事故一起自动化。

十、AI-native SDLC 最终改变的，可能不是研发，而是组织

把 Anthropic、GitLab，以及 Port.io、mirrord 等后续分析放在一起看，会发现一条比 Claude Code 本身更大的趋势。

AI 编程的第一阶段解决的是"模型能不能写代码"，第二阶段解决的是"Agent 能不能独立完成任务"。而现在的问题已经变成：一个组织，能不能让大量 Agent 同时工作，却仍然保持目标一致、知识一致、权限受控、结果可验证、责任可追踪。

这时真正关键的资产，不再只是代码，还包括：intent.md 沉淀的问题与目标、CLAUDE.md 沉淀的项目经验、Skills 沉淀的组织能力、Hooks 沉淀的制度边界、Evals 沉淀的历史教训、Production Metrics 沉淀的真实反馈。那些原本看起来很"软"的东西——经验、制度、方法、上下文、复盘——第一次开始变成 Agent 可以直接执行的生产资料。

Bill Staples 把这一层概括为 Context、Verification、Governance 和 Evidence 四要素，并进一步指出：未来企业会同时使用多个模型和多个 Agent，因此真正应该长期属于企业的，不是某一个模型，而是模型外面那层组织 Context 与控制体系。这个判断，很可能比"谁是最强 Coding Model"重要得多。

模型会换，Agent 会换。今天是 Claude Code，明天可能是 Codex，也可能是企业自己的 Harness。但一家公司的架构知识、业务规则、安全规范、历史事故、判断标准、审批权限、质量证据，不应该随着 Agent 一起被换掉。模型是执行器，组织 Context 才是资产。

十一、代码不再稀缺之后，人真正值钱的地方才暴露出来

所以，"代码不再是瓶颈"并不意味着代码不重要，更不意味着软件工程师不重要。真正发生的事情，是价值位置整体向上移动了。

当 Agent 能够大量承担 Implementation 的工作，人类会更集中在：这个问题到底值不值得解决、Intent 是否正确、架构该怎么取舍、什么风险可以承担、验证标准是否可信、规则什么时候应该被打破、出了问题到底由谁负责。Anthropic 内部管理 Claude Code 团队的负责人自己就描述过这种转变：早期团队还会认真写一份六个月的 Roadmap，但因为 Claude Code 本身进化太快，通常三个月就已经过时;现在团队的做法是"即时规划"(Just-in-Time Planning)，把设计文档为主的计划仪式，换成在 PR 和原型里边做边讨论——工程师更多承担 Context、设计与判断工作，而不是单纯以 Raw Coding Throughput 来衡量价值。

这也是整份 AI-native SDLC Playbook 最值得记住的地方。它表面写的是 Plan、Design、Build、Test、Deploy、Maintain，真正重新分配的却是三样东西：机器负责执行，系统负责验证和约束，人负责意图与判断。

过去六十年，软件工程一直在想办法保护一种稀缺资源：代码生产能力。如果 Agent 最终真的让这种能力变得越来越充裕，那么下一代软件工程要解决的，就完全是另一道题：如何让大量代码变化仍然符合正确的业务意图，如何让组织知识稳定进入 Agent，如何让机器自己拿到真实反馈，如何让制度从文档变成可执行的边界，如何让每一次失败永久增加系统的免疫力——以及最重要的，当一切都可以自动执行时，谁仍然对最终结果负责。

AI 编程的上半场，是把代码写出来。下半场，是让企业敢把它交付出去。这才是 AI-native SDLC 真正开始的地方。
