AI Agent 的叙事几乎被三个词占满：更强模型、更长上下文、更多工具。

但真正把 Claude Code、Codex、Copilot、Windsurf、Devin 放进日常工作流的人，会遇到一个更朴素的问题：Agent 很聪明，却不连续。它今天能帮你改完一个模块，明天又像刚入职的新同事；它能临时吃下几万 token 的上下文，却很难稳定继承“这个项目为什么不能这么改”。

这不是一个小体验问题，而是 AI 软件从玩具走向生产系统时必然撞上的墙。

没有记忆的 Agent，本质上是一次性执行器；有记忆但不可治理的 Agent，则是高风险助手。

Mem0 最近发了一篇很长的 thread，标题是《State of Memory in Agent Harness》。它把 Claude Code、Codex、GitHub Copilot、OpenClaw、Hermes、AWS Bedrock AgentCore、Windsurf、Devin 等一圈 Agent harness 的 memory 实现摊开比较。表面看，这是一份“各家怎么做 memory”的技术盘点；但如果从第一性原理看，它真正指向的是一个更大的判断：

Agent 的竞争正在从模型能力，迁移到 harness 的状态管理能力。

原文里有两句话很值得抓住。

"The harness, not the model, is increasingly the product that ships software."

越来越多时候，真正交付软件能力的不是模型本身，而是 harness。

"Memory is where harness design gets hard."

记忆，是 harness 设计真正变难的地方。

换句话说，Agent 不是“模型 + 工具”的简单相加。它要管理上下文、调度工具、沉淀经验、更新状态、控制权限、处理过期事实，还要保证不同用户、不同项目、不同团队之间不会互相污染。这里面的核心，不是“它能不能记住一句话”，而是“它能不能把过去的经验转化为下一次行动的约束”。

这才是 memory 的真实含义。

记忆不是长上下文

很多人把 long context 当成 memory，这是一个很常见的误解。长上下文更像一次会议里的白板，能写很多东西，也能让模型在这一轮任务里看得更远；但会议结束后，白板擦掉了，下一次仍然要重新解释。

真正的 Agent memory 更接近公司的知识库、工单系统、代码注释、复盘文档和权限体系的混合体。它不只保存信息，还要决定哪些信息值得留下，什么时候被召回，什么时候被更新，什么时候必须失效，以及谁有资格看见。

Mem0 原文把 Agent memory 分成三层，这个区分很关键。

Working memory 是上下文窗口里的临时状态，解决的是“这一轮任务能带多少材料”。窗口满了之后，哪些内容幸存下来，属于 compaction 问题。

External memory 是模型权重之外的持久化系统，比如 Markdown、SQLite、向量库、知识图谱、文件系统。2026 年几乎所有生产级 Agent memory，都还在这一层。

Parametric memory 是通过训练写进模型权重的知识，它更像“学会规则”，不是“检索旧笔记”。但在今天的生产 Agent 里，这一层基本还没有成为常规部署方式。

所以，Agent memory 现在首先不是模型训练问题，而是软件工程问题。它要回答的不是“上下文能不能更长”，而是六个更硬的问题：怎么写入，怎么检索，怎么去重，怎么更新，怎么处理过期，怎么隔离身份。

只要其中一个问题没处理好，Agent 就会从“健忘”走向“乱记”。前者烦，后者危险。

九种记忆路线

Mem0 这篇 thread 的信息密度很高，但最有价值的不是把九个工具背下来，而是看清它们背后的路线差异。大家都在做 memory，却没有一个方案接近终局；每一家都在自己的产品边界里，选择了一种最符合自身场景的记忆观。

Claude Code：透明的项目笔记，但检索还偏文件级

Claude Code 有两条 memory 轨道。一条是人写的 CLAUDE.md，记录项目约定、编码规范、特殊指令，在会话开始时读入；另一条是 auto-memory，由后台提取 Agent 写入本地目录，典型路径是 ~/.claude/projects/<repo>/memory/，再围绕 MEMORY.md 做索引，内容分成 user、feedback、project、reference 四类。

这个设计很工程友好，因为开发者能看见、能改、能把它当成 repo 的上下文资产。但它的检索方式并不是真正的语义搜索：每一轮 Claude Code 会把文件名和描述交给一个较小模型，让它决定加载哪些文件；没有 embeddings，每轮最多加载 5 个文件，超过上限还可能静默截断。

这意味着，Claude Code 的 memory 更像“结构化项目笔记”，而不是成熟的长期语义记忆系统。文件命名、索引描述、CLAUDE.md 的组织方式，都会直接影响它下次能不能找回正确上下文。

Anthropic Managed Agents：把记忆做成 workspace 的审计资产

Anthropic Managed Agents 不是 Claude Code 这种本地开发工具，而是托管 Agent runtime。它的 memory 更偏企业工作空间：session 是 append-only event log，天然支持回滚和审计；memory store 以文件系统形式挂载在 /mnt/memory/，每个 workspace 最多 8 个 store，每个大约 100KB；每次写入都是不可变版本，多个 Agent 可以共享同一个 store，并保留可审计历史。

这条路线说明，企业场景里的 memory 首先不一定是“更懂我”，而是可追踪、可回滚、可协作。它的短板也来自同一个方向：workspace 级 memory 不等于长期个人 memory，100KB 的 store 上限和 workspace scope，也不天然解决跨会话、跨工作区、跨身份的上下文积累。

Codex：写入流程很认真，读取方式仍偏原始

Codex 的 memory 放在 ~/.codex/memories/，包括 memory_summary.md、MEMORY.md、raw_memories.md、skills/ 和 rollout_summaries/ 等文件，默认关闭，需要通过 features.memories 启用。

它最值得看的是写入路径。Codex 不是在对话结束后随手写文件，而是分成两阶段：第一阶段在 session idle 6 小时后做提取、脱敏，先写入本地 state DB；第二阶段由 consolidation sub-agent 在全局锁下合并、修补、丢弃，最后把 diff 写进 memory 目录。

这说明 OpenAI 已经意识到一件事：memory 不是日志，而是加工后的状态。真正的问题在读取端，Codex 先读固定预算的 summary，其他内容靠 grep 找 MEMORY.md。summary 会被 5,000 token 预算截断，grep 只能匹配字面表达；如果事实换了一种说法，就可能从系统视野里消失。

所以 Codex 的 memory 给我的感觉是稳，但还不够灵。它像一套谨慎的本地工作日志整理系统，还不是实时、语义化、跨工具的长期经验层。

GitHub Copilot：记忆必须带证据

Copilot 的突出点是 just-in-time citation verification。它的 memory item 不是一段随意笔记，而是结构化对象：subject、factual content、file-and-line citation、reasoning。使用 memory 前，Agent 会对照当前分支验证 citation 是否仍然成立；如果代码已经改变，旧 memory 就会被重写或废弃。

这一步非常关键。真实工程里，memory 最大的风险往往不是忘记，而是记住了过期事实。一个已经被重构掉的接口、一个不再成立的约束、一个上个版本才有的 bug，如果被 Agent 当成当前事实调用，危害比失忆更大。

Copilot 也是少数拿出生产指标的方案。原文提到，开启 memory 后，PR merge rate 从 83% 提升到 90%，code-review precision +3%，recall +4%。这组数据很有杀伤力，因为它不是单纯 benchmark，而是进入真实开发流程后的结果。

它的问题也很清楚：citation schema 很适合代码事实，却很难承载“偏好最小抽象”“这个团队不喜欢引入重依赖”这类难以落到具体文件行号的经验。工程事实可以被验证，人的偏好和团队风格更难被结构化。

OpenClaw：有语义检索，但长期保留不稳定

OpenClaw 的原生 memory 比很多人想象中更先进。它用 ~/.openclaw/workspace 下的 Markdown 记录 curated MEMORY.md 和 dated daily logs，底层还有 per-agent SQLite index，支持 embeddings 和 hybrid retrieval，权重是 70% vector、30% BM25。

这说明 OpenClaw 已经越过了纯 grep 或文件名选择阶段，真正开始考虑语义召回。但它的问题在“什么能长期留下”。当 context window 快满时，OpenClaw 会触发一次 silent internal turn，让模型先把重要内容写到磁盘，再清空上下文。哪些经验进入长期记忆，很大程度上取决于模型在那一次内部回合里的判断。

这仍然不够稳定。memory 系统不能只靠“模型临场觉得什么重要”，它需要明确的抽取、更新、去重、失效和隔离机制。Mem0 的 OpenClaw 插件正是从这个缺口切入：Auto-Recall 在每轮对话前注入相关记忆，Auto-Capture 在每轮对话后持久化交换内容，新事实写入，旧事实更新，重复内容合并，并用 run_id 与 userId 区分 session 和长期身份。

Hermes Agent：像 Agent OS，但内置记忆容量太小

Hermes Agent 的 memory 结构很完整，甚至有点像一个小型 Agent OS。第一层是 working memory：MEMORY.md 约 2,200 chars，USER.md 约 1,375 chars，合计约 1,300 tokens，有容量仪表，并在 80% 容量时触发 consolidation。第二层是 skills：在 5 次以上 tool-call 任务后形成 procedural docs，再按计划整理。第三层是 session search：用 SQLite FTS5 搜索历史会话并按需总结。

这套设计最有意思的地方，是它不只记用户说过什么，还尝试沉淀 Agent 怎么做事。问题是容量太小，FTS5 本质上仍偏关键词检索；并且为了保留 prefix cache，本轮写入磁盘的内容通常要到下一次 session 才进入系统 prompt。

所以 Hermes 的内置 memory 架构感很强，但还没有真正突破本地小容量限制。它预留 provider slot，也说明它自己知道：长期 memory 很可能需要外部系统接管。

AWS Bedrock AgentCore：企业级托管 memory，但绑定云生态

AWS Bedrock AgentCore 是另一种路线。它把 Runtime 当成 harness 层，把 Memory 做成 managed service，支持三类异步抽取：semantic facts、preferences、narrative summary。变更过的事实不会直接删除，而是标记为 INVALID，保留 lineage。

这很适合企业理解 memory：事实有生命周期，状态有沿袭，系统要能审计。公开指标里，AgentCore Memory 报告了 LoCoMo 70.58、PrefEval 79、PolyBench-QA 83.02。短板也很 AWS：如果你本来就在 AWS 上跑 Agent，它会很顺；如果你希望 memory 跨模型、跨云、跨工具迁移，就必须认真考虑生态锁定。

Windsurf：无感自动记忆，也意味着不可控

Windsurf 的 memory 由 Cascade 自动生成和管理，存储在本地 workspace 文件里，主要记录代码库模式和约定。它的产品选择很清楚：开发者不用管理 memory，系统自己决定记什么。

这种设计短期体验很好，因为用户没有维护成本。但长期看，自动化越强，治理问题越重。你不太知道它为什么记、记了什么、什么时候会更新、什么时候该失效；同时 memory 被锁在 workspace 里，跨项目、跨设备、团队共享都不自然。

Devin：人工审批保证质量，但很难自然积累

Devin 把 memory 分成 Knowledge 和 DeepWiki。Knowledge 是人工 curated 的 trigger-content 事实，不自动捕获；DeepWiki 更像参考文档，有 30 pages、100 notes、每条 10,000 chars 的限制。Devin 会在 session 后建议沉淀 Knowledge，但最终要人确认。

这条路线保守，也现实。全自动容易乱记，人工审核能保证质量；但如果团队没有 review 习惯，memory 就不会增长。更麻烦的是，Devin 的 Knowledge 是为 Devin 策展的，很难自然迁移到 Claude Code、Codex 或 Windsurf。

真正的问题：memory 还没有成为基础设施

把九种方案放在一起看，结论其实很清楚：今天的 Agent memory 已经普遍存在，但大多数仍是各自工具内部的小功能。它们有价值，但边界太窄。

第一，存储常常有上限，并且大多本地化。Claude Code 有 25KB / 200 行索引限制，Hermes 内置 durable memory 容量很小，Codex summary 有 5,000 token 预算。容量一小，长期任务一复杂，memory 就会变成精选摘要，而不是完整经验系统。

第二，检索仍然太粗糙。Claude Code 靠文件名和描述选择，Codex 靠 grep，Hermes 靠 FTS5；它们能找到字面匹配的内容，却很难稳定找到语义相关的经验。OpenClaw 已经有 hybrid retrieval，AgentCore 也有云端语义能力，但前者受本地与 compaction 影响，后者绑定云生态。

第三，memory 被 harness 锁住。Claude Code 记住的东西，Codex 不知道；Windsurf 沉淀的 workspace，Devin 用不上。用户和组织的长期经验，本来应该属于人和团队，现在却被切成了各家工具里的小碎片。

第四，过期和污染问题还没有真正解决。Copilot 的 citation verification 是亮点，但更多系统缺少成熟的 staleness handling。更麻烦的是，memory 本身会成为攻击面。参考内容提到，研究测到正常使用下也可能出现 57%-71% 的 cross-user contamination，memory poisoning 攻击成功率也能到 6%-38%。

这就是我最想强调的一句话：

Agent 失忆很烦，Agent 乱记更可怕。

Benchmark 也没有测到核心

一个领域如果 benchmark 不靠谱，通常说明它还没有真正定义清楚自己要解决什么问题。现在很多 memory benchmark 测的是“你还记不记得过去对话里的事实”，这当然有用，但远远不够。

真实工作里的 memory，不是为了复述过去，而是为了指导行动。一个 Agent 能答出“上次用户说他喜欢 TypeScript”，不代表它能在重构项目时做出更好的工程判断；一个 Agent 能找回“某个接口上次改过”，也不代表它知道这次该不该再改。

LoCoMo 的问题在于样本小、很多问题不真正需要 memory，简单 grep baseline 都能拿到约 74% 的分数。LongMemEval 更严肃一些，有 500 个 curated questions，覆盖信息提取、跨会话推理、时序推理、知识更新和 abstention，并扩展到约 1.5M tokens，但仍然偏 recall-centric。

更接近核心的是 MemoryArena 和 Anatomy of Agentic Memory 这类研究，它们批评的正是“高分不等于能做对事”。生产环境还有规模问题：标准 benchmark 往往停在 1.5M tokens 左右，而真实 Agent 历史可能达到 10M+ tokens。BEAM 这种面向更大规模的测试，才更接近未来战场。

所以，看到任何 memory leaderboard 都别急着下结论。它们能告诉你系统会不会背过去的事实，却很难证明它真的能让下一次行动更正确。

Mem0 的位置：把 memory 推到工具边界之外

这篇 thread 当然带有 Mem0 自己的产品立场，这一点要先讲清楚。它会强调 harness-native memory 的边界，也会强调 external memory layer 的价值；这不是问题，问题是我们不能把厂商文章当成中立裁判。

但 Mem0 提出的方向是成立的：memory 不应该只是某个 Agent 工具里的附属功能，而应该成为跨 Agent、跨项目、跨团队的基础设施。

Mem0 的架构是 hybrid：vector store 负责语义检索，knowledge graph 负责关系推理，key-value 负责快速 metadata。v3 算法在 2026 年 4 月转向 single-pass ADD-only extraction，把 semantic、BM25、entity linking 放进同一轮 retrieval，并把 entity linking 放进 vector store，减少对外部 graph DB 的依赖。参考内容给出的对比是，Mem0 每次 query 大约 6,900 tokens、1.44 秒，而 full-context retrieval 大约 26,000 tokens、17.12 秒。

这组数字适合传播，但我更在意的是它背后的产品判断：memory 不应该属于某一个 Agent，而应该属于用户、团队和组织。如果这件事能做成，Claude Code 今天记住的项目偏好，明天 Codex 可以用；OpenClaw 沉淀的任务历史，后天 Hermes 可以接；企业内部的多个 Agent 不必各自维护一套碎片化小脑。

我的判断是：Mem0 的方向是对的，但最后赢的不一定是 Mem0。

记忆层会成为基础设施，这点我信；但基础设施到底是开源层、云服务、模型厂商内建能力，还是 IDE / Agent runtime 的一部分，现在还没有定。真正重要的是，未来的 memory 系统必须具备五个能力：语义检索、跨工具迁移、身份隔离、过期处理、可审计治理。

这五件事，才是 memory 从“高级便签”变成“生产基础设施”的分水岭。
